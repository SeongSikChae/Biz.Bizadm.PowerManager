# MQTT 접속 인증 강제

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #26

## 무엇을, 왜

내장 MQTT 브로커는 접속 인증을 하지 않는다(mqtt-broker R1). R9는 접속마다 비밀번호를 등록 `mqtt_key`와 비교해 `Match`·`Mismatch`·`Unknown`으로 판정하지만, 로그만 남기고 접속은 모두 받는다. 인증을 강제하기 전에 장비가 보내는 자격 증명 형식을 보려고 둔 관찰 단계였고, B540 실장비에서 비밀번호가 등록 `mqtt_key`와 같음(`Match`)을 확인했다(docs/specs/dawon-fake-device/spec.md).

이제 판정 결과대로 접속을 거부한다. 등록된 장치가 등록 `mqtt_key`로 접속할 때만 받고, 그 밖의 접속은 받지 않는다(D001). 확인하지 못한 접속도 받지 않는다(D002). 켜고 끄는 설정은 두지 않고 늘 강제한다(D003).

이 변경으로 서버 등록(`device-register`)을 거치지 않은 장치(예: V1 설정 도구로 `mqtt_key`를 직접 넣은 장치)와 `DAWONDNS-{mac}` 형식이 아닌 ClientId의 클라이언트는 이 브로커에 접속할 수 없게 된다.

## 완료 조건

- C1. 판정이 `Match`(ClientId `DAWONDNS-{12자리 16진수}`, 그 mac이 등록돼 있음(대소문자 무관), 비밀번호가 등록 `mqtt_key`와 같음)인 클라이언트는 비TLS·TLS 엔드포인트 모두에서 접속에 성공하고, 접속 뒤 발행·구독이 지금과 같이 동작한다.
- C2. 판정이 `Mismatch`(mac은 등록돼 있으나 비밀번호가 다르거나 없음)이면 접속을 거부하고, MQTT 3.1·3.1.1 클라이언트는 CONNACK 반환 코드 4(잘못된 사용자명 또는 비밀번호)를 받는다.
- C3. 판정이 `Unknown`(ClientId가 `DAWONDNS-{12자리 16진수}` 형식이 아니거나 그 mac이 등록돼 있지 않음)이면, C4의 예외 때는 빼고, 접속을 거부하고, MQTT 3.1·3.1.1 클라이언트는 CONNACK 반환 코드 4를 받는다(D001, D004).
- C4. 접속 확인 중 예외가 나면 Error 로그를 남기고 접속을 거부하며, MQTT 3.1·3.1.1 클라이언트는 CONNACK 반환 코드 3(서버 사용 불가)을 받는다(D002).
- C5. 인증을 끄는 설정 항목을 두지 않는다. 설정과 상관없이 C1~C4가 늘 적용된다(D003).
- C6. 접속마다 남기는 R9 로그(ClientId, 사용자명, 비밀번호 유무, 판정)는 거부한 접속에도 하나씩 남고, C4의 예외 때 판정은 `Unknown`이다. 비밀번호 값은 어떤 로그에도 남지 않는다.
- C7. 서버가 브로커에 주입하는 메시지(`tisyn` 응답)는 접속 인증과 상관없이 지금처럼 구독한 장치에 전달된다.
- C8. 배포본에서 B540 실장비 접속에 대해 서버 로그에 R9 판정 `Match` 로그, 그 장치의 `tisyn`에 대한 R5 응답 로그, 그 ClientId를 받는 쪽으로 한 R12 큐 넣음 로그가 있다.
- C9. 기준 spec `docs/features/mqtt-broker.md`의 R1에서 "접속 인증은 하지 않는다"를 R9 기준의 접속 인증으로 바꾸고, R9에 C2~C4의 거부와 C6(예외 때 판정 `Unknown`, 거부한 접속에도 로그)을 반영하고, 머리말·`파일:` 줄을 맞추고, 이력에 이번 작업 한 줄을 더한다.
