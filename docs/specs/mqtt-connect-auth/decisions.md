# MQTT 접속 인증 강제 결정

### D001 판정이 `Unknown`인 접속은 거부한다
- 단계: spec
- 질문: mqtt-broker R9의 판정 `Unknown`(ClientId가 `DAWONDNS-{12자리 16진수}` 형식이 아니거나, 그 mac이 `device-register`에 등록돼 있지 않음)인 접속을 받을지 거부할지. V1 설정 도구로 `mqtt_key`를 장치에 직접 넣고 서버 등록(`POST /api/v1/devices/register/create`)을 거치지 않은 장치(예: M130-W)도 여기에 들어갈 수 있다.
- 선택지:
  - A. 거부: 등록된 mac의 장치가 등록 `mqtt_key`로 접속할 때(`Match`)만 받는다. 등록하지 않은 장치와 형식이 다른 클라이언트는 접속하지 못한다.
  - B. 허용: 등록된 mac인데 비밀번호가 틀린 경우(`Mismatch`)만 거부하고, `Unknown`은 지금처럼 받고 로그만 남긴다.
- 결정: A
- 이유: A는 등록·키 없는 접속을 막는다는 인증 강제의 목적을 그대로 채운다. B는 등록되지 않은 mac이나 형식이 다른 ClientId로는 누구나 접속할 수 있어, 인증 효과가 등록된 mac을 사칭하는 경우로만 줄어들어 고르지 않았다.
- 반영: spec.md C3

### D002 접속 확인 중 예외가 나면 거부한다
- 단계: spec
- 질문: 접속 확인 중 예외(예: SQLite 조회 실패)가 나면 받을지 거부할지. 지금은 Error 로그만 남기고 접속을 받는다.
- 선택지:
  - A. 거부(fail-closed): Error 로그를 남기고 접속을 거부한다. DB 장애 동안 장치는 접속하지 못하고 다시 접속을 시도한다.
  - B. 허용(fail-open): 지금처럼 Error 로그만 남기고 접속을 받는다. DB 장애 동안 인증 없이 접속된다.
- 결정: A
- 이유: A는 장애를 틈타 인증 없이 접속되는 일을 막는다. B는 가용성은 높지만 장애 때 인증이 꺼지므로 고르지 않았다.
- 반영: spec.md C4

### D003 인증 강제를 켜고 끄는 설정을 두지 않는다
- 단계: spec
- 질문: 인증 강제를 설정 항목으로 켜고 끌 수 있게 할지(끄면 지금처럼 판정 로그만 남기고 모두 받음).
- 선택지:
  - A. 설정으로 켬/끔: `AppConfiguration`에 불(bool) 설정 하나를 더하고 기본값을 켬(강제)으로 둔다. 등록하지 않은 장치를 붙여야 할 때 코드 배포 없이 끌 수 있다.
  - B. 늘 강제: 설정을 더하지 않고 늘 인증을 강제한다. 끄려면 코드를 바꿔 다시 배포해야 한다.
- 결정: B
- 이유: 사용자가 B를 골랐다. B는 설정 항목·검증·테스트가 늘지 않아 가장 단순하다. A는 되돌리기는 쉽지만 설정 항목과 그 검증·테스트가 늘어 고르지 않았다.
- 반영: spec.md C5

### D004 예외 때 판정은 `Unknown`으로 두고 C3에서 예외를 뺀다
- 단계: spec
- 질문: spec 검토 3회차 지적 1. 검토 의견: C3은 "판정이 `Unknown`이면 CONNACK 4", C6은 "C4의 예외 때 판정은 `Unknown`", C4는 "예외면 CONNACK 3"이라 예외가 난 접속에 반환 코드 3과 4가 함께 정해진다. 판정 값만으로 반환 코드를 고르게 구현하면 D002가 정한 CONNACK 3 대신 4가 나갈 수 있고, 기준 spec으로 옮길 때도 모순이 넘어가므로 문제다.
- 선택지:
  - A. C3에 예외 단서: C3 조건에 "C4의 예외 때는 빼고"를 더한다. 로그 판정 값(`Unknown`)은 그대로 둔다.
  - B. 판정 값 `Error` 추가: 예외 때 판정을 새 값 `Error`로 두고 C6·C9와 R9 로그 형식을 바꾼다.
- 결정: A
- 이유: A는 C3 한 줄만 바꾸고 R9 로그 형식을 그대로 둔다. B는 로그로 예외와 미등록을 가를 수 있지만, 예외 때는 Error 로그가 따로 남아 얻는 것이 작고 로그 형식·테스트·기준 spec 고칠 곳이 늘어 고르지 않았다.
- 반영: spec.md C3

### D005 C3·C4의 MQTT 3.1.1 확인은 tasks.md에만 더한다
- 단계: tasks
- 질문: tasks 검토 1회차 지적 1. 검토 의견: spec C3·C4는 MQTT 3.1·3.1.1 클라이언트가 반환 코드 4·3을 받는다고 정하는데, 3.1.1(V311) 클라이언트 확인은 C2(틀린 비밀번호)에만 있고 C3(`Unknown`)·C4(예외)에는 없다. MQTTnet의 반환 코드 변환은 패키지 소스로 확인하지 못한 전제라, `ServerUnavailable`이 3.1.1에서 3으로 나가는지 확인하지 않은 채 완료로 처리되므로 문제다.
- 선택지:
  - A. tasks만 고침: T002 미등록 mac 경우에 V311 클라이언트 → `BadUserNameOrPassword`, T003에 V311 클라이언트 → `ServerUnavailable`을 더한다. 확인받은 plan.md는 바꾸지 않는다.
  - B. plan·tasks 함께: A에 더해 plan.md 검증 전략 C3·C4 줄에 V311 확인을 적고, 확인받은 문서 변경이므로 plan 검토·확인과 tasks 검토·확인을 다시 한다.
- 결정: A
- 이유: A는 spec이 이미 요구하는 확인을 채울 뿐 설계를 바꾸지 않아 tasks 두 줄로 끝난다. B는 문서 사이가 가장 잘 맞지만, 테스트 경우 둘을 더하려고 plan 검토·확인을 다시 하는 절차 비용이 커 고르지 않았다.
- 반영: tasks.md T002, T003

### D006 catch 주석 수정은 tasks.md T004에만 더한다
- 단계: tasks
- 질문: tasks 검토 1회차 지적 2. 검토 의견: `MqttBrokerHostedService.cs`의 catch 주석 "관찰 로그 실패로 접속을 막지 않는다."는 C4(예외 때 거부) 뒤 정반대 뜻이 되는데, plan.md와 T004는 클래스·메서드 주석 두 곳만 고친다고 적었다. 작업 목록대로만 하면 반대 뜻 주석이 남으므로 문제다.
- 선택지:
  - A. T004에 추가: T004 문구에 catch 주석 수정을 더한다. plan.md는 바꾸지 않는다.
  - B. plan·tasks 함께: A에 더해 plan.md 「바꿀 파일·구조」에도 적고, plan 검토·확인과 tasks 검토·확인을 다시 한다.
- 결정: A
- 이유: A는 tasks 한 줄로 끝나고, 주석 수정은 설계 변경이 아니라 plan을 다시 확인받을 필요가 없다. B는 주석 한 줄에 비해 절차 비용이 커 고르지 않았다.
- 반영: tasks.md T004
