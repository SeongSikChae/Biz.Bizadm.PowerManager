# 장치 MQTT 제어 기능 근거 문서 작성 계획

## 요약

B540 1.01.34와 M130-W 2.01.58 펌웨어 이미지를 Ghidra로 정적 분석해, 서버 → 장치 오퍼레이션 분기, 요소의 오브젝트·리소스 분기, 제어 뒤 장치 응답을 모델마다 정리한 새 근거 문서 `docs/reference/mqtt-device-control.md`를 쓴다. B540 분석 색인·이력 문서와 기존 MQTT 근거 문서에는 spec C8이 정한 줄만 고치고, 기준 spec `mqtt-broker`에는 이력 한 줄만 더한다.

## 바꿀 파일·구조

- `docs/reference/mqtt-device-control.md`(새 파일): 제어 기능 근거 문서. 절 구성은 아래 「인터페이스·데이터」.
- `docs/reference/b540-rea-analysis.md`: 머리말 「마지막 갱신」 줄, 「현재 진행 및 재개 지점」의 「현재 한계」 줄, 「상세 문서 색인」에 링크 한 줄, 「핵심 요약」의 「아직 결론 내릴 수 없는 항목」 가운데 제어·명령 및 응답 JSON·타이머·스케줄 관련 문구(C8, D001, D002).
- `docs/reference/b540-rea-history.md`: 「10. 기록 이력」에 한 줄(C8).
- `docs/reference/b540-mqtt-topic.md`: 머리말 관련 문서 줄에 새 문서 링크(C8).
- `docs/features/mqtt-broker.md`: 이력 표에 이번 작업 한 줄(C10).

분석 산출물(디컴파일 로그, Ghidra 프로젝트, 분할한 세그먼트)은 분석 서버의 작업 폴더에만 두고 저장소에 넣지 않는다.

## 결정

- 새 문서 하나에 두 모델을 함께 적는다: 서버 제어 기능 개발자가 모델별 차이를 한곳에서 보아야 한다. / 검토한 대안: 모델마다 문서를 따로 둠(B540 문서·M130-W 문서) — C5 요약 표와 C6 차이를 다시 한 문서에 모아야 해 같은 내용이 세 곳에 흩어지므로 고르지 않았다.
- 파일 이름 `mqtt-device-control.md`: 기존 `b540-*.md`는 B540 덤프 분석 문서들이고, 이 문서는 두 모델의 MQTT 제어를 다루므로 모델 접두를 붙이지 않는다. / 검토한 대안: `b540-mqtt-control.md` — M130-W 내용이 B540 문서처럼 보여 고르지 않았다.
- 분석 이미지: 모델마다 `_1`·`_2`가 IROM 주소 값(`+0x80000`)만 다른 같은 코드임을 확인했으므로(분할 비교: B540 882워드, M130-W 917워드가 모두 `+0x80000` 차이, IRAM·DRAM 차이도 모두 같은 재배치), B540은 기존 문서 주소와 같은 `_2`(IROM `0x40281010`, 덤프 슬롯 B와 바이트 일치), M130-W는 `_1`(IROM `0x40201010`)만 디컴파일한다. 문서 주소는 그 이미지의 링크 주소로 적고 다른 쪽 이미지로 바꾸는 규칙(IROM 주소 ± `0x80000`)을 1절에 적는다. / 검토한 대안: 네 이미지를 모두 디컴파일 — 같은 코드라 결과가 같고 비용만 두 배라 고르지 않았다.
- 도구: 분석 서버의 Ghidra 12.2 headless(언어 `Xtensa:LE:32:default`). 적재는 세그먼트마다 링크 주소 자리에 둔 평면 이미지 하나로 한다(시작 `0x3ffe8000`. DRAM `0x3ffe8000`~, IRAM `0x40100000`~, IROM 링크 주소~가 그 안의 자기 자리에 놓이고 빈 곳은 0)와 xtensa-lx106 objdump. REA `open_binary`는 Xtensa를 받지 않는다(기존 문서와 같은 이유).
- 분석 경로: 앞에서부터 따라간다. (1) 오퍼레이션 비교 함수와 처리 표 → 처리 함수 (2) 요소 처리 점프 표(`w`·`r` 공통 함수의 요소 수별 점프)를 바이트에서 직접 읽어 복원 → 요소마다 오브젝트 분기 함수 (3) 오브젝트별 리소스 분기 → 저장 위치·하드웨어 동작 함수 (4) 처리 뒤 발행 함수(응답 토픽 접미, `msg.o`, 요소 형식). 함수 이름 문자열(`Set_SmartPlugResourceData`, `CheckRemoteControl`, `MqttTypeReboot` 등)과 로그 형식 문자열을 참조하는 함수를 문자열 → 리터럴 풀 → `l32r` 순으로 찾아 교차 확인한다.
- 펌웨어 버전 표기: 요약 표와 실장비 확인 후보에 적용 펌웨어 버전을 적고, B540 실장비(`1.01.36` 관찰)와 분석 이미지(`1.01.34`)의 버전 차이를 머리말과 7절에 주의로 적는다. / 검토한 대안: spec C5·C7에 버전 요구를 더함 — 확정한 spec을 바꾸는 의도 변경이라 spec 검토·확인부터 다시 해야 해 고르지 않았다. (D003)
- 하드웨어 동작 판정: 리소스 처리가 GPIO 레지스터(`0x60000300` 근처)나 SDK GPIO 함수, UART 송신 함수로 이어지면 관찰로 적고, 그것이 릴레이라는 해석은 추정으로 적는다.

## 인터페이스·데이터

새 문서 절 구성(머리말 뒤에 1~7절):

- 머리말: 작성일, 근거(이미지 네 개의 이름·크기·SHA-256 앞 16자리·모델·버전, 도구·버전, 분석 날짜), 이미지마다 IROM·IRAM·DRAM 링크 주소와 길이 요약 표 (D004), 표기(관찰·추정·미확인), 관련 문서. 실장비 펌웨어 버전 주의: B540 실장비는 서버 로그로 `1.01.36`이 관찰됐고(`b540-mqtt-topic.md` 4절) 분석 이미지는 `1.01.34`라, 이 문서의 B540 내용을 다른 버전 장치에 쓸 때는 차이가 있을 수 있다. M130-W는 분석 이미지와 관찰 실장비가 모두 `2.01.58`이다 (D003)
1. 분석 대상의 관계: `_1`·`_2` 관계(재배치 차이 워드 수, 다른 쪽 주소로 바꾸는 규칙, 분석한 이미지(B540 `_2`, M130-W `_1`)와 문서의 주소가 그 이미지의 링크 주소라는 것), B540 이미지와 덤프 두 슬롯의 바이트 비교 결과, 기존 문서 주소를 그대로 쓸 수 있는지 (C1)
2. 제어 항목 요약 표: 행 = 제어 항목(릴레이 켜기/끄기, 재부팅, 시간 동기, 보고 조건, 스케줄·알람, FOTA, 자동 복구, 분석 중 찾은 항목), 열 = B540 메시지·근거 표기, M130-W 메시지·근거 표기, 근거 절 링크 (C5). 표 머리에 모델별 적용 펌웨어 버전(B540 `1.01.34`, M130-W `2.01.58`)을 적는다 (D003)
3. B540 1.01.34: 오퍼레이션 분기 표(값·번호·비교 순서·처리 함수·하는 일) (C2), 오브젝트 분기와 리소스 표(오브젝트·인스턴스·리소스·받는 오퍼레이션·값 해석·저장 위치/동작·읽기 응답·의미) (C3, 오브젝트 99는 `b540-mqtt-topic.md` 「오브젝트 99 리소스 처리」 참조 허용), 제어 뒤 장치 응답 (C4)
4. M130-W 2.01.58: 3절과 같은 구성 (C2~C4, 오브젝트 99 포함)
5. 모델 간 차이 (C6)
6. 기존 근거 문서와의 차이: `b540-mqtt-topic.md`의 절·표 위치마다 바뀜·확정·보완 (C11)
7. 미확인과 실장비 확인 후보: 항목, 보낼 메시지 후보, 상태 변경 여부 표시, 적용 펌웨어 버전 칸 (C7). 절 첫머리에 B540 실장비 `1.01.36` 관찰과 버전 차이 주의를 적는다 (D003)

메시지 표기는 기존 문서와 같게 `{"sid":"0","msg":{"o":"<op>","e":[{"n":"/<o>/<i>/<r>","sv":"<값>"}]}}`로 적는다. 서버 → 장치 토픽은 `b540-mqtt-topic.md` 2절(`<접두>.v1/iot-server/<장치 키>`)을 참조한다.

## 오류·위험

- Ghidra가 점프 표를 복원하지 못함(M130-W `0x4024dcec`에서 이미 확인): 표 주소의 워드를 직접 읽어 대상 주소에 함수를 만들어 디컴파일한다. 그래도 밝히지 못하면 미확인과 까닭을 적는다(C2·C3이 허용).
- 문자열 비교가 접두 비교라 순서가 판정을 바꿈(기존 문서 3절): 비교 순서를 표에 적는다.
- 하드웨어 동작을 잘못 해석할 위험: 디컴파일에 나타난 호출·레지스터만 관찰로 적고 기능 이름은 추정으로 둔다.
- 민감 정보: 설정 섹터의 `mqtt_key`, 장치 MAC, 분석 서버 주소·계정·절대 경로를 문서에 넣지 않는다(C9). 이미지 SHA-256은 앞 16자리만 적는다.
- 분석 서버 연결 끊김(이번 작업 중 한 번 있었음): 산출물은 서버 작업 폴더에 남으므로 다시 이어서 한다. 재부팅되면 볼륨을 다시 마운트한다.

## 검증 전략

- C1: 새 문서 머리말에 이미지 네 개의 항목, 도구·버전·날짜, 이미지마다 배치 요약 표가 있는지, 1절에 `_1`·`_2` 관계, 분석한 이미지와 문서 주소의 기준, 덤프 비교 결과와 주소 사용 가능 여부가 있는지 본다. SHA-256 앞자리는 로컬 `Get-FileHash`로 대조한다.
- C2: 모델마다 오퍼레이션 표에 펌웨어 비교 함수가 비교하는 값 전부가 있는지, 디컴파일 로그의 비교 함수 출력과 하나씩 대조한다.
- C3: 모델마다 오브젝트 분기 함수가 비교하는 오브젝트 번호 전부와, 리소스 분기 함수가 비교하는 리소스 번호 전부가 표에 있는지 디컴파일 로그와 대조한다.
- C4: 모델마다 응답 절이 있고, 발행 함수 근거 주소 또는 미확인 표기가 있는지 본다.
- C5: 요약 표에 spec이 정한 일곱 행이 모두 있고, 행마다 두 모델 칸에 메시지 또는 미확인과 근거 표기·링크가 있는지 본다.
- C6·C7·C11: 해당 절이 있고, C7 항목마다 상태 변경 표시가 있는지, C11 항목마다 기존 문서 위치가 있는지 본다.
- C8: 기준점부터 `git -C <저장소> diff 00646f4 -- docs/reference/b540-rea-analysis.md docs/reference/b540-rea-history.md docs/reference/b540-mqtt-topic.md`를 읽어, 바뀐 줄이 C8이 허용한 줄뿐인지 본다.
- C9: 새 문서와 바뀐 문서에서 12자리 이상 16진수 문자열을 모두 찾아, 일치마다 이미지 SHA-256 표기 칸이나 기존 해시 줄의 해시인지 하나씩 확인하고 그 밖의 일치(MAC 후보)가 없음을 본다. `mqtt_key` 값, 분석 서버 주소, 드라이브 문자·`/home/`·`/mnt/` 절대 경로도 검색해 없음을 확인한다.
- C10: `git -C <저장소> diff 00646f4 -- docs/features/mqtt-broker.md`가 이력 표 한 줄 추가뿐인지 본다.

## 원칙 점검

- 적용 규칙:
  - Bizadm MCP `workflow/spec-driven.md`: 변경 문서·기준점·검토·기준 spec 반영(T 마지막 단계)
  - `git/github-issue.md`: 이슈 #27, 커밋에 번호 참조, 종결 조건
  - `workflow/repository-content.md`: 저장소 기준 상대 경로, 비밀·개인 정보 제외(C9)
