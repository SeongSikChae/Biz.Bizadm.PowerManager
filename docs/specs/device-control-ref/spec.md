# 장치 MQTT 제어 기능 근거 문서 작성

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #27

## 무엇을, 왜

서버에서 장치를 MQTT로 제어하는 기능(릴레이 켜기/끄기, 재부팅, 스케줄, 보고 조건 등)을 나중에 개발하려면, 장치가 받아들이는 오퍼레이션과 오브젝트·리소스 경로(`/<object>/<instance>/<resource>`), 장치가 그에 어떻게 응답하는지가 먼저 밝혀져 있어야 한다.

지금 근거는 부족하다.

- `docs/reference/b540-mqtt-topic.md`는 B540 덤프 슬롯 B의 서버 → 장치 오퍼레이션 분기(`rg`·`drg`·`r`·`w`·`e`·`d`·`chg`·`reb`)와 오브젝트 99 리소스만 디컴파일로 정리했다.
- 같은 문서에서 오브젝트 3·4·5·100의 처리, `chg`·`reb`·`e`·`d`의 동작, 릴레이·FOTA·스케줄·자동 복구의 리소스 ID는 함수 이름만 알려져 있다(`Set_SmartPlugResourceData`, `CheckRemoteControl` 등).
- M130-W 펌웨어 분석은 저장소 근거 문서에 없다(`b540-mqtt-topic.md` 5절은 실통신 관찰뿐).
- 서버의 `MqttDeviceCommandPublisher`(`WriteAsync`·`ChangeAsync`·`RebootAsync`)는 껍데기만 있다.

사용자가 준 펌웨어 이미지 네 개를 정적 분석해 제어할 수 있는 항목을 새 근거 문서로 정리한다. 이미지는 `docs/.tmp`(`.gitignore` 대상)에 있으며 저장소에 넣지 않는다.

- `docs/.tmp/b540-1.01.34_1.bin`, `docs/.tmp/b540-1.01.34_2.bin`(B540, 펌웨어 1.01.34)
- `docs/.tmp/m130-2.01.58_1.bin`, `docs/.tmp/m130-2.01.58_2.bin`(M130-W, 펌웨어 2.01.58)

새 문서는 `docs/reference`에 두고, B540 분석 색인(`docs/reference/b540-rea-analysis.md`)의 원칙("제어·계량 분석을 시작하면 상세 문서를 따로 두고 색인에 링크를 더한다", "결과를 받으면 색인의 현재 상태, 주제 문서, 이력 문서의 짧은 갱신 항목을 고친다")대로 색인에 링크를 더하고, 색인의 현재 상태 가운데 제어 관련 문구와 이력 문서(`docs/reference/b540-rea-history.md`)를 갱신한다. 기존 근거 문서(`b540-mqtt-topic.md`)는 관련 문서 링크만 더하고 본문은 고치지 않는다. 새 분석이 기존 문서와 어긋나면 새 문서에 그 차이를 적는다.

서버 코드 변경, 실장비에 제어 메시지를 보내는 확인, 펌웨어 동적 실행(에뮬레이터 포함)은 범위 밖이다.

## 완료 조건

- C1. `docs/reference`에 새 근거 문서가 있다. 머리말에 분석 대상 이미지 네 개(파일 이름, 크기, SHA-256 앞 8자리 이상, 모델·펌웨어 버전), 도구와 버전, 분석 날짜, 이미지마다 메모리 배치(IROM·IRAM·DRAM 링크 주소)가 있다. `_1`과 `_2`의 관계(바이트 차이, 링크 주소 차이, 어느 쪽을 분석했는지)를 적는다. B540 이미지 두 개를 기존 근거 문서가 쓴 덤프(`docs/.tmp/b540-dump1.bin`)의 두 슬롯과 바이트 비교한 결과와, 기존 문서(`b540-mqtt-topic.md`)의 주소를 그대로 쓸 수 있는지를 적는다. 표기는 기존 근거 문서와 같은 **관찰**(디컴파일·바이트에 직접 나타남)·**추정**(관찰의 의미 해석)·**미확인** 세 가지를 쓴다.
- C2. 모델(B540·M130-W)마다 서버 → 장치 오퍼레이션 분기가 표로 있다. 펌웨어가 비교하는 `msg.o` 값 전부와 번호, 비교 순서, 각 번호의 처리 함수 주소, 처리 함수가 하는 일(요소 처리로 넘기는지, 재부팅·등록 등 요소와 무관한 동작인지)을 적는다. 처리를 밝히지 못한 오퍼레이션은 미확인과 그 까닭을 적는다.
- C3. 모델마다 요소 처리의 오브젝트 분기가 있다. 경로 `n`의 오브젝트 번호별 처리 함수 주소와, 오브젝트마다 처리하는 인스턴스·리소스 번호 전부를 적는다. 리소스마다 받는 오퍼레이션(검사하는 오퍼레이션 번호), 값 해석(문자열·정수·불리언 등), 저장 위치 또는 동작(릴레이·하드웨어 출력·재부팅 호출 등), 읽기 때 돌려주는 값을 관찰로 적고, 의미는 추정으로 적는다. 오브젝트 99는 B540 결과를 `b540-mqtt-topic.md`로 참조해도 되며, M130-W는 따로 적는다.
- C4. 모델마다 장치가 제어 메시지를 받은 뒤 서버로 보내는 것(응답·보고 발행 여부, 토픽 접미, `msg.o` 값, 요소 형식)을 적는다. 정적 분석으로 밝히지 못한 부분은 미확인으로 적는다.
- C5. 제어 항목 요약 표가 있다. 적어도 릴레이 켜기/끄기, 재부팅, 시간 동기, 보고 조건, 스케줄·알람, FOTA, 자동 복구 행이 있고, 분석 중 찾은 다른 제어 항목도 더한다. 행마다 모델별로 서버가 보낼 메시지(`o` 값, 경로, 값 형식)와 근거 표기(관찰·추정·미확인), 근거 절 링크를 적는다. 메시지를 밝히지 못한 항목은 미확인으로 남긴다.
- C6. B540과 M130-W의 제어 관련 차이(오퍼레이션 목록, 오브젝트·리소스, 응답)를 한곳에 모아 적는다.
- C7. 실장비 확인이 필요한 항목(정적 분석으로 확정하지 못한 것)과 확인할 때 보낼 메시지 후보를 미확인 절에 목록으로 적는다. 상태를 바꾸는 메시지(릴레이·재부팅 등)는 그렇다고 표시한다.
- C8. 다른 근거 문서의 바뀐 곳은 다음뿐이다.
  - `docs/reference/b540-rea-analysis.md`: 상세 문서 색인에 새 문서 링크 한 줄이 더해진다. 「현재 진행 및 재개 지점」의 「현재 한계」 줄과 「핵심 요약」의 「아직 결론 내릴 수 없는 항목」 목록에서 제어·명령 및 응답 JSON·타이머·스케줄 관련 문구만, 새 문서에서 밝힌 것과 남은 미확인에 맞게 새 문서 링크와 함께 바뀐다. 머리말 「마지막 갱신」 줄은 날짜가 2026-11-21로 바뀌고 제어 기능 근거 문서를 더했다는 짧은 문구가 덧붙으며, B540-20 대기 내용은 그대로 남는다. 그 밖의 줄은 바뀌지 않는다.
  - `docs/reference/b540-rea-history.md`: 「10. 기록 이력」에 이번 작업 한 줄이 더해진다. 그 밖의 줄은 바뀌지 않는다.
  - `docs/reference/b540-mqtt-topic.md`: 관련 문서 줄에 새 문서 링크가 더해진다. 그 밖의 줄은 바뀌지 않는다.
- C9. 새 문서와 바뀐 문서에 장치 MAC, `mqtt_key` 등 키 값, 개인정보, 이 PC나 분석 서버에만 맞는 절대 경로가 없다(저장소 파일은 저장소 기준 상대 경로).
- C10. 기준 spec `docs/features/mqtt-broker.md`의 이번 작업 diff는 이력 표에 이번 작업 한 줄(바꾼 요구 없음, 근거 문서 작성)을 더하는 것뿐이다.
- C11. 새 분석이 `docs/reference/b540-mqtt-topic.md`의 기술을 바꾸거나 확정·보완하는 곳을 새 문서의 한 절에 기존 문서 위치(절·표)와 함께 적는다. 없으면 없다고 적는다.
