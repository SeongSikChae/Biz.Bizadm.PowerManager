# 장치 MQTT 제어 기능 근거 문서 결정

### D001 B540 분석 색인은 링크만이 아니라 현재 상태의 제어 관련 문구와 이력 문서도 갱신한다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 처음 spec C8은 색인(`docs/reference/b540-rea-analysis.md`)에 새 문서 링크 한 줄만 더하고 다른 줄은 바꾸지 않는다고 했다. 그런데 색인의 「문서 유지 및 다음 인계 원칙」은 결과를 받을 때 색인의 현재 상태, 주제 문서, 이력 문서(`b540-rea-history.md`)의 짧은 갱신 항목을 고치라고 한다. 또 색인 「현재 한계」 줄과 「아직 결론 내릴 수 없는 항목」은 제품 제어 기능, 명령 및 응답 JSON, 타이머·스케줄 로직을 미확인으로 적고 있다. 링크만 더하면 색인이 새 문서가 밝힌 내용을 여전히 미확인이라고 말해 모순이 남는다.
- 선택지:
  - A. 색인 상태·이력도 갱신: 색인에 링크 한 줄을 더하고, 「현재 한계」·「아직 결론 내릴 수 없는 항목」에서 제어·명령 JSON·스케줄 관련 문구만 새 문서 결과(밝힌 것, 남은 미확인)로 바꾸며, `b540-rea-history.md` 갱신 이력에 한 줄을 더한다. 그 밖의 줄은 바꾸지 않는다.
  - B. 링크만, 예외 명시: C8은 링크 한 줄만 두고, 색인의 현재 상태·이력 갱신은 이번 범위가 아니라고 spec에 적는다.
- 결정: A
- 이유: A는 색인이 스스로 정한 갱신 원칙과 맞고, 색인과 새 문서 사이의 모순을 남기지 않는다. 비용은 바뀌는 파일 하나(이력 문서)와 색인 줄 2~3개뿐이다. B는 비용이 거의 없지만, 색인이 제어 기능을 계속 미확인이라고 말하는 모순이 남아 고르지 않았다.
- 반영: spec.md 「무엇을, 왜」 색인 문단, C8

### D002 색인 머리말 「마지막 갱신」 줄도 갱신한다
- 단계: spec
- 질문: spec 검토 2회차 지적 2. D001대로 넓힌 C8은 색인(`docs/reference/b540-rea-analysis.md`)에서 링크 한 줄과 제어 관련 문구만 바꾸고 "그 밖의 줄은 바뀌지 않는다"고 했다. 그래서 머리말 「마지막 갱신」 줄(지금 "2026-10-23 (KST), … B540-20 … 실행 여부·결과 대기")도 바꿀 수 없다. 작업이 끝나도 색인은 마지막 갱신을 2026-10-23으로 보여, D001이 없애려던 색인 안 불일치(현재 상태와 실제 갱신의 차이)가 머리말에 남는다. 앞서 MQTT 문서 링크를 더할 때도 이 줄은 바꾸지 않았다.
- 선택지:
  - A. 마지막 갱신 줄도 갱신: C8에 "머리말 「마지막 갱신」 줄은 날짜를 2026-11-21로 바꾸고 제어 기능 근거 문서를 더했다는 짧은 문구를 덧붙이며, B540-20 대기 내용은 그대로 둔다"를 더한다.
  - B. 바꾸지 않는다고 명시: C8에 "머리말 「마지막 갱신」 줄은 이전 링크 추가 관례대로 바꾸지 않는다"를 더한다.
  - 고치지 않음: C8을 그대로 둔다.
- 결정: A
- 이유: A는 비용이 B와 같은 한 문장이고, 색인 현재 상태를 갱신하기로 한 D001의 취지와 맞으며, B540-20 대기 내용을 지우지 않아 기존 기록도 보존한다. B는 의도를 드러내지만 날짜 불일치가 남아 고르지 않았다. 고치지 않음은 불일치가 남고 의도도 드러나지 않아 고르지 않았다.
- 반영: spec.md C8

### D003 펌웨어 버전 차이는 plan 설계(요약 표·실장비 확인 후보의 적용 버전 칸과 주의 문구)로 다룬다
- 단계: plan
- 질문: plan 검토 1회차 지적 2. B540 분석 이미지는 `1.01.34`인데, 서버 로그로 관찰한 B540 실장비는 펌웨어 `1.01.36`이다(`docs/reference/b540-mqtt-topic.md` 4절). 그런데 spec C7과 plan 「인터페이스·데이터」 8절은 실장비 확인 후보 메시지가 어느 펌웨어 버전 기준인지 적게 하지 않는다. 나중 작업이 1.01.34 기준 오퍼레이션·경로를 1.01.36 장치에 그대로 보내면, 결과가 어긋나도 버전 차이 때문인지 분석 오류 때문인지 가릴 수 없다. 상태를 바꾸는 메시지(릴레이·재부팅)라면 의도와 다른 동작을 일으킬 수도 있다. M130-W는 분석 이미지와 관찰 실장비가 모두 `2.01.58`이다.
- 선택지:
  - A. plan만 고침: plan 「인터페이스·데이터」 3절(요약 표)과 8절(실장비 확인 후보)에 적용 펌웨어 버전을 적게 하고, 머리말과 8절에 B540 실장비 `1.01.36` 관찰과 "1.01.34 분석을 다른 버전에 쓸 때는 차이가 있을 수 있다"는 주의를 적게 한다. 확정한 spec은 그대로 둔다.
  - B. spec C5·C7까지 고침: 완료 조건에 "항목마다 적용 펌웨어 버전과 실장비 관찰 버전 차이를 적는다"를 더하고 plan도 맞춘다. 확정한 spec을 바꾸는 의도 변경이라 spec 검토·사용자 확인부터 다시 한다.
  - 고치지 않음: 버전 차이를 다루지 않는다.
- 결정: A
- 이유: 문서에 버전과 주의를 적게 하려는 목적은 설계(문서 절 구성)로 충분히 이루어지고, 확정한 spec을 다시 검토·확인받는 비용을 피한다. B는 완료 조건으로 강제할 수 있지만 spec 단계부터 다시 해야 해 비용이 커 고르지 않았다. 고치지 않음은 1.01.34 기준 메시지를 1.01.36 장치에 그대로 보낼 위험이 남아 고르지 않았다.
- 반영: plan.md 결정 「펌웨어 버전 표기」, 「인터페이스·데이터」 1·3·8절

### D004 이미지별 메모리 배치 요약을 새 문서 머리말에 둔다
- 단계: plan
- 질문: plan 검토 2회차 지적 1. spec C1은 "머리말에 … 이미지마다 메모리 배치(IROM·IRAM·DRAM 링크 주소)가 있다"고 하는데, plan 「인터페이스·데이터」 1절(머리말)에는 배치가 없고 2절 「분석 대상과 메모리 배치」에만 있었다. 검증 전략 C1도 "머리말·2절"을 읽어 2절에 있어도 통과로 봐, spec과 판정 기준이 어긋났다. C1을 글자 그대로 대조하면 미충족으로 판정될 수 있다.
- 선택지:
  - A. 머리말에 배치 요약: plan 1절(머리말)에 이미지마다 IROM·IRAM·DRAM 링크 주소와 길이 요약 표를 넣고, 2절은 `_1`·`_2` 관계·덤프 비교·주소 재사용 판단만 맡긴다. 검증 전략 C1도 머리말·2절로 나눠 고친다.
  - B. 1·2절을 머리말로 봄: plan에 "1·2절을 C1의 머리말로 본다"는 문장만 더한다.
  - 고치지 않음: plan을 그대로 둔다.
- 결정: A
- 이유: A는 비용이 B와 비슷하게 plan 두 곳이고, spec C1 문구와 그대로 맞아 판정에 해석이 필요 없다. B는 spec 문구와 다른 해석에 기대므로 고르지 않았다. 고치지 않음은 C1 미충족 판정 혼선이 남아 고르지 않았다.
- 반영: plan.md 「인터페이스·데이터」 1·2절, 「검증 전략」 C1

### D005 B540 스케줄·자동 복구·FOTA 동작은 B540 함수를 디컴파일해 대조한 뒤 관찰로 적는다
- 단계: 구현
- 질문: 구현 후 검토 1회차 지적 3. 새 문서 3.1 자동 복구 카운터, 3.3 스케줄 전체, 2절 요약 표의 FOTA·자동 복구·스케줄 근거가 M130-W 디컴파일 결과인데 B540 관찰로 표기됐고, 요약 표 근거 칸이 두 모델 공통이었다. B540은 함수 주소와 문자열 참조만 확인한 상태라 spec C1(표기 규칙)과 C5(모델별 근거 표기)에 어긋났다.
- 선택지:
  - A. B540 디컴파일로 대조: B540 `0x402c9870`(스케줄 해석)·`0x402c9660`(스케줄 저장)·`0x4029b20c`(자동 복구)·`0x402c8f80`(URL 해석)을 디컴파일해 M130-W와 대조한다. 같으면 B540 관찰로 두고 근거 함수 주소를 B540 것으로 바꾸고, 다르면 차이를 적는다. 요약 표 근거 칸을 B540·M130-W로 나눈다.
  - B. B540을 추정으로 바꿈: 디컴파일하지 않고 B540 쪽을 "추정(M130-W 관찰, B540은 같은 이름의 함수 주소만)"으로 바꾸고 근거 칸을 모델별로 나눈다.
  - 고치지 않음: 그대로 둔다.
- 결정: A
- 이유: A는 분석 서버 실행 한 번과 대조만 더하면 되고, B540 제어 구현의 근거가 관찰로 남는다. B는 비용이 조금 작지만 B540 근거가 추정으로 남아 고르지 않았다. 고치지 않음은 C1·C5에 어긋나 고르지 않았다. 대조 결과 네 함수 모두 M130-W와 같은 구조였다.
- 반영: mqtt-device-control.md 2절 요약 표(근거 칸 분리), 3.1 자동 복구 항목, 3.2 오브젝트 5, 3.3

### D006 plan·tasks의 절 번호를 새 문서의 실제 번호(머리말 뒤 1~7절)에 맞춘다
- 단계: 구현
- 질문: 구현 후 검토 1회차 지적 10. 새 문서는 머리말 뒤에 1~7절로 번호를 매겼는데, plan 「결정 — 분석 이미지」의 "2절에 적는다"와 「인터페이스·데이터」 목록(1~8), tasks T006~T012의 절 번호는 예전 번호(머리말=1절)라, 그 번호로 검증하면 다른 절을 보게 된다. plan은 "번호는 쓰면서 맞춘다"고 했고 내용은 같다.
- 선택지:
  - A. plan·tasks 번호를 문서에 맞춤: plan의 규칙 위치를 1절로, 「인터페이스·데이터」 목록을 머리말·1~7절로, 검증 전략 C1을 1절로, tasks T006~T012와 체크포인트의 절 번호를 문서 번호로 바꾼다. 내용은 바꾸지 않는다.
  - B. 문서 번호를 plan에 맞춤: 새 문서 머리말을 1절로 두고 나머지를 2~8절로 다시 매기며 앵커 링크를 모두 고친다.
  - 고치지 않음: 그대로 둔다.
- 결정: A
- 이유: A는 두 문서의 번호 교체뿐이고 내용이 바뀌지 않아 규칙상 고치기만 하면 되는 수정이다. B는 제목 7개와 앵커 링크 수십 곳을 고쳐야 해 링크가 깨질 위험이 있어 고르지 않았다. 고치지 않음은 검증 때 다른 절을 보게 되어 고르지 않았다.
- 반영: plan.md 「결정」 분석 이미지·펌웨어 버전 표기, 「인터페이스·데이터」 목록, 「검증 전략」 C1, tasks.md T006~T012·단계 2 체크포인트

### D007 B540 현재 요일 저장 위치는 B540 `SetLocalAlramTime`을 디컴파일해 확인한 값으로 적는다

- 선택지:

- 반영: mqtt-device-control.md 3.3 `SetLocalAlramTime`

### D008 B540 `Send_RelayStatus` 요소는 B540 디컴파일 결과를 근거로 관찰로 적는다
- 단계: 구현
- 질문: 구현 후 검토 3회차 지적 2. 새 문서 3.1·3.3·3.4·7절이 B540 `Send_RelayStatus`(`0x402caa88`)가 `/100/0/31`·`/100/0/32`를 보낸다고 관찰로 적었지만 B540 함수는 디컴파일하지 않았고(요소는 M130-W `0x4024d280`에서만 확인), 6절 「장치 → 서버 보고」 행은 "M130-W 관찰"이라 문서 안 근거 표기가 어긋났다. 7절 B540 시계 확인은 이 요소와 원인 값을 판정 기준으로 쓴다.
- 선택지:
  - A. 디컴파일 근거로 표기 맞춤: B540 `0x402caa88`을 디컴파일해(검토 판단 전에 확인함: 연결 중 `notify`로 `/100/0/31`·`/100/0/32`) B540 관찰을 유지하고, 6절 행을 두 모델 함수 관찰로, 7절 기대값을 `/100/0/32` `"16"`으로 고친다.
  - B. B540을 추정으로: B540 부분을 "추정(M130-W와 같은 구조)"으로 낮춘다.
  - 고치지 않음: 그대로 둔다.
- 결정: A
- 이유: A는 확인이 이미 끝나 문구 몇 곳만 고치면 되고 근거가 관찰로 남는다. B는 이미 확인한 사실을 추정으로 낮춰 고르지 않았다. 고치지 않음은 문서 안 근거 표기 불일치가 남아 고르지 않았다.
- 반영: mqtt-device-control.md 3.1 자동 복구 항목, 3.3 「다시 켠 뒤」, 6절 「장치 → 서버 보고」 행, 7절 B540 시계 행
