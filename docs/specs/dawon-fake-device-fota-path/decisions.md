# 다원 가짜 장비 FOTA 요청 경로 맞춤 결정

### D001 FOTA 받기를 장치와 같은 한 요청으로 바꾼다
- 단계: spec
- 질문: 가짜 장비의 FOTA 받기 요청 형식을 정해야 했다. 지금은 받은 URL로 `GET {URL}/version`과 `GET {URL}` 두 요청을 보내고, 2026-11-20 실제 다원 실행에서 둘 다 404였다. 슬롯 B 펌웨어 분석(`docs/specs/b540-fota-path/`)과 이번 사전 확인으로 실제 장치는 `/version` 요청 없이 `GET <경로><반대편 슬롯 접미사>` 하나만 보내고, 그 경로(`_1`·`_2`)는 다원 서버에서 200으로 이미지를 준다는 것을 확인했다.
- 선택지:
  - A. 장치와 같게: 자동 받기(R14)와 콘솔 `fota` 명령(R15 첫째)이 `GET {URL}{접미사}` 하나만 보낸다. `/version` 요청과 기록의 버전 응답 본문 항목(R9)을 없앤다.
  - B. 기존 유지 + 추가: 기존 두 요청(`/version`, 접미사 없는 URL)을 그대로 두고 장치 형식 요청을 세 번째로 더한다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: A는 펌웨어 분석·실측과 같은 동작이라 실제 장치가 받는 것을 그대로 관찰하고, 늘 404인 요청이 사라진다. B는 늘 404인 요청 두 개가 남아 기록이 지저분하고 실제 장치 동작과 달라 고르지 않았다.
- 반영: spec.md C1·C3·C5

### D002 접미사는 흉내 낼 실행 슬롯 설정(기본 2)의 반대편으로 정한다
- 단계: spec
- 질문: 요청 경로 끝에 붙일 슬롯 접미사를 어떻게 정할지 정해야 했다. 실제 장치는 실행 중인 슬롯의 반대편 이미지를 받는다(user1 실행 중 → `_2`, user2 실행 중 → `_1`, GET 빌더가 실행 슬롯 판정 결과로 두 상수 가운데 고름). 덤프 장치(1.01.34)는 user2에서 돈다고 추정되어 실제로는 `_1`을 요청했을 것이다.
- 선택지:
  - A. 실행 슬롯 설정, 기본 2: 설정 `Device.RunningSlot`(1|2, 기본 2)을 더하고, 실행 슬롯 2면 `_1`, 1이면 `_2`를 붙인다. 그 밖의 값은 설정 오류(종료 코드 2)다.
  - B. `_1`·`_2` 둘 다 받기: URL마다 두 슬롯 이미지를 모두 받는다.
  - C. 접미사 직접 설정: 설정 `Fota.PathSuffix`(기본 `_1`)를 그대로 붙인다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: A는 펌웨어의 실제 규칙(반대편 슬롯)을 그대로 따르고 기본값이 덤프 장치 상태(user2 실행)와 맞으며, 다른 슬롯 이미지도 설정만 바꾸면 받는다. B는 이미지 수집에는 편하지만 실제 장치는 요청을 하나만 보내 장치 흉내와 달라 고르지 않았다. C는 유연하지만 "반대편 슬롯"이라는 장치 규칙이 설정에 드러나지 않고 잘못된 값을 넣기 쉬워 고르지 않았다.
- 반영: spec.md C2

### D003 장치의 버전 게이트는 흉내 내지 않는다
- 단계: spec
- 질문: 실제 장치는 URL 안의 버전이 자기 펌웨어 버전보다 높을 때만 요청을 보낸다. 가짜 장비가 이 게이트를 흉내 낼지 정해야 했다. 비교할 부분 문자열의 정확한 경계는 펌웨어 분석에서 미확인이다.
- 선택지:
  - A. 흉내 내지 않음: 버전 비교 없이 URL 후보를 찾으면 지금처럼 자동으로 받는다.
  - B. 장치처럼 비교: URL의 마지막 경로 조각과 `Device.FirmwareVersion`을 숫자 단위로 비교해 높을 때만 자동으로 받고, 아니면 건너뛴 것을 기록한다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: 이 도구의 목적은 다원이 주는 것의 관찰·수집이다. 비교 경계가 미확인이라 흉내 내면 틀릴 수 있고, 펌웨어 버전 설정을 낮춰야 FOTA URL이 오므로 실제 상황에서도 결과는 거의 같다. B는 추정한 규칙을 요구로 박게 되고 관찰 기회를 줄여 고르지 않았다.
- 반영: spec.md C1(버전 비교 없음)

### D004 콘솔 `get` 명령은 주어진 URL 그대로 요청한다
- 단계: spec
- 질문: 콘솔의 URL 하나만 GET하는 명령(R15 둘째, `get <URL>`)에도 접미사를 붙일지 정해야 했다.
- 선택지:
  - A. 그대로 둠: `get <URL>`은 주어진 URL을 가공하지 않고 요청한다.
  - B. 장치 형식으로 바꿈: `get <URL>`도 `{URL}{접미사}`로 요청한다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: 임의 경로(다른 슬롯, 다른 버전)를 시험하는 진단용이라 가공하지 않는 편이 쓸모 있고, 장치 형식은 `fota` 명령으로 받는다. B는 `fota` 명령과 겹치고 접미사 없는 경로를 시험할 방법이 사라져 고르지 않았다.
- 반영: spec.md C4

### D005 C7의 SHA-256 대조 기준값을 작업 문서에 남긴다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. C7은 실제 다원 실행에서 받은 이미지를 사전 확인에서 받은 이미지와 SHA-256으로 대조하라고 했지만, 작업 문서에 사전 확인 이미지의 SHA-256이 없고 파일은 scratchpad에만 있어 지워질 수 있다(검토 의견). 기준값이 없으면 실행 시점에 대조할 수 없어 C7의 완료를 판정할 수 없다.
- 선택지:
  - A. 해시를 작업 문서에 적음: 사전 확인의 `_1`·`_2` 이미지 SHA-256 전체를 작업 문서 사전 확인 절에 적고, C7의 대조 기준을 "작업 문서에 적은 사전 확인 SHA-256"으로 고친다.
  - B. 대조 요구 빼기: C7에서 SHA-256 대조를 빼고 요청 URL·상태·바이트 수·SHA-256 기록만 요구한다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: A는 파일이 지워져도 기준값이 남아 같은 이미지를 받았는지 판정할 수 있다. B는 받은 이미지가 올바른지 확인할 기준이 사라져 고르지 않았다.
- 반영: spec.md C7, 작업 문서 사전 확인 절

### D006 접미사 없는 경로의 Host 포트 없는 실측을 근거로 남긴다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. "무엇을, 왜"의 "접미사 없는 경로는 Host 헤더의 포트 유무와 관계없이 404"는 포트를 넣은 경우만 시험해 근거가 부족했다(검토 의견). 이 문장을 C8에서 분석 기록에 옮기면 근거 없는 관찰이 들어간다. 지적 뒤 Host 포트 없이 요청해 404를 확인했다.
- 선택지:
  - A. 실측을 작업 문서에 추가: "접미사 없는 경로, Host 포트 없음 → 404"를 작업 문서 사전 확인 절에 적고 spec 문장은 그대로 둔다.
  - B. spec 문장 줄임: spec에서 "Host 헤더의 포트 유무와 관계없음"을 뺀다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: A는 실측이 있으니 근거만 남기면 된다. B는 확인한 사실을 버리게 되어 고르지 않았다.
- 반영: 작업 문서 사전 확인 절

### D007 C7은 기준값이 없거나 해시가 달라도 기록하면 완료로 본다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. C7의 SHA-256 대조 기준값은 사전 확인한 `B540_W/1.01.34`의 `_1`·`_2` 이미지뿐인데, 실행 때 다원이 다른 버전의 URL을 보낼 수 있고(D003으로 버전 비교도 하지 않음) 해시가 다를 때의 처리도 없어 C7 완료 판정이 실행자에 따라 갈린다(검토 의견).
- 선택지:
  - A. 기록하면 완료: 기준값이 없는 버전이면 대조하지 않고 그 사실을 적고, 해시가 다르면 두 값과 불일치를 적는다. 어느 경우든 적으면 완료로 본다.
  - B. curl로 기준값 만들기: 기준값이 없는 버전이면 실행 뒤 같은 경로를 curl로 따로 받아 SHA-256을 적고 대조한다. 다르면 실패로 본다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: C7은 관찰 기록이라 불일치도 결과로 남기면 되고, 판정이 실행자에 따라 갈리지 않는다. B는 같은 서버의 같은 경로를 두 번 받는 것이라 대조의 의미가 약하고 서버 사정으로 실패할 수 있어 고르지 않았다.
- 반영: spec.md C7
