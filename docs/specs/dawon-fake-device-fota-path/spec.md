# 다원 가짜 장비 FOTA 요청 경로 맞춤

기능: dawon-fake-device(기준 spec docs/features/dawon-fake-device.md)
이슈: GitHub #24

## 무엇을, 왜

가짜 장비(dawon-fake-device)는 다원이 MQTT로 보낸 FOTA URL(`http://dwapi.dawonai.com:18446/DAWONDNS/B540_W/1.01.34`)로 `GET {URL}/version`과 `GET {URL}`를 보냈고, 2026-11-20 실제 다원 실행에서 둘 다 404였다. 그래서 펌웨어 이미지를 받지 못했다.

슬롯 B 펌웨어 분석과 이번 사전 확인으로 원인을 밝혔다.

- 실제 장치는 `/version` 요청을 보내지 않고, URL 경로 끝에 슬롯 접미사를 붙인 요청 하나만 보낸다. GET 빌더는 판정 함수의 결과가 0이면 `_2`, 1이면 `_1`을 붙인다(관찰). 이 함수가 SDK의 실행 슬롯 판정(0=user1, 1=user2)이라는 것은 함수 형태와 두 슬롯의 상수 배치에 근거한 추정이다. 따라서 **반대편 슬롯 접미사**(user1에서 돌면 `_2`, user2에서 돌면 `_1`)는 추정 규칙이다. 분석한 코드는 슬롯 B뿐이다.
- 다원 서버는 `…/1.01.34_1`·`…/1.01.34_2`에 200으로 서로 다른 이미지(user1·user2 빌드)를 준다. `_2`로 받은 이미지는 B540 덤프의 슬롯 B와 바이트 단위로 같다. 접미사 없는 경로는 404다(Host 헤더의 포트 유무와 관계없음).
- 지난 404의 원인은 접미사가 없던 것 하나다. .NET `HttpClient`는 GET 줄에 경로만 넣으므로, 기준 분석 기록 `docs/reference/b540-fota.md`의 "가짜 장비가 전체 URL을 GET 줄에 넣었다"는 서술과 "슬롯 B는 `_2`를 붙인다"는 서술은 틀렸다.

이 변경은 가짜 장비가 실제 장치와 같은 요청으로 FOTA 이미지를 받게 하고(D001~D004), 기준 분석 기록의 틀린 서술을 바로잡는다.

범위 밖: 장치의 버전 게이트 흉내(D003), 받은 이미지의 검증·실행, FOTA 진행·결과 보고.

## 완료 조건

- C1. 다원에서 받은 메시지에서 FOTA URL 후보를 찾고 자동 받기가 켜져 있으면, 가짜 장비는 그 URL마다 `GET {URL}{접미사}` 요청 하나만 보낸다. `/version` 요청과 접미사 없는 URL 요청은 보내지 않는다. URL의 버전과 설정의 펌웨어 버전은 비교하지 않는다. 한 번 실행하는 동안 같은 URL은 한 번만 자동으로 받는다(기존 규칙 유지).
- C2. 접미사는 설정 `Device.RunningSlot`(흉내 낼 실행 슬롯, 1 또는 2, 기본 2)의 반대편이다(위 추정 규칙을 따름). 실행 슬롯 2면 `_1`, 1이면 `_2`다. 1·2가 아닌 값이면 원인을 표준 오류에 쓰고 다원 서버에 연결하지 않은 채 종료 코드 2로 끝난다.
- C3. 콘솔 `fota <URL>` 명령은 C1과 같은 요청(`GET {URL}{접미사}`) 하나를 보낸다. 같은 URL이라도 명령마다 다시 받는다. 콘솔 도움말이 바뀐 동작을 보인다.
- C4. 콘솔 `get <URL>` 명령은 지금처럼 주어진 URL을 가공하지 않고 그대로 요청한다.
- C5. FOTA 기록(채널 `fota`)의 요청·응답 항목은 실제로 보낸 URL(접미사 포함)을 담는다. 버전 요청이 없어지므로 응답 항목에 응답 본문을 담는 경우는 없다. 나머지 응답 항목 내용(상태 코드·`Content-Type`·`Content-Length`·받은 바이트 수·SHA-256·저장 파일 이름)과 받기 규칙(헤더, 시간 제한, 크기 상한, 200일 때만 저장)은 그대로다.
- C6. C1~C5를 확인하는 자동 테스트가 있고, 가짜 장비의 기존 테스트와 함께 통과한다. 이 테스트는 실제 다원 서버 대신 테스트 안의 가짜 서버를 쓴다.
- C7. 실제 다원 서버로 한 번 실행한다(수동). 펌웨어 버전을 낮게(예: `1.01.30`) 설정하고 FOTA URL을 받으면, 자동 받기의 요청 URL·상태 코드·받은 바이트 수·SHA-256을 작업 기록에 적는다. 200이면 받은 파일의 SHA-256을 작업 문서에 적은 사전 확인의 같은 접미사 이미지 SHA-256과 대조한다. 기준값이 없는 버전이면 대조하지 않고 그 사실을 적는다. 해시가 다르면 두 값과 불일치를 적는다. 어느 경우든 적으면 완료로 본다. 다원이 FOTA 메시지를 보내지 않으면 그 사실을 적으면 완료로 본다. 받은 파일과 실제 값은 저장소에 넣지 않는다.
- C8. `docs/reference/b540-fota.md`가 다음을 적는다. 근거로 함수 참 링크 주소·DRAM 주소·파일 오프셋을 붙인다.
  - 관찰: GET 빌더가 판정 함수 결과 0이면 `_2`, 1이면 `_1`을 붙이는 분기와 두 상수의 위치(슬롯 B), 슬롯 A에도 같은 두 상수가 있다는 것
  - 추정: 판정 함수가 실행 슬롯 판정(0=user1, 1=user2)이어서 반대편 슬롯 이미지를 받는다는 규칙. 슬롯 A 코드는 미확인
  - 관찰: 다원 서버가 `<경로>_1`·`<경로>_2`에 200으로 user1·user2 이미지를 주고, `_2` 이미지가 덤프 슬롯 B와 같다는 사실
  - 관찰: 지난 404의 원인(접미사 없음)
  - 새 사실과 모순되는 다음 서술을 고치거나 지운다: 3절 4항의 "슬롯 접미사(상수 `0x3ffe990c`)", 다원 URL 예의 `_2` 요청과 "가짜 장비가 전체 URL을 GET 줄에 넣었다"·"`_2`로 맞춰야 한다"는 설명, 4절의 슬롯별 접미사 서술, 머리말 근거 줄의 "서버측 서빙은 관찰하지 않았다", 5절 미확인의 "서버가 `<path>_N` 경로로 서빙하는 이미지"

  서버 호스트·포트는 그대로 적고, 실장비 mac·계정·키와 덤프·원격 산출물 경로는 넣지 않는다.
- C9. 기준 spec `docs/features/dawon-fake-device.md`의 개요, 범위 밖, 요구(R1·R9·R13·R14·R15·R16), 이력이 이 변경대로 바뀐다. 범위 밖의 "다원이 보내지 않은 FOTA 경로를 추측한 요청"은 "다원이 보낸 URL에 장치 규칙의 접미사를 붙이는 것 밖의 추측 경로 요청"으로 바뀐다.
