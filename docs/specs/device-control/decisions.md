# 장치 제어 화면·기능 결정

### D001 상태·계량은 실시간 대시보드로 보이고 릴레이는 대시보드에서 바로 제어한다
- 단계: spec
- 질문: 상태·계량 읽기와 릴레이 켜기/끄기를 어떤 화면에 둘지. 처음 제안은 장비 목록에서 장비를 골라 들어가는 장비 상세 화면에 "읽기" 버튼이 있는 상태·계량 카드와 릴레이 켜기·끄기 버튼을 두는 것이었다.
- 선택지:
  - A. 장비 상세 화면: 장비를 골라 들어간 화면에서 "읽기" 버튼으로 상태·계량을 가져오고, 같은 화면에서 릴레이를 제어한다.
  - B. 대시보드: 장비 전체의 상태·계량을 한 화면에 실시간으로 보이고, 그 화면에서 릴레이를 바로 켜고 끈다.
- 결정: B
- 이유: 사용자가 "상태, 계량 정보는 대시보드 형태로 실시간으로 나오는 게 맞고, 릴레이 켜고 끄기는 대시보드에서 바로 하는 게 낫다"고 말함. A를 고르지 않은 이유는 사용자가 말하지 않음
- 반영: spec.md

### D002 계량 값은 장치가 스스로 보내는 보고만으로 갱신한다
- 단계: spec
- 질문: 대시보드의 계량 값을 얼마나 자주 갱신할지. 장치는 보고 조건(최소 간격·최대 간격·변화 기준, `docs/reference/b540-mqtt-topic.md` 「오브젝트 99 리소스 처리」)에 따라서만 계량 값을 보고하므로, 보고 사이에는 값이 갱신되지 않는다. 릴레이 변경은 장치가 바로 알린다(`docs/reference/mqtt-device-control.md` 3.4).
- 선택지:
  - A. 장치 보고만 사용: 장치가 보내는 보고를 받는 대로 보인다. 더 자주 보려면 보고 조건 제어로 간격을 줄인다.
  - B. 서버가 주기적으로 읽기: 대시보드를 보는 동안 서버가 일정 간격으로 `r` 메시지를 보내 값을 받는다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md

### D005 장비별 최신 상태는 서버 메모리에만 보관한다

- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md

### D008 대시보드는 카드 배치로 한다
- 단계: spec
- 질문: 대시보드에서 장비를 어떤 형태로 늘어놓을지. 시안(저장소 밖, 2026-11-22)에 두 안을 만들어 보였다.
- 선택지:
  - A. 카드: 장비마다 카드 하나. 전력을 크게, 전압·전류·역률을 그 아래에 두고, 카드 아래쪽에 릴레이 스위치와 "제어" 버튼을 둔다. 좁은 화면에서는 한 줄로 쌓인다.
  - B. 표: 장비 한 대가 한 줄. 상태, MAC, 모델, 전력, 전압, 전류, 역률, 마지막 보고, 릴레이 스위치, "제어" 버튼 순서. 좁은 화면에서는 표 안에서 가로 스크롤한다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md

### D009 서버 재시작 뒤 릴레이 상태는 서버가 한 번 읽고, 모르는 동안에는 켜기·끄기 버튼으로 제어한다
- 단계: spec
- 질문: spec 검토 1회차 지적 2. 주기 보고(`Report`)의 요소에는 `/100/0/30`·`31`이 없다(근거 문서 4.3). 릴레이 요소는 `Send_FirstRelay`(조건 플래그가 0일 때 한 번), `e` 응답, `Send_RelayStatus`에만 있고, 그 플래그가 재접속 때 0으로 돌아가는지 근거에 없다. 그런데 spec은 릴레이 스위치를 "릴레이 상태를 아는 장비에서만" 누를 수 있게 해, 서버를 다시 시작하면 릴레이를 켜고 끌 방법이 없어질 수 있었다. 또 토픽 정보를 상태 보고에서만 배우게 돼 있어, 접속 직후의 `tisyn`만 온 장비는 제어할 수 없었다.
- 선택지:
  - A. 모를 때 켜기·끄기 버튼: 릴레이 상태를 모르면 스위치 대신 "켜기"·"끄기" 버튼을 보이고(끄기는 확인 창), 상태를 알게 되면 스위치로 바꾼다. 서버는 읽지 않는다.
  - B. 서버가 `r`로 읽기: 장비의 토픽 정보를 알았는데 릴레이 상태를 모르면 서버가 `r` `/100/0/30`을 한 번 보낸다.
  - C. 둘 다: B로 채우고, 그래도 모르는 동안에는 A의 버튼으로 제어한다.
  - 고치지 않음: 릴레이 상태를 모르면 스위치를 누를 수 없다.
  - 세 방법 모두 토픽 정보를 `tisyn`을 포함한 장치의 모든 메시지에서 기억하도록 고친다.
- 결정: C
- 이유: 사용자가 말하지 않음
- 반영: spec.md 「확정한 결정」, C3, C30, C19, C21, C22, C25

### D010 예약의 요일은 일~토 순서로 추정해 만들고 실장비에서 확인한다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. 예약 문자열의 요일 7자리가 어느 요일에 대응하는지 spec에 없었고, 근거 문서 3.3도 대응을 적지 않았다(비트 순서는 추정). 화면에서 고른 요일과 다른 요일에 전원이 끊길 수 있고, 서버 테스트의 기대 페이로드도 정할 수 없었다.
- 선택지:
  - A. 매일만 지원: 요일 선택을 없애고 항상 `1111111`을 보낸다.
  - B. 추정 순서로 지원: 첫 자리를 일요일(일~토)로 정하고 추정임을 밝힌다.
  - 고치지 않음: 대응을 정하지 않는다.
- 결정: B에 실장비 확인을 더함. 추정 순서로 만든 뒤 실장비에서 확인하고, 다르면 고친다.
- 이유: 사용자가 "B로 만들고 실장비에서 검증을 한 뒤 다르면 수정 조치. 현재 요일 기준으로 현재 시간 기준 몇 분 뒤에 설정해 두고 동작하는지 확인해 보면 검증 가능"이라고 말함. A와 고치지 않음을 고르지 않은 이유는 사용자가 말하지 않음
- 반영: spec.md 「근거의 한계」, C12, C26, C31

### D011 설정 값은 서버 메모리에만 두고, 예약 저장은 항상 `U`, 삭제는 항상 받는다
- 단계: spec
- 질문: spec 검토 1회차 지적 5. 서버가 마지막으로 보낸 설정 값이 메모리에만 있어 서버를 다시 시작하면 "보낸 적 없음"이 된다. 처음 spec은 그때 예약 삭제를 404로 막고 버튼도 비활성으로 둬, 장치에 남은 예약을 지울 수 없었다. 또 그때 저장하면 `I`를 보내는데, 같은 번호 항목이 이미 있는 장치의 `I` 처리는 근거에 없다(근거 문서 3.3이 관찰한 것은 "`U`인데 기존 항목이 없으면 `I`로 바꿔 처리"뿐). 삭제 메시지의 나머지 항목 값도 정해지지 않았고, 설정 값의 메모리 보관은 D005(최신 상태만 다룸)에 들어 있지 않았다.
- 선택지:
  - A. 메모리 유지: 저장은 항상 `U`를 보내고, 삭제는 서버 기록과 상관없이 받아 고정 문자열 `"1,D,F,0,1111111,00:00:00,F,0"`을 보낸다. 설정 값은 서버 메모리에만 둔다.
  - B. DB 저장: A의 저장·삭제 규칙에 더해, 마지막으로 보낸 설정 값을 DB에 저장한다(테이블·마이그레이션 추가).
  - 고치지 않음: `I`/`U` 구분과 삭제 404를 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md 「확정한 결정」, 범위 밖, C12, C13, C26

### D012 대기전력 차단은 만들되 근거의 한계를 밝힌다
- 단계: spec
- 질문: spec 검토 1회차 지적 6. 대기전력 차단 값의 범위(기준 전력 0.00~9999.99, 지연 0~9999)에 출처가 없었다. 근거 문서 3.2에서 `/100/0/40`~`42`의 의미는 추정이고 배율 상수는 미확인이며, 받아들이는 범위와 지연의 단위는 없다.
- 선택지:
  - A. 한계 명시: 범위가 서버가 정한 입력 제한임을 적고, 의미 추정·배율·단위 미확인을 「근거의 한계」와 화면 안내에 밝힌다.
  - B. 범위에서 뺌: 대기전력 차단을 이번에 만들지 않는다.
  - 고치지 않음: 범위를 출처 표기 없이 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md 「근거의 한계」, C11, C26

### D013 전원 재투입과 재부팅에는 확인 창을 둔다
- 단계: spec
- 질문: spec 검토 1회차 지적 9-1. 「확정한 결정」의 "릴레이 끄기에만 확인 창을 둔다(D004)"와 장비 제어 화면의 "전원 재투입과 재부팅은 확인 창을 거친다"가 문면상 어긋났다. D004는 켜기·끄기 사이의 결정이었다.

  - 고치지 않음: 두 문장을 그대로 둔다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md 「확정한 결정」, C25

### D014 장치 메시지는 ClientId의 mac과 토픽 장치 키의 mac이 같을 때만 반영한다
- 단계: spec
- 질문: spec 검토 1회차 지적 9-2. 상태 보고를 어느 장비의 것으로 볼지(토픽의 장치 키인지, 보낸 ClientId인지) spec에 없었다. 인증된 다른 장치가 남의 장치 키 토픽으로 보고하면 누구의 상태와 제어 토픽이 바뀌는지 정해지지 않았다. B540 장치 키의 3요소 순서도 미확인이다(`docs/reference/b540-mqtt-topic.md` 2절·4절).
- 선택지:
  - A. 두 mac이 같을 때만: 보낸 ClientId의 mac과 토픽 장치 키의 mac(마지막 `-` 뒤)이 같을 때만 반영하고, 다르면 Warning 로그를 남기고 반영하지 않는다.
  - B. 토픽 장치 키만: 토픽 장치 키의 mac으로만 귀속한다.
  - 고치지 않음: 귀속 기준을 정하지 않는다.
- 결정: A
- 이유: 사용자가 말하지 않음
- 반영: spec.md 완료 조건 용어, C1, C3

### D015 릴레이 상태 읽기는 장비의 메시지를 받았을 때 보내고, 큐에 넣지 못하면 다음 메시지 때 다시 시도한다
- 단계: spec
- 질문: spec 검토 2회차 지적 2. D009로 더한 조건(C30)은 "토픽 정보를 알고, 온라인이고, 릴레이 상태를 모르면 `r` `/100/0/30`을 한 번 보낸다"였다. 재접속 때는 토픽 정보가 이미 있어 접속한 순간 조건이 맞는데, 그 순간 장치는 아직 서버 → 장치 토픽을 구독하지 않았을 수 있고(구독이 없으면 메시지는 아무에게도 가지 않는다. mqtt-broker R13), 보내는 시점과 큐에 넣지 못한 것도 "한 번"으로 치는지가 정해지지 않았다.
- 선택지:
