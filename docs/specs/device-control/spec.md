# 장치 제어 화면·기능

기능: device-dashboard(새 기능) / device-control(새 기능) / mqtt-broker(기준 spec docs/features/mqtt-broker.md) / admin-ui(기준 spec docs/features/admin-ui.md) / device-list(기준 spec docs/features/device-list.md)
이슈: GitHub #28

## 무엇을, 왜

관리 화면에는 장비 목록만 있고, 장비의 상태(릴레이, 계량 값)를 보거나 장비를 제어할 방법이 없다. 서버의 서버 → 장치 명령 발행(`MqttDeviceCommandPublisher`)은 껍데기이고, 장치가 보내는 상태 보고(`notify`)는 로그로만 남는다.

#27에서 B540·M130-W 펌웨어를 분석해 서버 → 장치 제어 메시지를 `docs/reference/mqtt-device-control.md`(아래 "근거 문서")로 정리했다. 이 근거로 다음을 만든다.

- **대시보드**: 등록된 장비 전체의 온라인 여부, 릴레이 상태, 계량 값을 실시간으로 보이고, 그 화면에서 릴레이를 바로 켜고 끈다(D001).
- **장비 제어 화면**: 장비 한 대의 전원 재투입, 재부팅, 보고 조건, 대기전력 차단, 예약 전원 재투입을 제어한다.
- **서버 제어 기능**: 위 화면이 쓰는 관리 API, MQTT 명령 발행, 장치 상태 보관과 브라우저로의 실시간 전달.

화면은 시안(저장소 밖, 2026-11-22)으로 확정했다. 대시보드는 시안의 "A. 카드"안이다(D008).

확정한 결정:

- 계량 값은 장치가 스스로 보내는 보고만으로 갱신한다(D002). 장치는 보고 조건에 따라서만 계량 값을 보고하므로(`docs/reference/b540-mqtt-topic.md` 「오브젝트 99 리소스 처리」) 계량 값은 보고 조건만큼 늦을 수 있다.
- 원격 켜기·끄기(`e`)의 응답과 자동 복구로 다시 켤 때 장치가 릴레이 상태를 알린다(근거 문서 3.3·3.4). 본체에서 바꾼 것으로 보이는 변경을 알리는 것을 실장비 B540 `1.01.36`에서 관찰했다(2026-11-22 서버 로그: `/100/0/31` `false`·`/100/0/32` `2`). 같은 날 동작한 예약(`0200000`, 16:00:00) 시각 전후에는 다시 켤 때의 보고(`/100/0/31` `true`·`/100/0/32` `16`)만 왔고 꺼짐 보고는 오지 않았다(한 번 관찰, 실제로 꺼진 것은 확인하지 않음). 대기전력 차단으로 끌 때도 알리는 것을 같은 장치에서 관찰했다(2026-11-22 서버 로그: `/100/0/31` `false`·`/100/0/32` `1`, 네 번. M130-W는 미확인). 그래서 대시보드의 릴레이 상태는 장치가 마지막으로 알린 값이다.
- 서버 → 브라우저 전달은 SSE로 한다(D003).
- 릴레이는 끄기에만 확인 창을 두고 켜기는 바로 실행한다(D004). 전원 재투입과 재부팅은 전원이 내려가는 동작이라 확인 창을 둔다. 예약 삭제도 서버 기록과 상관없이 누를 수 있어 확인 창을 둔다(D018).
- 장비별 최신 상태는 서버 메모리에만 둔다(D005). 서버를 다시 시작하면 사라진다. 계량 값은 다음 장치 보고로 다시 채워지고, 릴레이 상태는 서버가 장치에 읽기를 보내(C30) 채우며, 그래도 모르는 동안에는 켜기·끄기 버튼으로 제어한다(D009).
- 서버가 마지막으로 보낸 설정 값(보고 조건, 대기전력 차단, 예약)도 서버 메모리에만 둔다(D011). 서버를 다시 시작하면 사라져 화면에 빈 값으로 보이며, 장치에 남은 설정은 그대로다.
- 관리 화면에는 인증이 없다(admin-ui 기준 spec 머리말). 새 관리 API도 관리 포트 제한(admin-ui R6)만 둔다.

근거의 한계와 그에 따른 범위:

- 근거 문서는 정적 분석이고, B540 분석 이미지는 `1.01.34`인데 관찰한 실장비는 `1.01.36`이다(근거 문서 머리말). 이 작업의 검증은 테스트용 MQTT 클라이언트로 서버가 근거 문서대로 메시지를 보내고 받는지까지다. 실장비에 제어 메시지를 보내는 확인은 예약(C31) 하나만 완료 조건에 넣는다.
- 예약(스케줄)은 근거 문서 3.3에서 확인된 동작만 만든다. 확인된 동작은 "자동 복구 시간 N이 0이 아닌 항목 하나를 기준으로, 정한 요일·시각에 릴레이를 끄고, 현재 초가 항목의 초에 N을 더한 값과 같아질 때 다시 켠다"이다. 스케줄 판정은 그 한 항목만 보므로(근거 문서 3.3 「기준 항목」) 예약은 장비마다 하나만 둔다. 정한 시각에 켜기만·끄기만 하는 동작은 `OnOff` 필드의 쓰임이 미확인이라 만들지 않는다. 그래서 N은 다시 켤 때까지의 초로 추정한다(근거 문서 3.3)(D017).
- 예약의 요일 7글자는 일·월·화·수·목·금·토 순서다. 예약 해석 함수(`SetLocalAlram`, B540 `1.01.34` `0x402c9870`, M130-W `2.01.58` `0x4024c0a0`, 디컴파일)는 각 글자를 요일 비트(일 `0x40`, 월 `0x20`, …, 토 `0x01`)로 옮겨 더하는데, 첫 글자(일)는 더하지 않고 글자가 `0`·`1`인지 검사하지 않는다. 그래서 첫 글자로는 일요일이 저장되지 않고, 둘째 글자에 `2`를 넣으면 일요일 비트가 된다. 실장비 B540 `1.01.36`에서 2026-11-22(일요일)에 `1000000`과 `1111111`은 동작하지 않았고 `0200000`은 동작했다(자동 복구로 다시 켤 때의 보고 관찰). 서버는 이 방식으로 일요일을 보낸다(D027, C12). M130-W 실장비는 미확인이다.
- 예약 시각은 장치 시계로 판정한다. 장치 시계는 서버의 시간 동기 응답으로 맞춰진다(B540 `1.01.36` 한 대에서 위 시험으로 확인. M130-W 실장비의 시계 값은 미확인). 그 시험에서 다시 켜졌다는 보고가 서버 시각으로 예상한 때보다 약 7초 늦었으며(시간 동기 약 3분 뒤, 한 번 관찰), 장치 시계의 오차는 미확인이다.
- B540 장치 키의 요소 순서는 미확인이다(`docs/reference/b540-mqtt-topic.md` 2절·4절. 회사-모델-MAC 순서는 M130-W에서만 관찰했다). 그래서 장치 메시지가 어느 장비의 것인지 가릴 때 장치 키 안 mac의 위치를 가리지 않는다(D016).
- 전원 재투입 값(`/100/0/68`)의 단위는 근거 문서 2절·7절에 미확인으로 적혀 있다. 실장비 B540 `1.01.36`에서 N=10은 끄기 응답 약 11.4초 뒤, N=30은 약 31.4초 뒤에 켜짐 보고가 와서 한 단위가 약 1초임을 관찰했다(2026-11-22). M130-W는 미확인이다. 화면은 이 내용을 안내한다(C25).
- 대기전력 차단 리소스(`/100/0/40`~`42`)의 의미는 추정이고, 배율·지연 단위·받아들이는 범위는 미확인이다(근거 문서 3.2). 실장비 B540 `1.01.36`에 기준 전력 `1.00`을 보내자 장치가 `/100/0/41` `1.10`으로 응답했다(2026-11-22, 네 번). 보낸 값의 1.1배가 저장되는 것일 수 있으나 값 하나만 본 것이라 추정이다.
- `/99/0/2`·`3`·`4`(보고 조건)는 읽기(`r`)로도 값이 덮어써지고(근거 문서 2절 「`r` 주의」), 스케줄은 읽기 응답 값이 없다(근거 문서 3.2). 그래서 보고 조건과 예약은 장치에서 현재 값을 읽지 않고, 서버가 마지막으로 보낸 값을 보인다. 대기전력 차단도 같은 방식으로 맞춘다.

범위 밖:

- FOTA(`/5/0/1`), 설정 초기화·등록 해제(`drg`·`d`), 타이머(`/100/0/50`~`57`), 시간 동기 화면(D007). 시간 동기는 기존 `tisyn` 자동 응답(mqtt-broker R5)을 그대로 둔다.
- 인증·권한(별도 일감)
- 서버가 주기적으로 `r`을 보내 계량 값을 읽는 것(D002), 계량 값 이력 저장과 그래프
- 상태·설정 값의 DB 저장(D005, D011)
- 현재 요일 쓰기(`/100/0/59`): 장치가 시간 동기 값으로 현재 요일을 정하므로(`docs/reference/b540-mqtt-topic.md` 「시간 동기」, B540 `1.01.36`의 위 예약 시험에서 동작) 보내지 않는다.
- 다크 모드, 모바일 전용 화면

## 완료 조건

용어: **관리 포트**는 `HttpPort`·`HttpsPort`, **장치 포트**는 `DeviceHttpPort`·`DeviceHttpsPort`다. **mac**은 소문자 12자리 16진수다. **온라인**은 그 mac의 MQTT 클라이언트(ClientId `DAWONDNS-{mac}`)가 브로커에 접속해 있는 것이다. **제어 메시지**는 서버 → 장치 토픽(mqtt-broker R2)에 retain 없이 보내는 `{"sid":"<문자열>","msg":{"o":"<op>","e":[{"n":"<경로>","sv":"<값>"}]}}`이다. **장비의 메시지**는 장치 → 서버 토픽(mqtt-broker R2)으로 온 메시지 가운데, 토픽 장치 키를 `-`로 나눈 요소 가운데 보낸 클라이언트 ClientId의 mac과 같은 것(대소문자 무시)이 있는 것이다. 그런 요소가 없거나 ClientId에서 mac을 읽을 수 없는 메시지는 Warning 로그를 남기고 C1·C3에 반영하지 않는다(기존 분배와 로그는 그대로다).

장비 상태(서버):

- C1. 서버는 장비의 메시지 가운데 상태 보고(`msg.o`가 `notify` 또는 `n`)의 요소에서 장비별 최신 상태를 만든다. `/100/0/30` 또는 `/100/0/31`의 `true`·`false`는 릴레이 켜짐·꺼짐, `/100/0/1`·`/100/0/2`·`/100/0/3`·`/100/0/11`은 전압(V)·전류(A)·역률·전력(W)이다. 보고에 없는 항목은 이전 값을 유지하고, 숫자로 해석할 수 없는 계량 값은 무시한다. 상태 보고를 받을 때마다 마지막 보고 시각을 그 시각으로 바꾼다. 받은 내용을 Information 로그로 남기는 기존 동작(mqtt-broker R5)은 그대로다.
- C2. 서버는 장비별 온라인 여부를 브로커의 접속·끊김에 맞춰 바꾼다. 같은 ClientId가 다시 접속해 이전 연결이 끊긴 경우에도 온라인으로 남는다.
- C3. 서버는 장비의 메시지(상태 보고, `tisyn` 등 오퍼레이션과 관계없이)의 토픽에서 그 장비의 토픽 접두와 장치 키를 기억한다. 제어 메시지는 이 접두·장치 키로 만든 토픽에 보낸다.
- C30. 서버는 장비의 메시지를 받았을 때, 그 장비의 릴레이 상태를 모르고 이번 접속에서 읽기를 그 장비 클라이언트의 전송 큐에 넣은 적이 없으면, 제어 메시지 `o` `r`, 요소 `/100/0/30`(값 빈 문자열)을 보낸다. 큐에 넣었으면 응답이 없어도 그 접속 동안 다시 보내지 않고, 넣지 못했으면 다음 장비의 메시지 때 다시 시도한다. 장치의 응답은 C1로 반영한다.
- C4. 관리 포트의 장비 상태 조회 API는 등록된 장비 전체를 배열로 반환한다. 원소에는 `mac`, `modelId`, 온라인 여부, 릴레이 상태(켜짐·꺼짐·모름), 전압·전류·역률·전력(없으면 null), 마지막 보고 시각(없으면 null), 제어 가능 여부(온라인이고 C3의 토픽 정보가 있음)가 있다. MQTT 키는 어떤 이름으로도 없다. 서버 시작 뒤 보고가 없던 장비는 릴레이 모름, 계량 값·마지막 보고 시각 null이다.
- C5. 관리 포트의 장비 상태 스트림 API는 `text/event-stream`으로 응답한다. 연결하면 먼저 C4와 같은 전체 상태를 보내고, 그 뒤 어느 장비의 C4 원소가 바뀔 때마다(상태 보고, 온라인 변경, 토픽 정보를 처음 알게 됨, 장비 등록 등 원소의 값이 달라지는 모든 경우) 바뀐 장비의 원소를 보낸다. 클라이언트가 연결을 끊거나 서버가 종료하면 스트림이 끝난다.

제어(서버):

- C6. 관리 포트의 제어 API는 mac으로 장비를 가리킨다. mac 형식이 틀리면 400, 등록되지 않은 mac이면 404, 제어 가능하지 않으면(C4) 409, 입력 값이 아래 범위를 벗어나면 400을 ProblemDetails로 반환하고 제어 메시지를 보내지 않는다. 브로커가 그 장비의 클라이언트(ClientId `DAWONDNS-{mac}`)의 전송 큐에 메시지를 넣었으면 성공, 넣지 못했으면 409를 반환한다. 성공은 장치가 메시지를 받았거나 처리했다는 뜻이 아니다.
- C7. 릴레이 켜기는 `o` `e`, 요소 `/100/0/31` `"true"`, 끄기는 `/100/0/31` `"false"` 하나를 보낸다.
- C8. 전원 재투입은 `o` `e`, 요소 `/100/0/31` `"false"`와 `/100/0/68` `"<N>"`을 이 순서로 보낸다. N은 1~999의 정수다.
- C9. 재부팅은 `o` `reb`, 빈 요소 배열을 보낸다. `modelId`가 `B540`으로 시작하는 장비만 받고, 그 밖의 모델은 400이다(M130-W는 `reb`를 읽기로 처리하는 것으로 추정된다. 근거 문서 4.1).
- C10. 보고 조건 저장은 `o` `w`, 요소 `/99/0/2`·`/99/0/3`·`/99/0/4`에 최소 간격·최대 간격·변화 기준을 10진 정수 문자열로 보낸다. 범위는 최소 간격 1~3600, 최대 간격 11~14400, 변화 기준 1~100이고(`docs/reference/b540-mqtt-topic.md` 「오브젝트 99 리소스 처리」의 부팅 범위 검사), 최소 간격이 최대 간격보다 크면 400이다.
- C11. 대기전력 차단 저장은 `o` `w`, 요소 `/100/0/40`에 `"true"`·`"false"`, `/100/0/41`에 기준 전력(0.00~9999.99, 소수 둘째 자리까지의 10진 문자열), `/100/0/42`에 지연(0~9999의 10진 정수 문자열)을 보낸다. 이 범위는 서버가 정한 입력 제한이며, 펌웨어가 받아들이는 범위는 미확인이다.
- C12. 예약 전원 재투입 저장은 `o` `w`, 요소 `/100/0/58` 하나에 `"1,U,<사용>,0,<요일>,<HH:MM:SS>,F,<N>"`을 보낸다. 동작은 항상 `U`다(항목이 없으면 장치가 추가로 처리한다. 근거 문서 3.3 `AddModifiedAlram`). 사용은 `T`·`F`, 요일은 7글자이며 첫 글자는 늘 `0`, 둘째 글자는 월요일을 고르면 1과 일요일을 고르면 2를 더한 숫자(`0`~`3`), 셋째~일곱째 글자는 화·수·목·금·토 순서의 `0`·`1`이다(요일을 하나 이상 골라야 한다. 근거는 「근거의 한계」 예약 요일), N은 다시 켤 때까지의 초다. N은 1 이상이고 시각의 초와 N의 합이 60 미만이어야 하며(근거 문서 3.3 `CheckAutoRecovery`), 아니면 400이다. 예약 삭제는 서버가 보낸 예약이 있는지와 상관없이 받고, 요소 `/100/0/58`에 `"1,D,F,0,1111111,00:00:00,F,0"`을 보낸다.
- C13. 서버는 장비마다 C10·C11·C12로 마지막에 보낸 값(성공한 것만)을 기억하고, 관리 포트의 설정 조회 API로 돌려준다. 보낸 적이 없는 항목은 null이다. 예약 삭제가 성공하면 예약은 null이 된다. mac 형식이 틀리면 400, 등록되지 않은 mac이면 404를 ProblemDetails로 반환한다.
- C14. 서버는 제어 메시지를 보낼 때마다 Information 로그 항목 하나에 mac, 토픽, `sid`, 오퍼레이션, 요소를 남긴다. 실패(큐에 넣지 못함 포함)는 Warning 또는 Error 로그로 남긴다.
- C15. C4·C5·C6·C13의 API는 장치 포트에서 404 ProblemDetails를 반환하고 장비 정보를 내주지 않으며 제어 메시지를 보내지 않는다(admin-ui R6).

화면 공통:

- C16. 관리 화면의 경로는 대시보드 `/`, 장비 목록 `/devices`, 장비 제어 `/devices/{mac}`이다. 사이드바 메뉴는 "대시보드", "장비" 순서이고 현재 화면의 메뉴에 `aria-current="page"`가 붙는다(장비 제어 화면에서는 "대시보드"). 주소를 직접 열거나 새로 고쳐도 그 화면이 열리고, 브라우저 뒤로 가기가 동작한다. 장비 목록 화면의 동작(device-list R4~R12)은 경로 말고는 바뀌지 않는다.
- C17. 새 화면은 admin-ui R1~R5를 따른다(토큰 색만, shadcn 부품, 상태 화면, 접근성). 온라인 표시를 위해 상태용 색 토큰 하나를 `src/index.css`에 더하고, 온라인·오프라인은 색 점과 함께 글자("온라인"·"오프라인")로도 보인다.

대시보드:

- C18. 본문 머리에 제목 "대시보드", 요약("온라인 N대 · 오프라인 N대 · 합계 X W". 합계는 온라인 장비의 전력 합, 소수 첫째 자리), 실시간 연결 상태("실시간 연결됨"·"연결 끊김 — 다시 연결 중")를 보인다.
- C19. 등록된 장비마다 카드 하나를 mac 오름차순으로 보인다. 카드에는 모델, mac(고정폭), 온라인 여부, 전력(크게, 소수 둘째 자리, 단위 W), 전압(소수 둘째 자리, V)·전류(소수 셋째 자리, A)·역률(소수 셋째 자리), 릴레이 제어(C21), "제어" 버튼(장비 제어 화면으로), 마지막 보고의 상대 시간(device-list R6과 같은 규칙, 없으면 "보고 없음")이 있다. 값이 없으면 "—"다. 오프라인 장비의 계량 값은 흐리게 보인다.
- C20. 상태 스트림(C5)으로 받은 변경은 새로 고침 없이 카드와 요약에 반영된다. 스트림이 끊기면 연결 상태를 "연결 끊김 — 다시 연결 중"으로 바꾸고 마지막으로 받은 값을 그대로 보이며, 다시 연결되면 전체 상태를 다시 받아 맞춘다.
- C21. 릴레이 제어는 릴레이 상태에 따라 모양이 다르고, 제어 가능한(C4) 장비에서만 누를 수 있다.
  - 상태를 알 때: 스위치와 상태 글자("켜짐"·"꺼짐")를 보인다. 꺼진 스위치를 누르면 바로 켜기를 보낸다. 켜진 스위치를 누르면 장비(모델·mac)를 밝힌 확인 창이 뜨고, "끄기"를 누르면 끄기를 보내며 "취소"나 Esc는 아무것도 보내지 않는다.
  - 상태를 모를 때: "상태 모름" 글자와 "켜기"·"끄기" 버튼을 보인다. "켜기"는 바로 켜기를 보내고, "끄기"는 위와 같은 확인 창을 거친다. 릴레이 상태를 알게 되면 스위치로 바뀐다.
- C22. 켜기·끄기를 보낸 뒤 그 장비의 릴레이 상태가 보낸 값으로 바뀐 것을 스트림으로 받을 때까지 릴레이 제어는 진행 중 표시와 함께 비활성이다. API가 실패하거나 10초 안에 상태가 바뀌지 않으면 릴레이 제어를 장비의 마지막 상태로 되돌리고, 그 카드에 원인을 담은 오류 안내를 보인다.
- C23. 처음 불러오는 동안은 카드 모양 스켈레톤, 실패하면 오류 안내와 "다시 시도", 등록된 장비가 없으면 빈 목록 안내를 보인다(admin-ui R5). 폭 390px에서 카드는 한 줄로 쌓이고 페이지 가로 스크롤이 생기지 않는다.

장비 제어 화면:

- C24. 머리에 "← 대시보드" 링크, 모델과 mac, 온라인 여부, 전력, 마지막 보고 상대 시간을 보이고, 스트림으로 실시간 반영한다. 등록되지 않은 mac이면 "장비를 찾을 수 없습니다" 안내와 대시보드 링크를 보인다.
- C25. "전원" 묶음에 릴레이 제어(C21·C22와 같은 동작), 전원 재투입(값 입력 1~999, 기본 10, "실행"), 재부팅 버튼이 있다. 묶음 안내로 "전원 재투입 단위는 약 1초입니다(B540에서 확인)"를 보인다. 전원 재투입과 재부팅은 장비를 밝힌 확인 창을 거친다. 재부팅은 `modelId`가 `B540`으로 시작하는 장비에서만 보인다.
- C26. 설정 묶음은 셋이다.
  - "보고 조건": 최소 간격·최대 간격·변화 기준 입력과 "저장".
  - "대기전력 차단": 사용 스위치, 기준 전력, 지연 입력과 "저장". 지연 입력에는 단위를 적지 않고, 묶음에 "값의 의미와 단위는 추정입니다" 안내를 보인다.
  - "예약 전원 재투입": 사용 스위치, 요일 선택(일~토, 하나 이상), 시각(시·분·초), 다시 켤 때까지의 초 입력과 "저장"·"삭제". "삭제"는 서버가 보낸 예약이 있는지와 상관없이 제어 가능한 장비면 누를 수 있고, 확인 창을 거친다.
  - 세 묶음은 서버가 마지막으로 보낸 값(C13)으로 채우고, 보낸 적이 없으면 비워 두며, "서버가 마지막으로 보낸 값이며 장비의 현재 값과 다를 수 있다"는 안내를 보인다.
- C27. 입력이 C8·C10·C11·C12의 범위를 벗어나면 보내지 않고 그 입력 옆에 이유를 보인다. 보내는 동안 그 묶음의 버튼은 비활성이다. 성공하면 그 묶음에 "장비에 보냈습니다" 안내를, 실패하면 원인을 담은 오류 안내를 보인다. 제어 가능하지 않은 장비(C4)에서는 모든 제어 버튼이 비활성이고 그 까닭("장비가 오프라인입니다" 등)을 보인다.
- C32. 장비 제어 화면의 네 묶음(C25·C26)은 같은 규격으로 놓는다(D032).
  - 배치: 본문 왼쪽에 맞춘 최대 폭 1120px 안에서 2열(전원·보고 조건 / 대기전력 차단·예약 전원 재투입)로 놓는다. 두 열이 들어가지 않는 폭(390px 등)에서는 한 열로 쌓이고 페이지 가로 스크롤이 생기지 않는다. 1440px 이상의 화면에서는 폭과 상관없이 열 수와 묶음 폭이 같다. 같은 줄의 묶음은 높이가 같다.
  - 묶음 안: 제목, 안내, 입력(릴레이·사용 스위치·요일 포함), 버튼 순서다. 늘 보이는 안내(C25·C26)는 제목 바로 아래에 같은 글자 크기로 모은다. 입력의 이유(C27)는 그 입력 아래, 실패 오류 안내(C27)는 버튼 줄 위, 릴레이 오류 안내(C22)는 릴레이 제어 아래에 보이며, 이 세 가지가 나타나면 묶음 높이가 늘어날 수 있다. 글자 입력 칸은 모든 묶음에서 2칸 격자의 한 칸 폭이다. 버튼은 묶음 맨 아래 한 줄에 두고, 묶음의 주 버튼("실행"·"저장")은 채운 버튼, 나머지("재부팅"·"삭제")는 테두리 버튼이다. "장비에 보냈습니다" 안내는 버튼 줄에 보여 그 안내가 나타나도 묶음 높이가 바뀌지 않는다.

테스트·문서·실장비 확인:

- C28. 서버 테스트가 C1~C15·C30을 확인하고 통과한다. 서버 테스트는 테스트용 MQTT 클라이언트로 브로커에 접속해 장비의 메시지를 보내고 제어 메시지를 받아 토픽과 페이로드를 확인한다. 클라이언트 테스트가 C16, C17의 글자 표시, C18~C27(C23의 390px 배치 제외)과 C32의 안내·버튼 순서와 종류를 확인하고 통과한다. C23의 390px 배치와 C17의 색 토큰은 브라우저 화면으로 확인하고, 그 밖의 C32(배치, 안내 글자 크기, 입력 칸 폭, 버튼 줄 자리, 성공 안내가 나타난 뒤의 높이)는 1440px·2000px·390px 브라우저 화면으로 확인한다. 기존 테스트도 통과한다.
- C29. 기준 spec을 맞춘다. `docs/features/device-dashboard.md`와 `docs/features/device-control.md`를 새로 만들고, `docs/features/mqtt-broker.md`(명령 발행 구현, 상태 보고 처리, 접속·끊김 추적), `docs/features/admin-ui.md`(메뉴, 경로, 상태용 색 토큰, 새 UI 부품), `docs/features/device-list.md`(화면 경로)에 이번 변경을 반영한다.
- C31. 실장비 한 대(사용자가 실행 전에 정해 준 장치)에서 예약을 확인한다. 그 날의 요일만 고른 예약을 몇 분 뒤 시각으로 장비 제어 화면에서 저장하고, 서버가 보낸 문자열의 요일이 C12대로인지를 로그에서, 그 시각에 릴레이가 꺼졌다가 N초 뒤 켜지는 것을 본체에서, 다시 켤 때의 상태 보고(`/100/0/31` `true`, `/100/0/32` `16`)를 로그에서 본다. 동작하지 않으면 원인을 가려 고친 뒤 다시 확인한다. 확인에 쓴 예약은 끝난 뒤 삭제한다. 확인 결과(펌웨어 버전, 보낸 문자열, 관찰)와 「확정한 결정」·「근거의 한계」에 적은 2026-11-22 관찰(요일 글자, 전원 재투입 단위, 본체 조작 때와 예약 시각 전후의 보고, 대기전력 차단 때의 보고와 기준 전력의 응답, 장치 시계가 시간 동기로 맞춰진 것과 약 7초 늦은 보고)을 근거 문서와 `docs/reference/b540-mqtt-topic.md`의 해당 절에 적는다.
