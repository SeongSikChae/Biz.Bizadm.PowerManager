# 다원 가짜 장비 클라이언트

기능: dawon-fake-device(새 기능)
이슈: GitHub #24

## 무엇을, 왜

다원 서버가 장치에 보내는 메시지의 실제 형식은 아직 모른다(`tisyn` 응답, 앱 조작 때의 `w`·`r` 등. `docs/reference/b540-mqtt-topic.md` 4절). 이것을 관찰하려고 중계 모드(dawon-relay, #20)를 만들었지만, 실장비·우리 서버 배포·장치 재설정·다원 계정 상태가 모두 맞아야 기록이 남는다. 2026-11-20 1차 시도의 중계 기록에서는 다음과 같았다.

- 등록: 이미 다원 계정에 등록된 mac이라 다원이 409 `{"status":"REGISTERED"}`로 거절했다. 키가 발급되지 않았다.
- MQTT: 장치가 우리 서버에서 받은 로컬 키로 접속해, 다원이 접속마다 CONNACK 4(사용자명·비밀번호 오류)로 거절했다.
- `device/connect`: 다원이 200 `{"delay":"0"}`(한 번은 `"-9"`)으로 응답했다.

그래서 장치를 흉내 내는 가짜 장비 클라이언트를 새 콘솔 프로그램으로 만든다(D001). 이 프로그램은 다원 REST 서버(`dwapi.dawonai.com:18443`)에 직접 등록하고, 다원 브로커(`dwmqtt.dawonai.com:8883`)에 장치와 같은 방식으로 접속한다. 장치 메시지를 보내고, 보내고 받은 원문을 모두 기록한다. 우리 서버와 실장비 없이 한 대의 PC에서 시험할 수 있고, 보낼 메시지와 시점을 우리가 정할 수 있다.

장치 쪽 형식의 근거는 다음과 같다.

- 등록 요청 형식: `docs/reference/b540-rest-api.md` 2절(관찰). 등록 응답의 `verify` 계산식: device-register R3(실제 다원 응답과 일치 확인).
- MQTT 접속: MQTT 3.1(`MQIsdp`), TLS(`docs/reference/b540-mqtt-topic.md` 1절).
- 접속 자격 정보: 실장비가 우리 브로커에 보낸 값을 서버 로그로 확인했다(2026-11-19, M130-W 3대·B540 1대).
  - ClientId는 `{회사}-{mac}`이다.
  - 사용자명은 장치 키 `{회사}-{모델}-{mac}`이다.
  - B540의 비밀번호는 등록 `mqtt_key`와 같다(mqtt-broker R9 판정 `Match`).
  - B540 실장비가 보낸 `rg`의 `/3/0/3`(펌웨어 버전)은 `1.01.36`이다(같은 로그. 정적 덤프는 `1.01.34`).
- 토픽과 메시지 형식: `docs/reference/b540-mqtt-topic.md` 2·3·5절.
  - 구독 `{접두}.v1/iot-server/{장치 키}/#`
  - 상태 보고 `{접두}.v1/{장치 키}/iot-server/notify/json`, `o` `n`, 요소마다 `ti` `""`(M130-W 관찰은 근거 문서 5절. B540도 같은 토픽·형식으로 `sid` `2`·`1`인 `n`을 접속 직후 보냈다, 2026-11-19 서버 로그 관찰)
  - 시간 동기 `.../iot-server/timesync/json`(관찰)
  - 등록 메시지 `rg`의 토픽 접미는 미확인이다(형식 문자열 `%s%s/json`으로 보아 `json` 추정).

MQTT 키는 등록 응답으로 받는 것이 기본이다. 이미 등록된 mac처럼 키를 받을 수 없는 경우를 위해 설정으로 키와 접속 자격 정보를 줄 수 있게 한다(D002). 접속한 뒤에는 정해진 메시지와 콘솔에서 입력한 메시지를 보낸다. 받은 메시지에는 응답하지 않고 기록만 한다(D003).

펌웨어 무선 업데이트(FOTA)도 관찰 대상으로 넣는다. 다원이 내려주는 펌웨어 이미지를 받으면 지금 정적 분석에 쓰는 플래시 덤프보다 새 펌웨어(실장비 `1.01.36`)를 분석할 수 있다. 근거 문서 `docs/reference/b540-fota.md` 3절(추정)에 따르면 다음과 같다.

- 업데이트는 서버가 MQTT 쓰기(`Set_UpgradeResourceData`, 리소스 ID 미확인)로 정보를 보내면서 시작된다.
- 장치는 URL을 해석해 `GET {URL}/version`으로 버전을 확인하고, 이미지를 HTTP `GET`으로 받는다.
- 다원의 FOTA URL과 이미지 경로 규칙은 미확인이다.

그래서 다원에서 받은 메시지에 URL이 있으면 그 URL에서 버전(`GET {URL}/version`)과 URL 자체를 받아 파일로 저장하고(URL이 이미지 자체일 수도 있다. 근거 문서 2절 `LFota_Url` "이미지 URL 또는 경로"), 콘솔 명령으로 URL을 직접 주어 받을 수도 있게 한다(D010). 이미지 이름 규칙은 미확인이라, 이미지가 따로 있으면 기록을 보고 콘솔 명령으로 받는다. 다원이 업데이트를 내려보내게 하려고 실제 확인에서는 `rg`에 낮은 펌웨어 버전을 보내고, 다원 앱에서 업데이트를 눌러 본다(D011). 받은 파일은 저장만 하고 실행하지 않는다. 다원이 보내지 않은 경로를 추측해 요청하지 않는다.

범위 밖:

- 받은 메시지에 대한 자동 응답(D003). FOTA 진행·결과 보고 메시지도 보내지 않는다.
- 접속이 끊겼을 때의 자동 재접속, 여러 장치 동시 실행
- 기록 내용의 분석과 근거 문서(`docs/reference`) 반영, 받은 펌웨어의 분석(기록을 모은 뒤 따로 한다)
- 다원이 보내지 않은 FOTA 경로를 추측해 요청하는 것(다원이 보낸 값을 이어 붙인 URL은 추측이 아니다)
- `register/create`·`device/connect`와 FOTA 다운로드 밖의 HTTP 요청
- 서버(`Server.Spa`)와 중계 모드(dawon-relay)의 동작 변경

## 완료 조건

### 실행과 설정

- C1. 프로그램은 명령줄로 받은 설정 파일 하나를 읽어 실행한다.
  - 다원 서버
    - REST 서버 호스트·포트(기본 `dwapi.dawonai.com`·18443)
    - MQTT 브로커 호스트·포트(기본 `dwmqtt.dawonai.com`·8883)
    - TLS 인증서 검증을 끄는 선택(기본은 검증함, REST·MQTT·FOTA 모두에 적용)
  - 장치
    - mac(필수, 12자리 16진수, 소문자로 정규화)
    - 모델(기본 `B540_W`), 회사(기본 `DAWONDNS`)
    - 등록 요청의 user_id·lati·long(기본 빈 값·`0`·`0`)
    - 펌웨어 버전(기본 `1.01.36`)
  - 등록
    - `mqtt_key`(선택. 주면 등록을 건너뛴다)
    - `verify` 확인에 쓰는 서버 주소(기본: MQTT 브로커 호스트). device-register R3 치환표 문자로만 이뤄져야 한다.
  - MQTT 접속
    - ClientId(기본 `{회사}-{mac}`), 사용자명(기본 `{회사}-{모델}-{mac}`), 비밀번호(기본 `mqtt_key`)
    - keepalive 초(기본 60)
    - 토픽 접두(기본 `dwd`)
    - Will 토픽·페이로드(기본 `/lwt`·`offline`, QoS 0, retain 없음)
  - 발행
    - 접속 직후 `rg`·`tisyn`을 보낼지(기본 둘 다 보냄)
    - `rg` 토픽 접미(기본 `json`)
    - 발행 QoS(기본 0)
    - `tisyn` 주기 초(기본 0 = 접속 직후 한 번만)
    - 상태 보고 주기 초(기본 0 = 보내지 않음)와 상태 보고 요소 목록(`n`·`sv` 쌍)
  - FOTA
    - 받은 메시지의 URL로 자동으로 받을지(기본 받음, C14)
    - 요청의 `User-Agent`(기본: B540 펌웨어 덤프에 있는 FOTA 요청 `User-Agent` 전체 문자열)
  - 기록 폴더(기본: 실행 폴더 아래 `dawon-fake-device`)

  설정 파일이 없거나, mac 형식이 틀리거나, `verify` 확인 서버 주소에 치환표 밖 문자가 있거나, 값의 형식이 틀리면 원인을 표준 오류에 쓰고 다원 서버에 연결하지 않은 채 0이 아닌 종료 코드로 끝난다.

### REST

- C2. 설정에 `mqtt_key`가 없으면 다원 REST 서버에 HTTPS `POST /api/v1/devices/register/create`를 보낸다.
  - 헤더: `Content-Type: application/json`, `X-HIT-Version: 1.0`
  - 본문: `{"account":{"user_id":…},"device":{"mac":…,"model_id":…,"company":…,"lati":…,"long":…,"verify":"true"}}`(`docs/reference/b540-rest-api.md` 2절 첫 형식, 값은 설정)
  - 성공 조건: 200, 본문이 JSON 객체, 최상위 `mqtt_key`가 비어 있지 않은 문자열
  - 성공하면 그 `mqtt_key`를 이번 실행의 키로 쓴다. 최상위 `verify`가 문자열이면 device-register R3 계산식(설정의 `verify` 확인 서버 주소, mac, 키)으로 계산한 값과 같은지 판정해 기록과 콘솔에 남긴다. 같지 않아도 계속한다. 키에 치환표 밖 문자가 있으면 판정을 "계산 불가"로 기록·콘솔에 남기고 계속한다.
  - 성공 조건을 채우지 못하거나, 연결에 실패하거나, 10초 안에 응답이 없으면 그 결과를 기록하고 콘솔에 상태 코드(또는 오류)를 쓴 뒤, MQTT에 접속하지 않고 0이 아닌 종료 코드로 끝난다.
- C3. 키가 정해지면(등록 성공 또는 설정) `GET /api/v1/device/connect/{회사}-{모델}-{mac}`을 보내고 응답을 기록한다. 응답 내용, 연결 실패, 10초 시간 초과와 관계없이 MQTT 접속으로 넘어간다.

### MQTT

- C4. MQTT 3.1(`MQIsdp`)로 다원 브로커에 TLS 1.2로 접속한다. C1의 ClientId·사용자명·비밀번호·keepalive·Will을 쓰고, clean session을 켠다.
  - 다원이 거부하면 CONNACK 반환 코드를 기록하고 콘솔에 쓴 뒤 0이 아닌 종료 코드로 끝난다.
  - 연결 실패, 10초 시간 초과도 같은 방식으로 끝난다.
- C5. 접속하면 `{접두}.v1/iot-server/{회사}-{모델}-{mac}/#`를 QoS 0으로 구독한다. 구독 요청과 SUBACK 결과를 기록한다.
  - 10초 안에 SUBACK이 없으면 기록하고 0이 아닌 종료 코드로 끝난다.
  - SUBACK이 실패 값이면 기록하고 콘솔에 쓴 뒤 C6으로 넘어간다.
- C6. 구독 결과를 받은 뒤 정해진 메시지를 보낸다. 모든 발행 토픽은 `{접두}.v1/{회사}-{모델}-{mac}/iot-server/{접미}`이고, QoS는 설정값, retain은 없음이다.
  - `rg`(설정이 켜져 있으면 접속 직후 한 번)
    - 접미: 설정값
    - 페이로드: `{"sid":"0","msg":{"o":"rg","e":[…]}}`
    - 요소: `/3/0/0`=회사, `/3/0/1`=모델, `/3/0/2`=mac, `/3/0/3`=펌웨어 버전, `/3/0/997`=`1`, `/3/0/998`=`1.0`, `/3/0/999`=`1`(각각 `{"n":…,"sv":…}`)
  - `tisyn`
    - 설정이 켜져 있으면 `rg` 뒤에 한 번 보낸다. 주기가 0보다 크면 그 뒤로 주기마다 보낸다.
    - 접미 `timesync/json`, 페이로드 `{"sid":"0","msg":{"o":"tisyn","e":[]}}`
  - 상태 보고
    - 주기가 0보다 크면 정해진 `rg`·`tisyn` 뒤 바로 한 번 보내고, 그 뒤 주기마다 보낸다.
    - 접미 `notify/json`, 페이로드 `{"sid":"1","msg":{"o":"n","e":[…]}}`
    - 요소: 설정의 요소 목록을 순서대로 `{"n":…,"sv":…,"ti":""}`로 넣는다.
- C7. 실행 중 콘솔에서 한 줄 명령을 받는다.
  - 토픽과 페이로드를 받아 그대로 발행한다(QoS는 설정값, retain 없음). 장치 발행 접두 `{접두}.v1/{장치 키}/iot-server/`를 줄여 접미만 쓰는 방법도 있다. 페이로드는 JSON인지 따지지 않는다.
  - FOTA 명령은 C15·C16대로 처리한다.
  - 종료 명령을 받으면 C11대로 끝낸다.
  - 알 수 없는 명령은 사용법을 콘솔에 쓰고 무시한다.
- C8. 다원에서 받은 메시지는 토픽·QoS·retain·페이로드를 기록하고 콘솔에 토픽과 페이로드를 쓴다. 응답 메시지는 보내지 않는다.

### 기록과 종료

- C9. 보내고 받은 모든 주고받음을 기록 폴더의 UTC 날짜별 파일 `dawon-fake-device-yyyyMMdd.jsonl`에 한 줄에 JSON 하나로 덧붙인다.
  - 형식은 dawon-relay R9·R10과 같은 형식을 쓴다.
    - 공통 필드: `ts`·`channel`·`direction`·`kind`
    - `device-to-dawon`은 가짜 장비가 보낸 것, `dawon-to-device`는 다원에서 받은 것이다.
    - 본문·페이로드는 자르지 않는다. 올바른 UTF-8이 아니면 Base64로 기록하고 인코딩을 표시한다.
  - REST는 요청 항목과 응답 항목으로 남긴다(메서드·경로·본문, 응답은 상태 코드까지).
  - MQTT는 접속(ClientId·사용자명·비밀번호 유무·keepalive·clean session·Will), CONNACK, 구독, SUBACK, 발행(양방향), 종료를 남긴다.
  - FOTA(C14~C16)는 요청 항목과 응답 항목으로 남긴다(채널 `fota`). 응답 항목에는 다음을 담는다.
    - URL·상태 코드·`Content-Type`·`Content-Length`(없으면 없음)
    - 받은 바이트 수, SHA-256, 저장한 파일 이름
    - 버전 요청(`/version`)의 응답 본문. 그 밖의 요청의 본문은 기록에 넣지 않고 파일로만 둔다.
  - C2의 `verify` 판정, 연결 실패·시간 초과도 각각 항목으로 남긴다.
  - 동시에 기록해도 줄이 섞이지 않는다.
- C10. 기록, 콘솔, 표준 오류에 비밀 값이 남지 않는다.
  - REST 응답 본문(JSON 객체)의 최상위 `mqtt_key`·`verify`는 `***`로 가린다.
  - MQTT 비밀번호와 설정의 `mqtt_key`는 있는지 여부만 남긴다.
- C11. 종료 명령이나 Ctrl+C를 받으면 DISCONNECT를 보내 정상 종료하고, 종료 항목을 기록한 뒤 종료 코드 0으로 끝난다. 다원 쪽에서 접속이 끊기면 종료 항목(비정상 끊김)을 기록하고 0이 아닌 종료 코드로 끝난다.

### FOTA

- C14. 다원에서 받은 메시지(C8)의 페이로드가 JSON이고, 그 안의 문자열 값 가운데 `http://` 또는 `https://`로 시작하는 값이 있으면 그 값을 FOTA URL 후보로 본다.
  - 후보를 찾으면 콘솔에 쓰고 기록에 표시한다.
  - 자동 받기 설정이 켜져 있으면 두 요청을 차례로 보낸다.
    - 버전 요청: `GET {URL}/version`(URL 끝의 `/`는 하나로 맞춘다)
    - URL 요청: `GET {URL}`(URL이 이미지 자체일 수도 있어 그대로 받아 둔다)
  - 다원이 주소·포트·경로를 나눠 보내 URL 후보가 없으면 FOTA 요청을 보내지 않는다(원문은 C8대로 기록된다).
  - 한 번 실행하는 동안 같은 URL은 한 번만 자동으로 받는다.
- C15. 콘솔 명령으로 URL을 직접 받는다.
  - URL 하나를 주면 C14의 두 요청(버전·URL)을 보낸다.
  - URL 하나를 주고 그 URL만 `GET`하는 명령도 있다.
  - 같은 URL이라도 명령마다 다시 받는다.
- C16. C14·C15의 받기는 다음 규칙을 따른다.
  - 모든 요청은 `Connection: keep-alive`와 C1 설정의 `User-Agent`를 보낸다(근거 문서 `docs/reference/b540-fota.md` 3절의 고정 헤더).
  - 두 요청(버전·URL)을 보낼 때는 버전 요청의 결과와 관계없이 두 번째 요청도 보낸다.
  - HTTP와 HTTPS를 모두 받는다. C1의 TLS 인증서 검증 설정을 따른다.
  - 200이면 응답 본문을 기록 폴더 아래 `fota` 폴더에 요청마다 새 파일로 저장한다. 받은 파일은 실행하지 않는다.
  - 200이 아니거나, 연결에 실패하거나, 60초 안에 끝나지 않거나, 본문이 4 MiB를 넘으면 그 요청의 받기를 멈추고 그 결과를 기록·콘솔에 남긴다. 받은 데까지의 파일은 남기지 않는다.
  - 받기가 실패해도 프로그램은 계속 실행한다. MQTT 처리와 정해진 발행은 받는 동안에도 멈추지 않는다.

### 확인

- C12. C1~C11과 C14~C16을 확인하는 자동 테스트가 있고 통과한다. 이 테스트는 실제 다원 서버 대신 테스트 안의 가짜 REST 서버, 가짜 MQTT 브로커, 가짜 FOTA HTTP 서버를 쓴다.
- C13. 실제 다원 서버로 한 번 실행한다(수동). 등록 또는 설정 키로 접속을 시도하고, `rg`·`tisyn` 발행, 다원에서 받은 메시지를 확인한다. 다음 결과를 작업 문서에 적는다.
  - 쓴 설정 항목(mac 등 실제 값은 빼고 종류만)
  - 등록·`device/connect` 응답 상태
  - CONNACK 반환 코드
  - 받은 메시지 종류(`tisyn`에 다원이 응답했는지 포함)
  - FOTA 시도 결과
    - 펌웨어 버전을 기본값보다 낮게(예: `1.01.30`) 설정해 실행했을 때 다원이 FOTA 메시지를 보냈는지
    - 접속에 성공했으면, 사용자가 다원 앱에서 그 장치의 펌웨어 업데이트를 눌렀을 때 받은 메시지
    - FOTA URL을 받았으면 받은 파일의 종류(버전·URL·명령으로 받은 파일)·크기·SHA-256

  다원이 FOTA 메시지를 보내지 않으면 그 사실을 적으면 FOTA 시도는 완료로 본다. FOTA URL을 받았지만 받기가 실패하면 요청마다 실패 원인(상태 코드·오류)을 적으면 FOTA 시도는 완료로 본다. FOTA로 보이는 메시지가 왔지만 URL 후보가 없으면 받은 메시지를 적고, 다원이 보낸 값으로 URL을 이을 수 있으면 C15로 받아 그 결과까지 적는다. 이을 수 없으면 메시지만 적으면 FOTA 시도는 완료로 본다. 받은 펌웨어 파일은 저장소에 넣지 않는다. 등록이 거부되면 응답 상태를 적고, 설정으로 줄 다원 키가 있으면 그 키로 다시 실행해 접속 결과까지 적는다. 줄 키가 없으면 등록 결과만으로 완료로 본다. 접속이 거부되면 CONNACK 코드까지 적으면 완료로 본다. 발행·수신 항목은 접속에 성공했을 때만 적는다. 기록 파일과 실제 값은 저장소에 넣지 않는다.
