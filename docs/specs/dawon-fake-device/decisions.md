# 다원 가짜 장비 클라이언트 결정

### D001 가짜 장비 클라이언트를 새 콘솔 프로젝트로 만든다
- 단계: spec
- 질문: 다원 서버에 장치처럼 접속하는 가짜 장비 클라이언트를 어떤 형태의 프로그램으로 만들지 정해야 했다.
- 선택지:
  - A. 새 콘솔 프로젝트: `src`에 독립 콘솔 프로젝트를 두고 설정 파일을 읽어 실행한다. Core의 `DeviceVerify`·`DeviceTopic`·`MqttEnvelope`를 그대로 쓴다.
  - B. DeviceConfig CLI 하위 명령: 기존 장치 설정 CLI(Wi‑Fi·TCP 설정 도구)에 명령을 더한다.
  - C. MCP 도구: 에이전트가 접속·발행·수신 조회를 도구로 부르게 한다.
- 결정: A
- 이유: 장치 설정 도구와 목적(장치 설정 vs 다원 서버 통신 관찰)이 달라 섞지 않는 편이 낫고, Core의 계산·토픽 코드를 그대로 쓸 수 있다. B는 따로 배포할 것이 없다는 장점이 있지만 Wi‑Fi·TCP 설정 도구에 MQTT 클라이언트가 섞인다. C는 대화형 분석에는 편하지만 장시간 접속 유지와 상태 관리가 복잡하다.
- 반영: spec.md 무엇을·왜, C1

### D002 MQTT 키는 등록으로 받고, 설정으로 키·접속 자격 정보를 덮어쓸 수 있게 한다
- 단계: spec
- 질문: 다원 브로커 접속에 쓸 `mqtt_key`와 ClientId·사용자명·비밀번호를 어떻게 정할지 정해야 했다. 이미 다원 계정에 등록된 mac은 등록 요청이 409 `REGISTERED`로 거절되어 새 키를 받을 수 없다(2026-11-20 중계 기록).
- 선택지:
  - A. 등록 + 설정으로 덮어쓰기: 기본은 `register/create`로 다원 키를 받아 비밀번호로 쓴다. 설정에 `mqtt_key`를 주면 등록을 건너뛰고, ClientId·사용자명·비밀번호도 설정으로 바꿀 수 있다.
  - B. 등록으로만: 항상 `register/create`로 키를 받고 정해진 규칙으로만 접속한다.
  - C. 설정으로만: 등록 요청 없이 설정 값으로만 접속한다.
- 결정: A
- 이유: 이미 등록된 mac이나 다른 경로로 구한 키로도 접속을 시험할 수 있고, 접속 규칙 추정이 틀려도 코드를 고치지 않고 여러 조합을 시험할 수 있다. B는 단순하지만 409로 막히거나 추정이 틀리면 코드를 고쳐야 한다. C는 키를 늘 다른 방법으로 구해야 해 등록 응답 자체를 관찰할 수 없다.
- 반영: spec.md C1, C2

### D003 접속 뒤에는 정해진 발행과 콘솔 입력 발행만 하고 자동 응답은 하지 않는다
- 단계: spec
- 질문: 다원 브로커에 접속한 뒤 가짜 장비가 무엇을 보내고, 받은 메시지에 응답할지 정해야 했다. 보내고 받은 원문은 모든 선택지에서 기록한다.
- 선택지:
  - A. 정해진 발행 + 콘솔 입력: 접속 직후 `rg`·`tisyn`을 보내고, 주기적으로 `tisyn`·상태 보고(`n`)를 보낸다(내용·주기는 설정). 실행 중 콘솔에 토픽·페이로드를 입력해 임의 메시지를 보낼 수 있다. 자동 응답은 하지 않는다.
  - B. 정해진 발행만: 설정에 적은 메시지를 정해진 시점에만 보낸다.
  - C. 간단한 자동 응답까지: A에 더해 다원이 보낸 `w`·`r`에 고정 형식으로 응답한다.
- 결정: A
- 이유: 받은 메시지를 보고 바로 다른 메시지를 시험할 수 있어 형식을 찾는 데 맞다. B는 단순하지만 시험할 때마다 다시 실행해야 한다. C는 앱에 온라인으로 보일 가능성은 있지만 응답 형식 자체가 미확인이라 추측으로 만든 응답이 기록을 흐릴 수 있다.
- 반영: spec.md C6, C7, C8, 범위 밖

### D004 펌웨어 버전 기본값 1.01.36을 두고 실장비 관찰 출처를 적는다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. C1 펌웨어 버전 기본값 `1.01.36`(C6 `rg`의 `/3/0/3`)이 근거 문서에 없다는 의견이다. `docs/reference/b540-mqtt-topic.md` 3절은 슬롯 A `1.01.30`, 슬롯 B `1.01.34`, 설정 섹터 `1.01.34`다. 값은 2026-11-19 서버 로그에서 B540 실장비가 보낸 `rg` 값이지만 spec에 출처가 없어 근거 문서와 모순처럼 읽혔다.
- 선택지:
  - A. 출처 추가: 기본값 `1.01.36`을 두고 "무엇을, 왜"에 실장비 관찰 출처(정적 덤프는 `1.01.34`)를 더한다.
  - B. `1.01.34`로 바꿈: 기본값을 근거 문서의 슬롯 B 값으로 바꾼다.
- 결정: A
- 이유: 실제 장비가 지금 다원에 보내는 값이라 다원이 받는 형식에 더 가깝다. B는 근거 문서와 맞지만 실장비보다 오래된 버전이라 다원 반응이 실장비와 달라질 여지가 생긴다.
- 반영: spec.md 무엇을·왜

### D005 verify 확인 서버 주소는 설정 오류로 검사하고, 치환표 밖 키는 판정 "계산 불가"로 기록하고 계속한다
- 단계: spec
- 질문: spec 검토 1회차 지적 2. device-register R3 계산식은 치환표 안 위치를 쓰므로 표 밖 문자가 있으면 계산할 수 없는데, C2는 키를 "비어 있지 않은 문자열"로만 보고 그때 처리가 없었다. C1의 `verify` 확인 서버 주소도 형식 검사 대상인지 정해지지 않았다. `DeviceVerify.Compute`는 표 밖 문자에 예외를 던진다.
- 선택지:
  - A. 계산 불가 기록: C1에 서버 주소가 치환표 문자로만 이뤄지지 않으면 설정 오류를 더하고, C2에 키가 표 밖 문자를 담으면 판정을 "계산 불가"로 기록·콘솔에 남기고 계속한다를 더한다.
  - B. 등록 실패로 종료: C1 설정 오류는 같고, C2 성공 조건을 치환표 문자열로 좁혀 아니면 MQTT 접속 없이 종료한다(dawon-relay R2와 같게).
- 결정: A
- 이유: 목적이 관찰이라 키가 예상 밖 형식이어도 그 키로 접속되는지 시험하는 편이 정보가 많다. B는 중계 모드와 기준이 같아지지만 그 시험 기회를 잃는다.
- 반영: spec.md C1, C2

### D006 SUBACK 무응답은 10초 뒤 종료하고, 실패 값이면 기록하고 발행을 계속한다
- 단계: spec
- 질문: spec 검토 1회차 지적 3. C5·C6에 SUBACK이 실패 값(0x80)일 때와 오지 않을 때의 동작이 없었다(다른 단계는 10초 제한). 구독 허용 여부는 근거 문서에서도 추정이다.
- 선택지:
  - A. 실패면 계속: 10초 안에 SUBACK이 없으면 기록하고 0이 아닌 코드로 끝내고, 실패 값이면 기록·콘솔에 쓴 뒤 C6으로 넘어간다.
  - B. 둘 다 종료: 무응답과 실패 값 모두 기록하고 0이 아닌 코드로 끝낸다.
- 결정: A
- 이유: 다원이 구독은 막아도 발행은 받을 수 있고 그 반응도 관찰 대상이다. B는 단순하지만 구독 거부 때 발행에 대한 다원 반응을 볼 수 없다.
- 반영: spec.md C5

### D007 C13은 등록·접속이 거부되어도 그 단계까지의 결과를 적으면 완료로 본다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. C13은 `rg`·`tisyn` 발행과 수신 확인을 적었지만 CONNACK 거부면 불가능해, 거부 결과만 적어도 완료인지 판정할 수 없었다. 1차 중계 시도에서 이미 409와 CONNACK 4가 나왔다.
- 선택지:
  - A. 거부도 완료: 거부되면 그 단계까지의 결과(응답 상태, CONNACK 코드)를 적으면 완료로 보고, 발행·수신 항목은 접속에 성공했을 때만 적는다.
  - B. 접속 성공까지: 접속에 성공해 발행·수신까지 확인해야 완료로 본다.
- 결정: A
- 이유: 다원 계정 상태는 이 작업이 통제할 수 없다. B는 목적에 더 맞지만 다원이 계속 거부하면 코드가 맞아도 작업이 끝나지 않는다.
- 반영: spec.md C13

### D008 상태 보고는 B540 관찰 출처를 적고, 정해진 rg·tisyn 뒤 바로 한 번 보낸 뒤 주기마다 보낸다
- 단계: spec
- 질문: spec 검토 1회차 지적 6. (가) `n`·`notify/json`·`ti` `""` 관찰은 근거 문서 5절의 M130-W 관찰이고 3절은 B540 보고를 미확인으로 두는데, spec은 기본 모델 B540에서 관찰로 들었다(실제로는 2026-11-19 서버 로그에서 B540도 같은 형식으로 보냈지만 출처가 없었다). (나) "접속 뒤 주기마다"의 첫 송신 시점이 모호해 테스트 기대값을 정할 수 없었다.
- 선택지:
  - A. 출처 + 즉시 첫 송신: B540 관찰 출처를 더하고, 주기가 0보다 크면 정해진 `rg`·`tisyn` 뒤 바로 한 번 보내고 그 뒤 주기마다 보낸다.
  - B. 출처 + 한 주기 뒤: 출처는 같고, 첫 송신은 구독 결과를 받은 때부터 한 주기 뒤로 한다.
- 결정: A
- 이유: 실장비도 접속 직후(`rg` 뒤 1~2초 안) 보고를 보냈다. B는 실장비와 달라 다원이 장치를 온라인으로 보는 시점이 늦어질 수 있다.
- 반영: spec.md 무엇을·왜, C6

### D009 C13에서 등록이 거부되면 줄 다원 키가 있을 때만 그 키로 다시 실행해 접속 결과까지 적는다
- 단계: spec
- 질문: D007 보완. spec 검토 2회차 지적 1. C13 첫 문장은 접속 시도를 요구하는데, D007로 더한 문장은 "등록·접속이 거부되면 그 단계까지의 결과를 적으면 완료"라고 했다. 등록이 거부되면 C2에 따라 MQTT에 접속하지 않아 CONNACK이 없으므로, 등록 상태만 적으면 완료인지 설정 키로 다시 실행해 접속까지 해야 완료인지 판정할 수 없었다. 이미 등록된 mac은 409로 거절되는 것을 관찰해 가장 먼저 부딪힐 상황이다.
- 선택지:
  - A. 키 있으면 재실행: 등록이 거부되면 응답 상태를 적고, 설정으로 줄 다원 키가 있으면 그 키로 다시 실행해 접속 결과까지 적는다. 줄 키가 없으면 등록 결과만으로 완료다. 접속이 거부되면 CONNACK 코드까지 적으면 완료다.
  - B. 등록 거부도 완료: 등록이 거부되면 등록 응답 상태만 적어도 완료로 분명히 적는다.
  - C. 임의 키라도 접속: 등록이 거부되면 설정 키(올바른 키가 없으면 임의 키)로 다시 실행해 CONNACK 결과까지 적어야 완료다.
- 결정: A
- 이유: 쓸 수 있는 키가 있으면 끝까지 시험하고, 없을 때 작업이 막히지 않는다. B는 쓸 키가 있어도 접속 시험을 건너뛸 수 있다. C는 임의 키로 받는 CONNACK 4가 1차 중계 기록에서 이미 본 결과라 새 정보가 없다.
- 반영: spec.md C13

### D010 FOTA를 범위에 넣고, 받은 메시지의 URL로 자동으로 받으며 콘솔 명령으로도 받는다
- 단계: spec
- 질문: 사용자가 spec 확인 전에 FOTA도 대상으로 하자고 했다. 다원이 내려주는 펌웨어를 받으면 분석에 도움이 된다는 이유다. 근거 문서 `docs/reference/b540-fota.md`에 따르면 서버가 MQTT 쓰기로 URL을 보내고 장치가 `GET {URL}/version`과 이미지 `GET`을 하지만, 다원의 FOTA URL과 이미지 경로 규칙은 미확인이다. 다원이 보낸 URL을 어떻게 받을지 정해야 했다. 받은 파일은 저장만 하고 실행하지 않으며, 다원 서버 경로를 추측해 요청하는 것은 어느 선택지에도 넣지 않았다.
- 선택지:
  - A. 자동 + 콘솔 명령: 받은 메시지의 값에 http(s) URL이 있으면 장치처럼 `GET {URL}/version`과 이미지를 받아 저장한다(설정으로 끌 수 있음). 이미지 경로 규칙이 미확인이라 콘솔에 URL을 직접 주어 받는 명령도 둔다.
  - B. 콘솔 명령만: 자동으로 받지 않고, 기록에서 URL을 본 뒤 콘솔 명령으로 받는다.
  - C. 기록만: 받기는 넣지 않고 FOTA 메시지 기록에서 멈춘다.
- 결정: A
- 이유: URL이 짧은 시간만 유효해도 놓치지 않고, 자동 규칙이 맞지 않으면 명령으로 경로를 바꿔 받을 수 있다. B는 단순하지만 URL이 짧게만 유효하면 놓칠 수 있다. C는 펌웨어를 얻는다는 목적을 채우지 못한다.
- 반영: spec.md 무엇을·왜, 범위 밖, C1, C7, C9, C12, C14, C15, C16

### D011 실제 확인에서 rg에 낮은 펌웨어 버전을 보내고 다원 앱 업데이트도 눌러 FOTA를 유도한다
- 단계: spec
- 질문: 다원이 FOTA 메시지를 보내야 받을 수 있으므로, 실제 다원 확인(C13)에서 업데이트를 어떻게 유도할지 정해야 했다. 어느 쪽이든 다원이 업데이트를 보내지 않으면 그 결과를 적는 것으로 완료한다.
- 선택지:
  - A. 낮은 버전 + 앱 업데이트: `rg`에 낮은 펌웨어 버전(예: `1.01.30`)을 보내 보고, 접속에 성공하면 사용자가 다원 앱에서 펌웨어 업데이트도 눌러 본다.
  - B. 낮은 버전만: `rg`의 낮은 버전만 시험하고 앱 조작은 하지 않는다.
  - C. 유도하지 않음: 기본 버전으로 실행해 다원이 스스로 FOTA를 보내는지만 본다.
- 결정: A
- 이유: 다원이 업데이트를 내려보내는 두 경로(버전 비교, 사용자 요청)를 모두 시험해 받을 가능성이 가장 높다. B는 앱 요청 경로를 시험하지 않는다. C는 다원이 스스로 보낼 이유가 적어 받을 가능성이 낮다.

### D012 FOTA 자동 받기의 두 번째 요청을 "URL 그대로 요청"으로 두고 이미지라고 단정하지 않는다
- 단계: spec
- 질문: spec 검토 4회차 지적 1. C14의 이미지 요청 `GET {URL}`이 근거 문서(`docs/reference/b540-fota.md` 3절: 버전 `GET %s/version`, 이미지 `GET %s%s` = 경로 + 이미지 이름)와 맞지 않는다는 의견이다. URL은 기준 경로일 수 있고, spec은 이미지 경로 규칙이 미확인이라면서 C14에서 규칙을 확정했다. 다만 같은 문서 2절은 `LFota_Url`을 "이미지 URL 또는 경로"로 적어 URL이 이미지 자체일 가능성도 있다.
- 선택지:
  - A. URL 그대로 요청: 두 번째 요청을 "URL 요청 `GET {URL}`(URL이 이미지 자체일 수도 있어 그대로 받아 둔다)"으로 바꾸고 "장치처럼 이미지를 받는다"는 단정을 빼며, 이미지 이름 규칙은 미확인이라 기록을 보고 C15 단일 GET으로 받는다고 적는다.
  - B. 자동은 버전만: 자동 받기는 버전 요청 하나로 줄이고 URL 자체 요청은 콘솔 명령으로만 한다.
  - C. SDK 이름까지 자동: `user1.bin`·`user2.bin`을 붙인 요청도 자동으로 보낸다.
- 결정: A
- 이유: URL이 이미지 자체일 수도 있어 바로 받아 두는 값이 있고, 근거와 다른 단정만 없앤다. B는 URL이 이미지 자체이면서 짧게만 유효하면 놓친다. C는 SDK 관례를 빌린 경로 추측 요청이라 범위 밖 원칙과 부딪히고, 덤프에서 그 파일 이름도 찾지 못했다.
- 반영: spec.md 무엇을·왜, C9, C13, C14, C15

### D021 FOTA 헤더 순서는 만든 요청 메시지의 단위 테스트로 보고, 가짜 서버로는 헤더가 있는지와 값만 본다

### D022 C8 "응답하지 않음"은 수신 기록이 생긴 뒤 1초 동안 클라이언트 발행이 없는지로 본다
