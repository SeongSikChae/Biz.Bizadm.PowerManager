# MQTT 브로커 패킷 분할 끄기

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #25

## 무엇을, 왜

#21에서 서버가 시간 동기 요청(`tisyn`)에 응답을 보내도 실장비(M130-W 3대, B540)가 동기되지 않고, 진단용 읽기(`r`) 요청에도 반응하지 않았다. #23에서 더한 로그(mqtt-broker R10·R12)로 장비가 서버 → 장치 토픽을 구독하고 있고 브로커가 응답을 장비 클라이언트 큐에 넣는 것까지 확인했다.

2026-11-21 TLS 포트 패킷 캡처에서, 서버는 `tisyn`을 받을 때마다 응답 PUBLISH 하나를 TLS 레코드 두 개로 나눠 보냈고, 장비는 TCP 수준에서 받기만 하고 아무 반응이 없었다. 내장 브로커가 쓰는 MQTTnet은 페이로드가 있는 패킷을 기본으로 머리(고정 헤더·토픽)와 페이로드로 나눠 두 번 쓰며(`MqttChannelAdapter`, 엔드포인트 옵션 `AllowPacketFragmentation` 기본 `true`), TLS에서는 쓰기마다 레코드가 하나씩 생긴다. 장비 펌웨어의 MQTT 라이브러리(B540은 근거 문서 `docs/reference/b540-mqtt-topic.md`에서 esp_mqtt(tuanpmt) 계열로 추정, M130-W 2.01.58은 펌웨어 분석에서 MQTT 로그 문구가 B540과 같음을 관찰했으며 근거 문서 반영은 #21 후속)는 수신 콜백 하나를 MQTT 패킷 하나로 처리하고 여러 콜백에 걸친 패킷을 다시 합치지 않는 것으로 보인다. 그러면 첫 조각은 데이터가 빈 메시지로, 둘째 조각은 알 수 없는 패킷으로 처리되어 응답이 버려진다. 이것이 무반응의 유력한 원인이다(재조립하지 않는다는 점은 라이브러리 원본 기준 추정이며 펌웨어에서 직접 확인하지는 않았다).

MQTTnet 설명은 나뉜 패킷을 지원하지 않는 클라이언트가 접속하면 분할을 끄도록 하며, 그런 클라이언트는 연결을 닫는다고 적는다. 관찰한 장비는 연결을 유지한 채 반응하지 않아 증상은 다르다. 브로커의 비TLS·TLS 엔드포인트 모두에서 패킷 분할을 꺼, 브로커가 클라이언트에 보내는 MQTT 패킷마다 한 번에 쓰게 한다. 메시지 내용·토픽·구독·전달 대상은 바꾸지 않는다.

장비가 이 변경 뒤 동기되는지는 #21의 실장비 판정(#21 C7)에서 따로 기록한다. 이 작업은 패킷이 한 번에 나가는지까지 확인한다.

## 완료 조건

- C1. TLS 엔드포인트(`MqttsPort`)에 접속해 서버 → 장치 토픽을 구독한 클라이언트가, 서버가 그 토픽에 주입한, MQTT 패킷 전체가 16384바이트(TLS 레코드 평문 최대 크기) 이하인 페이로드 있는 PUBLISH를 TLS 레코드 하나로 받는다(클라이언트가 받은 원시 바이트에서 그 PUBLISH를 담은 TLS 레코드가 하나다).
- C2. 브로커가 만드는 MQTT 서버 옵션에서 비TLS 엔드포인트와 TLS 엔드포인트 모두 패킷 분할 허용(`AllowPacketFragmentation`)이 `false`다.
- C3. 이 변경으로 다른 동작이 바뀌지 않는다. 기존 테스트가 모두 통과하고 빌드 경고가 없다.
- C4. 기준 spec `docs/features/mqtt-broker.md`에 C1·C2를 요구로 반영하고 이력에 이 작업을 남긴다.
- C5. 서버 로컬 배포 폴더에 배포한 뒤 TLS 포트 패킷 캡처에서, 캡처하는 동안 `tisyn`을 보낸 실장비(적어도 한 대)마다 그 응답이 모두 TLS 레코드 하나로 나가면 충족한다. 장비의 `tisyn` 재요청 간격은 판정하지 않고 관찰한 내용을 이 작업의 작업 문서에 적는다(동기 판정은 #21 C7).
