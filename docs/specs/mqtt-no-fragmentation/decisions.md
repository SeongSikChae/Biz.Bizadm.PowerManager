# MQTT 패킷 분할 끄기 결정

### D001 비TLS 엔드포인트의 분할 끔은 서버 옵션 값으로 확인한다
- 단계: spec
- 질문: spec 검토 1회차 지적 4. C2("C1과 같은 설정")는 무엇을 확인하면 충족되는지 정해져 있지 않고, 비TLS에서는 TCP가 조각을 합치거나 나눌 수 있어 수신 관찰로 쓰기 횟수를 판정하기 어렵다. 서버 옵션은 지금 `StartAsync` 안에서 만들어져 밖에서 확인할 수 없다.
- 선택지:
  - A. 옵션 값으로 확인: C2를 "브로커가 만드는 MQTT 서버 옵션에서 비TLS·TLS 엔드포인트 모두 `AllowPacketFragmentation`이 false"로 바꾸고 테스트에서 옵션 값을 확인한다.
  - B. 비TLS 수신 관찰: C2를 "비TLS 엔드포인트에서 원시 TCP 클라이언트가 PUBLISH 전체를 한 번의 수신으로 받는다"로 바꾼다.
  - 고치지 않음: C2를 그대로 둔다.
- 결정: A
- 이유: A는 결정적으로 확인할 수 있고, 비TLS 경로도 TLS와 같은 송신 코드(`MqttChannelAdapter`)를 쓰므로 설정이 맞으면 동작이 같다. B는 TCP가 두 쓰기를 한 세그먼트로 합칠 수 있어 분할이 켜진 상태에서도 테스트가 통과할 수 있다(결정적이지 않음). 고치지 않으면 코드를 읽는 것 말고는 완료를 판정할 수 없다.
- 반영: spec.md C2

### D002 C5는 캡처 중 tisyn을 보낸 실장비 모두의 응답을 확인한다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. C5가 "실장비의 `tisyn`에 대한 응답"이라고만 해 몇 대를 확인해야 충족인지 정해져 있지 않다. B540까지 요구하는 것으로 읽으면 B540이 캡처 시간 안에 `tisyn`을 보내지 않을 때(2026-11-21 캡처에서 B540으로 추정되는 연결은 PING만 주고받음) C5를 끝낼 수 없다.
- 선택지:
  - A. tisyn 보낸 장비 모두: "캡처하는 동안 `tisyn`을 보낸 실장비(적어도 한 대)마다 그 응답이 모두 TLS 레코드 하나로 나가면 충족"으로 고친다.
  - B. 한 대면 충족: "실장비 한 대의 응답이 TLS 레코드 하나로 나가면 충족"으로 고친다.
  - 고치지 않음: C5를 그대로 둔다.
- 결정: A
- 이유: A는 범위가 분명하고, 특정 장비가 `tisyn`을 보내지 않아도 끝낼 수 있으며, 캡처에 잡힌 장비는 빠짐없이 확인한다. B는 송신 코드가 같아 결과는 거의 같지만 잡힌 다른 장비의 응답을 보지 않아도 되어 확인이 약하다. 고치지 않으면 완료 판정이 읽는 사람마다 달라진다.
- 반영: spec.md C5

### D003 C1의 판정 문구를 원시 TLS 레코드 개수로 바꾼다
- 단계: spec
- 질문: 의도 변경(spec 확인 뒤, plan 작성 전 실험에서 발견). 확인받은 C1 괄호 "(TLS 스트림을 한 번 읽어 PUBLISH 패킷 전체를 얻는다)"는 판정 방법으로 맞지 않다. 실험(MQTTnet.Server 5.2.0.1603 TLS 1.2, 117바이트 PUBLISH)에서 분할이 켜져 있어도 `SslStream`이 이미 도착한 두 레코드를 합쳐 돌려주어 한 번 읽기로 전체를 얻는 경우가 섞여 나왔다(주입 전에 건 읽기 3회 중 50/117/117바이트, 300ms 뒤 읽기는 늘 117바이트). 반면 `SslStream` 아래의 원시 수신 바이트에서 TLS 레코드 머리를 세면 분할 켬 2개(74·91바이트), 끔 1개(141바이트)로 3회 모두 같았다. C1 본문("TLS 레코드 하나로 받는다")은 맞다.
- 선택지:
  - A. 괄호를 레코드 머리로 바꿈: 괄호를 "(클라이언트가 받은 원시 바이트에서 그 PUBLISH를 담은 TLS 레코드가 하나다)"로 바꾸고 spec 검토·확인을 다시 한다.
  - B. 괄호를 뺌: 괄호 설명만 지우고 판정 방법은 plan 검증 전략에 두며 spec 검토·확인을 다시 한다.
  - 고치지 않음: spec은 그대로 두고 plan 검증 전략에서만 레코드 머리로 판정한다.
- 결정: A
- 이유: A는 완료 조건의 판정 방법이 실제로 결정적인 방법과 같아지고, 분할을 다시 켜면 테스트가 반드시 실패한다. B는 본문만으로도 확인할 수 있지만 "레코드 하나"를 무엇으로 보는지가 spec에서 덜 분명하다. 고치지 않으면 확인받은 문서에 맞지 않는 판정 방법이 남아 plan·구현 후 검토에서 어긋남이 생긴다.
- 반영: spec.md C1
