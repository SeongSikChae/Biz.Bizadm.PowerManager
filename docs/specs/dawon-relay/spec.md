# 다원 서버 중계 모드

기능: dawon-relay(새 기능) / device-register(기준 spec docs/features/device-register.md) / mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #20

## 무엇을, 왜

장치와 다원 서버 사이에서 실제로 오가는 MQTT 메시지와 REST 응답의 형식 가운데 상당 부분이 아직 미확인이다.

- 서버 → 장치 MQTT 명령(`w`·`r`·`e`·`d`·`chg`·`reb`)의 실제 페이로드
- `tisyn`에 대한 서버 응답
- 등록 응답의 실패 형식, `device/connect` 응답 값

지금 근거는 B540 펌웨어 정적 분석(`docs/reference/b540-mqtt-topic.md`, `docs/reference/b540-rest-api.md`)과, 장치가 우리 서버에 보낸 메시지(M130-W)뿐이다. 다원 서버가 보내는 쪽은 관찰한 적이 없다. 장치와 다원 서버 사이 통신은 TLS라 패킷 캡처로는 내용을 볼 수 없다.

그래서 서버에 중계 모드를 둔다. 중계 모드에서 서버는 지금처럼 장치의 REST 요청과 MQTT 접속을 받는다. 동시에 같은 요청과 메시지를 다원 서버(`dwapi.dawonai.com:18443`, `dwmqtt.dawonai.com:8883`)로 전달하고, 다원 서버의 응답과 메시지를 장치에 돌려준다. 양방향 원문은 JSONL 파일로 기록한다. 장치는 다원 서버와 직접 통신할 때처럼 동작하므로, 다원 앱에서 장치를 조작하면 서버 → 장치 명령도 기록에 남는다.

장치에는 우리 서버 주소가 설정되어 있다(또는 장치 DNS가 다원 호스트 이름을 우리 서버로 가리킨다). 다원이 돌려준 `verify`는 다원 쪽 `server_addr`로 계산한 값이라, 장치에 설정된 `server_addr`와 다르면 장치가 키를 버린다. `verify` 계산식은 이미 확인했다(device-register R3). 그래서 다원이 준 `mqtt_key`로 서버 설정의 `DeviceMqttServerAddr` 기준 `verify`를 다시 계산해 돌려준다. 다원이 준 `mqtt_key`는 DB에 저장한다. 그 장치가 MQTT로 접속하면 서버는 같은 ClientId·사용자명·비밀번호로 다원 브로커에 대신 접속한다.

중계 모드는 설정 하나로 모든 장치에 대해 켜거나 끈다. 기본값은 꺼짐이며, 꺼져 있으면 지금 동작(로컬 키 발급, 로컬 브로커)과 같다. 중계 중 다원 서버에 연결하지 못하면 로컬 처리로 대신하지 않고 장치에도 실패로 응답한다. 실제 다원 서버 장애와 같은 상황을 만들어 기록이 왜곡되지 않게 하기 위해서다.

범위 밖:

- 기록 내용의 분석과 근거 문서(`docs/reference`) 반영(기록을 모은 뒤 따로 한다)
- FOTA(`/fota`)와 위 두 endpoint 밖의 REST 요청 중계
- 장치별(mac별) 중계 대상 선택
- 관리 화면에서 기록 조회
- 서버가 직접 장치에 명령을 발행하는 기능(`MqttDeviceCommandPublisher`)

## 기준 spec에 미치는 변경

중계 모드가 켜져 있을 때만 아래 기준 spec 요구와 다르게 동작한다. 꺼져 있으면 기준 spec 그대로다.

- device-register R1: 올바른 요청이라도 등록 응답의 상태 코드·`Content-Type`·본문은 다원 응답을 따르거나, 다원에 연결하지 못하면 502다(C2·C3).
- device-register R2: 새로 발급하지 않고 다원 키를 쓴다(C2).
- device-register R6: 이미 저장된 mac이라도 다원 키로 바꾼다(C2). "같은 mac의 첫 등록이 동시에 들어오면 저장된 키 하나로 응답한다"는 적용하지 않는다. 응답은 요청마다 그 요청이 받은 다원 본문을 따르고, 저장되는 키는 마지막에 저장된 다원 키다.
- device-register R8: connect는 로컬 등록 여부 대신 다원 응답을 돌려준다(C4).
- mqtt-broker R1: 다원 접속 결과에 따라 장치 접속을 거부할 수 있다(C5).
- mqtt-broker R9: 접속 관찰 로그는 그대로 남긴다. 다만 R9의 "접속은 거부하지 않는다"는 C5가 대신한다.

## 완료 조건

### 설정

- C1. 중계 설정은 다음과 같다. 켜짐 여부의 기본값은 꺼짐이다.
  - 다원 REST 서버 호스트·포트(기본 `dwapi.dawonai.com`·`18443`)
  - 다원 MQTT 브로커 호스트·포트(기본 `dwmqtt.dawonai.com`·`8883`)
  - 기록 폴더(`ContentRootPath` 기준 상대 경로 또는 절대 경로, 기본 `dawon-relay`)
  - 다원 서버 TLS 인증서 검증을 끄는 선택(기본은 검증함)

  꺼져 있으면 REST·MQTT 동작은 지금 기준 spec(device-register R1~R8, mqtt-broker R1~R9)과 같고 기록 파일을 만들지 않는다.

### REST 중계(켜짐)

- C2. `POST /api/v1/devices/register/create`는 장치가 보낸 본문을 바꾸지 않고 다원 REST 서버(HTTPS, 같은 경로, `Content-Type: application/json`, `X-HIT-Version: 1.0`)로 보낸다.
  - 성공 조건: 다원이 200으로 응답하고, 본문이 JSON 객체이며, 최상위 `mqtt_key`가 문자열이고, 그 값이 비어 있지 않으며 device-register R3 치환표 문자로만 이뤄진다. `verify`가 있는지는 성공 조건과 관계없다.
  - 성공하면 다원의 `mqtt_key`를 그 mac의 등록 키로 저장한다. 처음이면 새로 만들고, 이미 있으면 키를 바꾸며, 마지막 요청 시각과 user_id·model_id·company는 device-register R5·R6 규칙대로 다룬다.
  - 저장한 뒤 장치에 200과 다원의 `Content-Type`, 다원 본문을 돌려준다. 본문은 다원 응답의 원문 바이트(키 순서·공백·이스케이프 형태 포함)를 그대로 쓴다. 최상위 `verify`가 문자열이면 그 값 자리만 다시 계산한 값으로 바꾸고, 이 값은 이스케이프하지 않는다(값은 모두 치환표 문자). `verify`가 없거나 문자열이 아니면 본문을 그대로 두고 넣거나 바꾸지 않는다. 다시 계산한 값은 device-register R3 계산식에 `DeviceMqttServerAddr`, 요청 mac, 다원 키를 넣은 값이다.
- C3. 실패 처리.
  - 등록 요청의 mac이 올바르지 않으면 다원으로 보내지 않고 device-register R4대로 400을 반환한다.
  - 다원이 응답했지만 C2 성공 조건을 채우지 못하면, 다원의 상태 코드·`Content-Type`·본문을 그대로 장치에 돌려주고 DB를 바꾸지 않는다.
  - 다원에 연결하지 못하거나 시간 초과면 502를 반환하고 DB를 바꾸지 않는다.
- C4. `GET /api/v1/device/connect/{deviceKey}`는 다원 REST 서버의 같은 경로로 보내고, 다원의 상태 코드·`Content-Type`·본문을 그대로 장치에 돌려준다. 다원에 연결하지 못하거나 시간 초과면 502다.

### MQTT 중계(켜짐)

- C5. 브로커에 접속하는 모든 클라이언트를 중계한다. ClientId 형식은 따지지 않는다.
  - 클라이언트가 접속하면, 서버는 그 클라이언트의 ClientId·사용자명·비밀번호·keepalive·clean session과 Will(토픽·페이로드·QoS·retain)을 그대로 써서 MQTT 3.1(`MQIsdp`)로 다원 브로커에 TLS 접속한다.
  - 다원이 접속을 받아들인 뒤에만 클라이언트 접속을 받아들인다.
  - 다원이 거부하면 다원의 CONNACK 반환 코드 그대로 클라이언트 접속을 거부한다.
  - 다원에 연결하지 못하거나 시간 초과면 클라이언트 접속을 서버 사용 불가(반환 코드 3)로 거부한다.
- C6. 구독과 구독 해제를 중계한다.
  - 클라이언트가 구독하면 같은 토픽 필터·QoS로 다원에도 구독하고, 다원 SUBACK을 기다려 필터마다 다원이 허용한 QoS를 그대로 클라이언트에 SUBACK으로 돌려준다. 다원 구독이 연결 오류나 시간 초과로 실패하면 클라이언트 접속을 끊는다.
  - 구독을 해제하면 같은 토픽 필터로 다원에서도 해제한다.
  - 다원에서 받은 메시지는 그 클라이언트의 접속에만 같은 토픽·페이로드·QoS·retain으로 전달하며, 다시 다원으로 보내지 않는다.
- C7. 클라이언트가 발행한 메시지는 같은 토픽·페이로드·QoS·retain으로 다원에 발행한다. 장치 메시지의 로컬 처리(mqtt-broker R2~R8)와 접속 관찰 로그(mqtt-broker R9)도 지금처럼 한다.
- C8. 접속 종료를 양쪽에 맞춘다.
  - 클라이언트가 정상 종료(DISCONNECT)하면 다원 접속도 정상 종료한다.
  - 클라이언트 접속이 비정상으로 끊기면 다원 접속을 DISCONNECT 없이 끊어, 다원 쪽에서 Will이 발행되게 한다. 이때 로컬 브로커가 발행하는 그 클라이언트의 Will은 다원으로 따로 보내지 않는다.
  - 다원 접속이 끊기면 클라이언트 접속을 끊는다.

### 기록(켜짐)

- C9. 중계한 모든 주고받음을 기록 폴더의 UTC 날짜별 파일(`dawon-relay-yyyyMMdd.jsonl`)에 한 줄에 JSON 하나로 덧붙인다.
  - 공통 필드: 시각(UTC, ISO 8601), 채널(`rest`·`mqtt`), 방향(`device-to-dawon`·`dawon-to-device`), 종류
  - REST는 한 번의 중계를 항목 둘로 남긴다.
    - 요청 항목(`device-to-dawon`): 메서드·경로·요청 본문
    - 응답 항목(`dawon-to-device`): 메서드·경로·다원 상태 코드·다원 응답 본문
    - 장치에 실제로 돌려준 응답은 다원 응답과 `verify` 값만 다르므로 따로 기록하지 않는다.
  - MQTT 항목은 모두 ClientId를 담는다. 종류별로 더 담는 값은 다음과 같다.
    - 접속(`device-to-dawon`): 사용자명, 비밀번호 유무, keepalive, clean session, Will(토픽·페이로드·QoS·retain, 없으면 없음)
    - 접속 결과(`dawon-to-device`): CONNACK 반환 코드
    - 구독(`device-to-dawon`): 토픽 필터와 QoS 목록
    - 구독 결과(`dawon-to-device`): 다원 SUBACK의 필터별 값(받은 그대로)
    - 구독 해제(`device-to-dawon`): 토픽 필터 목록
    - 발행(양방향): 토픽, QoS, retain, 페이로드
    - 종료(양방향): 정상 종료인지 비정상 끊김인지
  - 연결 실패와 시간 초과도 별도 종류의 항목 하나로 남긴다(대상과 오류 내용).
- C10. 본문과 페이로드는 자르지 않고 UTF-8 문자열로 기록한다. 올바른 UTF-8이 아니면 Base64로 기록하고 그 사실을 같은 항목에 표시한다. 여러 요청이 동시에 기록해도 줄이 섞이거나 깨지지 않는다.
- C11. 기록과 서버 로그에 비밀 값이 남지 않는다.
  - 기록하는 다원 REST 응답 본문(등록·connect 모두)이 JSON 객체이면 최상위 `mqtt_key`·`verify` 값을 `***`로 가린다.
  - MQTT 접속 비밀번호는 값 대신 있는지 여부만 남긴다.
  - device-register R7(서버 로그에 `mqtt_key`·`verify`를 남기지 않음)은 중계 모드에서도 지킨다.

### 확인

- C12. C1~C11을 확인하는 자동 테스트가 있고 통과한다. 이 테스트는 실제 다원 서버 대신 테스트 안의 가짜 REST 서버와 가짜 MQTT 브로커를 쓴다.
- C13. 실장비 확인(수동). 중계 모드를 켠 서버에 B540 실장비 1을 등록시키면 다음이 일어난다.
  - 장치가 다원 키로 등록되고 서버를 거쳐 다원 브로커에 접속한다.
  - 다원 앱에서 켜기·끄기를 한 번 하면 기록 파일에 등록 요청·응답, MQTT 접속, 장치 → 다원 발행, 다원 → 장치 발행이 남는다.

  실행한 내용과 기록에 남은 항목 종류를 작업 문서에 적는다. 기록 파일과 실제 값은 저장소에 넣지 않는다.
