# tisyn 시간 동기 응답

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #21

## 무엇을, 왜

장치는 MQTT로 시간 동기 요청(`msg.o` `tisyn`, 토픽 `{prefix}.v1/{장치 키}/iot-server/timesync/json`)을 보낸다. 지금 서버는 이 요청을 로그로만 남기고(mqtt-broker R5) 응답하지 않는다. 그래서 장치가 동기될 때까지 간격을 늘려 가며 `tisyn`을 다시 보낸다. 2026-11-20 서버 로그에서 M130-W 3대가 12:56:24부터 2·4·8·16초 간격으로 다시 보내는 것을 관찰했다(요청 `sid`는 `"0"`, 요소 없음).

근거 문서 `docs/reference/b540-mqtt-topic.md` 「시간 동기」 절(B540 펌웨어 정적 디컴파일)에 따르면 다음과 같다.

- 장치는 서버 → 장치 메시지의 `w`(리소스 쓰기)로 `/99/0/1`에 쓴 값을 시각으로 저장하고 동기 완료로 표시한다(관찰). 동기 완료 표시를 다시 0으로 되돌리는 곳은 찾지 못했다.
- 동기 완료 뒤에도 `tisyn`을 멈추지 않고 7200틱마다 보낸다(관찰). 동기 전에는 간격을 두 배씩 늘리다 300틱 간격을 유지하며, 상수와 분기에서 나오는 수열이 두 가지다(관찰). 부팅 뒤 첫 틱에 이미 연결돼 있으면 2·4·…·256·512 다음 300이고, 연결되지 않은 틱을 지나면 연결 뒤 30틱 만에 첫 송신을 하고 60·120·240·480 다음 300이다. 실제로 어느 수열이 나타나는지는 미확인이다.
- 틱 단위는 근거 문서에서 미확인이다. 위 M130-W 관찰 간격(2·4·8·16초)이 2·4·8·16틱 수열과 맞으므로, 이 작업은 1틱을 약 1초로 본다(추정). 그러면 동기 전 재요청 간격은 가장 길어도 약 512초다.
- 장치는 `tisyn`을 보내는 순간 다음 송신 시점을 정한다(동기 전이면 `7200 − 간격`, 동기 뒤면 0으로 카운터를 둠, 관찰). `/99/0/1` 쓰기는 동기 표시만 바꾸고 카운터는 건드리지 않는다(카운터를 0으로 되돌리는 것은 `/99/0/0`뿐, 관찰). 그래서 동기 전에 보낸 요청에 응답해도, 장치는 남은 간격(최대 약 512초)이 지나면 `tisyn`을 한 번 더 보내고, 그다음 송신부터 7200틱(약 2시간) 간격이 된다(추정).
- 값은 UTC 기준 Unix epoch 초의 10진수 문자열로 추정한다. 장치가 +32400초(KST)를 스스로 더한다(관찰, 해석은 추정).
- 응답 메시지 형식 `{"sid":"0","msg":{"o":"w","e":[{"n":"/99/0/1","sv":"<값>"}]}}`은 3절 메시지 형식에 따른 추정이다. 값 키 `sv`와 `sid` 값은 수신 파서에서 확인하지 못했다(4절 미확인 항목). 이 작업은 응답 `sid`에 요청의 `sid`를 그대로 쓴다(D001). 요청과 응답의 짝을 맞추는 방식이고, 관찰한 요청 `sid`가 `"0"`이라 근거 문서의 예와 같은 값이 된다.
- 근거는 B540 분석이고, 응답을 받을 실장비는 M130-W다. 같은 제조사의 같은 메시지 체계(5절)지만, M130-W 펌웨어의 수신 처리는 분석하지 않았다.

이번 작업은 서버가 `tisyn` 요청마다 그 장치의 서버 → 장치 토픽으로 현재 시각을 `w` `/99/0/1`로 보낸다. 이로써 장치가 시간을 맞춰 재요청 간격이 동기 뒤 간격으로 바뀌게 하고, 위 추정을 실장비로 확인한다. 시각 값은 보낸 순간에만 맞으므로 retained 메시지로 남기지 않는다. 남기면 장치가 다시 접속해 구독할 때 지난 시각으로 동기 완료가 된다.

중계 모드(dawon-relay)가 켜져 있으면 장치의 `tisyn`은 다원으로도 중계되고, 다원의 응답이 장치에 주입된다. 이때 서버도 응답하면 장치가 응답을 두 번 받으므로, 중계 모드에서는 서버가 응답하지 않는다.

기준 spec mqtt-broker에 미치는 변경: R5는 "기본 핸들러는 받은 내용을 Information 로그로만 남기고, 서버 → 장치 발행(`MqttDeviceCommandPublisher`)은 `NotImplementedException`"이다. 이번 작업 뒤 R5는 다음 내용을 직접 담는다(이 작업의 C번호를 가리키지 않음). 기본 핸들러는 받은 내용의 Information 로그를 그대로 남긴다. 중계 모드가 꺼져 있으면 `tisyn`마다 그 장치의 서버 → 장치 토픽에 retain 없이 `w` `/99/0/1`(요청 `sid`, 없으면 `"0"`, 값은 서버 시각의 UTC Unix epoch 초 10진수 문자열)을 보내고 응답 로그를 남긴다. 중계 모드가 켜져 있으면 `tisyn`에 응답하지 않는다. 기준 spec 머리말의 "지금 핸들러는 로그만 남기고" 문장도 이에 맞춘다. 서버 → 장치 명령 발행(`MqttDeviceCommandPublisher`의 `w`·`chg`·`reb`)은 그대로 `NotImplementedException`이다(D002). `tisyn` 응답은 이 명령 발행과 별개인 시간 동기 응답으로 정하며, 일반 `w` 명령 발행의 동작은 이번 작업에서 정하지 않는다.

하지 않는 것:

- 서버 → 장치 명령 발행(`MqttDeviceCommandPublisher`의 `w`·`chg`·`reb`). 지금처럼 구현하지 않은 상태로 둔다(D002).
- 시간 동기 뒤 장치의 보고 동작(`MqttTypeWrite` 뒤 보고)에 대한 처리.
- 장치별 시간대 설정(장치가 KST 보정을 스스로 한다는 추정을 따른다).

## 완료 조건

- C1. 중계 모드가 꺼져 있을 때 장치 → 서버 메시지가 `msg.o` `tisyn`으로 분배되면(mqtt-broker R4), 서버는 그 요청 토픽의 접두·장치 키로 만든 서버 → 장치 토픽(`{prefix}.v1/iot-server/{장치 키}`, mqtt-broker R2)에 retain 표시 없이 메시지 하나를 발행한다. 그 장치 키를 와일드카드(`{prefix}.v1/iot-server/{장치 키}/#`)로 구독한 클라이언트가 그 메시지를 받고, 발행 뒤 새로 구독한 클라이언트는 retained 메시지로 그 메시지를 받지 않는다.
- C2. C1의 메시지 페이로드는 `{"sid":<요청 sid>,"msg":{"o":"w","e":[{"n":"/99/0/1","sv":"<값>"}]}}` 형태의 JSON이다. `sid`는 요청의 `sid` 문자열을 그대로 쓰고, 요청에 `sid`가 없으면 `"0"`을 쓴다(D001). `<값>`은 응답을 만들 때 서버 시각의 UTC Unix epoch 초(소수점 아래 버림)를 10진수 문자열로 쓴 것이다.
- C3. 중계 모드가 켜져 있으면 C1의 메시지를 발행하지 않는다. `tisyn`을 받은 내용의 Information 로그(지금 `Device message "tisyn": ...` 로그)는 중계 모드와 상관없이 남긴다.
- C4. C1의 응답을 발행하면 Information 로그 항목 하나에 장치 키, 토픽, `sid`, 보낸 값을 남긴다. 발행이 실패하면 Error 로그를 남기고, 예외는 브로커로 번지지 않는다(mqtt-broker R4).
- C5. 기준 spec `docs/features/mqtt-broker.md`의 R5가 위 「기준 spec mqtt-broker에 미치는 변경」대로 바뀐다. 바뀐 R5는 응답 토픽·형식·retain 없음·중계 모드에서 응답하지 않음을 이 작업의 C번호를 가리키지 않고 직접 적는다. 머리말의 핸들러 설명이 바뀐 R5와 어긋나지 않고, 이력 표에 이번 작업 한 줄이 있다.
- C6. 자동 테스트: C1~C4를 확인하는 테스트가 있고, `dotnet build`가 경고 없이 끝나며 `dotnet test` 전체가 실패 없이 통과한다.
- C7. 실장비 확인: 서버 로컬 배포 폴더의 `config.yaml`에서 `DawonRelay.Enabled`가 꺼진 상태로 배포하고 서버를 다시 시작한다. 그 뒤 M130-W 장비가 `tisyn`을 보내면 서버 로그에 C4의 응답 로그가 남는지 본다. 응답 로그가 남은 장비마다 그 장비의 첫 응답 로그 시각부터 60분을 판정 구간으로 두고, 그 구간의 `tisyn` 시각을 서버 로그로 모아 다음 가운데 하나로 판정한다. 간격은 구간 시작(첫 응답 로그 시각)부터 구간 안 첫 `tisyn`까지, 구간 안의 이웃한 두 `tisyn` 사이, 마지막 `tisyn`부터 구간 끝까지를 보고, 구간 안에 `tisyn`이 없으면 구간 전체(60분)를 간격 하나로 본다(응답 직후 한 번 더 오는 `tisyn`은 동기에 성공해도 생기므로 그것만으로 판정하지 않는다). 구간 안에 그 장비의 접속이 끊긴 기록이 있으면 그 구간은 판정하지 않고, 다음 응답 로그부터 다시 잰다. 끊긴 기록은 다음 세 로그 가운데 하나이며, 장비는 ClientId(`DAWONDNS-{mac}`)나 장치 키(`DAWONDNS-{모델}-{mac}`) 끝의 MAC 12자리(대소문자 무관)로 맞춘다.
  - 그 장비 ClientId의 접속 로그 `MQTT client connecting: clientId=...`(mqtt-broker R9)
  - 그 장비 ClientId의 해석 불가 토픽 로그 `Unparsed topic passed through: "/lwt", clientId=...`(mqtt-broker R7. M130-W에서 장치 키 없는 `/lwt` 메시지를 관찰했고 Will 메시지로 추정한다, 근거 문서 5절)
  - 그 장비 장치 키의 `Device offline (LWT): ... device=...` 로그(mqtt-broker R4)
  - 동기 완료: 구간 안에서 간격이 한 번이라도 20분을 넘는다.
  - 동기 안 됨: 구간 안의 간격이 모두 20분 안이다(동기 전 재요청 간격은 가장 길어도 약 512초이므로).
  - 판정 결과와 관찰한 시각·간격을 작업 문서와 근거 문서 `docs/reference/b540-mqtt-topic.md`(4절 미확인 항목, 5절 M130-W 관찰)에 적는다. 결과가 "동기 안 됨"이어도 그 관찰을 적으면 이 조건은 채운 것으로 본다(응답 형식 추정이 틀렸다는 관찰 결과이므로).
