# tisyn 시간 동기 응답 결정

### D001 응답 `sid`는 요청의 `sid`를 그대로 쓴다(없으면 `"0"`)
- 단계: spec
- 질문: spec 검토 1회차 지적 3. 「무엇을, 왜」는 근거 문서의 응답 예처럼 `"sid":"0"`을 들었는데, 완료 조건 C2는 요청의 `sid`를 그대로 되돌리라고 적어 두 곳이 달랐다. 근거 문서는 응답 `sid` 값을 미확인으로 두고(4절), B540 요청은 고정 문자열 `"sid":"0"`이며, M130-W 요청 `sid`는 2026-11-20 서버 로그에서 `"0"`으로 관찰했다. 어느 쪽이 의도인지 정하지 않으면 구현·테스트 기대값이 갈리고, 실장비가 응답을 받아들이지 않을 때 원인 후보를 좁히는 근거가 남지 않는다.
- 선택지:
  - A. 요청 `sid` 되돌림: 응답 `sid`에 요청의 `sid` 문자열을 그대로 쓰고, 요청에 `sid`가 없으면 `"0"`을 쓴다. 「무엇을, 왜」를 이에 맞추고 이유를 적는다.
  - B. 항상 `"0"`: 근거 문서의 응답 예대로 요청과 상관없이 응답 `sid`를 늘 `"0"`으로 둔다. C2를 이에 맞춘다.
- 결정: A
- 이유: 요청과 응답의 짝을 맞추는 일반적인 방식이고, 지금 관찰한 요청 `sid`가 `"0"`이라 실장비에서는 근거 문서의 예와 같은 값이 된다. B는 지금 장비에서는 결과가 같지만, 장치가 `"0"`이 아닌 `sid`를 보내는 경우 요청과 응답의 짝이 어긋나고, 그렇게 고정할 근거(수신 파서 확인)도 없다.
- 반영: spec.md 「무엇을, 왜」 응답 형식 항목, C2

### D002 기준 spec R5는 `tisyn` 응답만 적고, 명령 발행(`w`·`chg`·`reb`)은 구현하지 않은 채 둔다
- 단계: spec
- 질문: spec 검토 2회차 지적 2. 「기준 spec에 미치는 변경」은 R5에 "서버 → 장치 발행은 `w`만 동작"이라고 적게 되어 있었는데, 완료 조건 C1~C4는 `tisyn` 응답만 정한다. `tisyn`과 상관없는 일반 `w` 발행의 `sid`(현재 `IDeviceCommandPublisher.WriteAsync`에는 `sid` 인자가 없음), retain 여부, 토픽은 어떤 조건에도 없어서, 기준 spec이 "`w` 발행이 동작한다"고 적으면서 그 동작은 정해지지도 확인되지도 않은 채 남는다.
- 선택지:
  - A. R5를 `tisyn` 응답으로 한정: R5에는 "기본 핸들러가 `tisyn`에 응답한다"만 적고, 명령 발행(`MqttDeviceCommandPublisher`의 `w`·`chg`·`reb`)은 지금처럼 `NotImplementedException`으로 둔다. `tisyn` 응답은 명령 발행과 별개인 시간 동기 응답으로 정한다.
  - B. 일반 `w` 발행도 정의: `WriteAsync`의 토픽, retain 없음, `sid`(인자로 받도록 인터페이스를 바꿈)를 완료 조건에 더하고 테스트하며, `tisyn` 응답도 이것을 써서 보낸다.
- 결정: A
- 이유: 범위가 가장 작고, 근거 없는 일반 `w` 명령의 동작(어떤 `sid`·QoS로 보낼지)을 이번 작업에서 정하지 않아도 된다. B는 인터페이스 변경과 테스트가 늘고, 일반 명령 발행의 동작을 실장비 근거 없이 정하게 된다.
- 반영: spec.md 「기준 spec mqtt-broker에 미치는 변경」, 「하지 않는 것」

### D003 기준 spec R5에는 발행 실패 처리를 적지 않고, tasks T007에서 그 항목을 뺀다
- 단계: tasks
- 질문: tasks 검토 1회차 지적 1. T007은 기준 spec R5를 spec 「기준 spec mqtt-broker에 미치는 변경」대로 고친다고 하면서 괄호 안에 그 절에 없는 "발행 실패는 Error 로그만"을 넣었다. 그 절이 R5에 직접 담기로 한 것은 받은 내용의 Information 로그 유지, 중계 꺼짐이면 retain 없이 `w` `/99/0/1` 전송(요청 `sid`, 없으면 `"0"`, UTC epoch 초 문자열), 응답 로그, 중계 켜짐이면 응답 안 함, 명령 발행 `w`·`chg`·`reb`는 `NotImplementedException`의 다섯 가지이고, 발행 실패 처리는 완료 조건 C4에만 있다. T007대로 고치면 기준 spec R5가 spec이 정한 내용과 달라져 T007 체크포인트와 구현 후 검토(C5)에서 판정이 갈린다.
- 선택지:
  - A. T007에서 빼기: tasks.md T007 괄호 안의 `, 발행 실패는 Error 로그만`을 지운다. spec.md·plan.md는 그대로 두고, 실패 처리 동작은 C4와 T004 구현·T005 실패 경로 단위 테스트로 그대로 확인한다.
  - B. spec에 더하기: spec.md 「기준 spec mqtt-broker에 미치는 변경」의 "…응답 로그를 남긴다." 뒤에 "응답 발행이 실패하면 Error 로그만 남기고 예외는 브로커로 번지지 않는다."를 더하고 T007은 그대로 둔다. 확인받은 spec의 의도 변경이라 spec 검토·확인, plan 검토·확인, 일관성 점검·tasks 검토·확인을 차례로 다시 한다.
- 결정: A
- 이유: spec이 정한 R5 범위에 tasks를 맞추고 확인받은 문서를 건드리지 않는다. 실패 처리는 C4와 테스트로 확인되므로 동작이 빠지지 않는다. B는 기준 spec이 조금 더 자세해지는 대신 검토와 확인을 세 단계 다시 해야 해 얻는 것에 비해 비용이 크다.
- 반영: tasks.md T007
