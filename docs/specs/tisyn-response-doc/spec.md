# B540 tisyn 시간 동기 응답(서버 → 장치) 분석 결과 기록

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #18

## 무엇을, 왜

근거 문서(당시 .gitignore 대상인 로컬 분석 폴더에 있었음, 지금 `docs/reference/b540-mqtt-topic.md`)는 `tisyn`을 "장치 → 서버, 시간 동기 요청"으로만 적고, 서버가 장치에 무엇을 보내야 하는지는 적지 않는다. 머리말도 "코드 흐름 디컴파일은 하지 않았다"고 적는다. 그래서 `mqtt-broker`의 `TimeSyncAsync`가 무엇을 해야 하는지 근거가 없다.

2026-11-19에 B540 플래시 덤프(근거 문서가 이미 쓰는 같은 덤프)의 슬롯 B를 Ghidra 12.2 headless(Xtensa:LE:32)로 정적 분석했다. REA `open_binary`는 Xtensa를 허용하지 않아(허용 아키텍처 6502·x86·x86_64·arm·arm64·m68k) 쓰지 못했다. 분석에서 다음을 확인했다(주소는 슬롯 B 링크 주소).

- 서버 → 장치 오퍼레이션 분기(`0x402c8890`): `msg.o`를 `rg`=1, `drg`=2, `r`=3, `w`=4, `e`=5, `d`=6, `chg`=7, `reb`=8과 비교하고, 그 밖은 `0xffff`다. `tisyn`은 이 목록에 없다.
- 요소 분기(`0x402ca708` → `0x402ca6c0` → `0x402c9300`): 오브젝트 99(`0x63`), 인스턴스 0이면 리소스 번호로 나눈다. 리소스 1에 오퍼레이션 `w`(4)이면 값 문자열을 시간 저장소(`ctx+0x298c`)에 복사하고 시간 동기 완료 플래그(`ctx+0x43c`)를 1로 만든다. 이 플래그를 1로 쓰는 곳은 디컴파일한 함수 전체(2415개)에서 이 한 곳이고, 0으로 되돌리는 곳은 찾지 못했다.
- 값 해석(`0x4029b0e0`): 값에 `0x7e90`(32400초, +9시간)을 더해 시·분·초와 요일 비트를 계산한다. 장치는 이후 그 10진수 문자열을 1씩 올린다(`0x4029b188`).
- 송신 주기(`0x4029ae54`, 로그 함수 이름 `CheckReport_timer`): 틱마다 카운터(`ctx+0x29a4`)를 올리고, `0x1c1f`(7199)를 넘으면 플래그와 상관없이 `tisyn`을 보내고 카운터를 0으로 되돌린다. 플래그가 1이면 그대로 두어 다음 송신은 7200틱 뒤다. 플래그가 1이 아니면 간격 값(전역 `0x3ffe8774`)을 300 미만일 때 두 배로, 300 이상일 때 300으로 바꾸고 `TimeSynCnt` 로그를 남기며, 카운터를 `7200 − 간격`으로 맞춰 간격만큼 뒤에 다시 보낸다. MQTT 연결 상태 값(`ctx+0x444`)이 1이 아니면 카운터를 `0x1c02`(7170), 간격을 30으로 둔다. 부팅 함수 `0x4029c0dc`(로그 `mainmode_Boot`)는 간격을 1, 카운터를 `0x1c1f`(7199)로 둔다(DRAM 초기값 30을 덮어씀). 그래서 송신 간격 수열은 조건에 따라 갈린다. 부팅 뒤 첫 틱에 이미 연결 상태 값이 1이면 곧바로 보내고 간격 2·4·8·…·256·512 다음 300이다. 미연결 틱을 지나면 연결 뒤 30틱 만에 첫 송신을 하고 간격 60·120·240·480 다음 300이다.
- 같은 함수에서 송신하지 않는 틱(카운터 ≤ 7199)에는 `ctx+0x438`이 1일 때 보고 판정을 한다. 별도 카운터 `ctx+0x299c`를 `ctx+0x230`과, 전역 카운터 `0x3fff11dc`를 `ctx+0x234`와 비교하고, `ctx+0x238`은 비교 함수 `0x4029adc0`의 인자로 넘겨, 보고 함수(`0x402ca7b8`)를 부를지 정한다. 부팅 함수 `0x4029c0dc`는 세 값을 범위 검사해 기본값을 넣고(`0x230`: 1~3600 밖이면 300, `0x234`: 11~14400 밖이면 3500, `0x238`: 1~100 밖이면 20) `MinTime = %d MaxTime = %d CheckPer = %d` 로그를 남긴다. `/99/0/5` 처리는 전역 카운터 `0x3fff11dc`의 현재 값을 그 요소의 응답 값 버퍼(`ctx + idx*0x204 + 0x980 + 0x12`)에 문자열로 기록한 뒤 0으로 만든다(읽은 뒤 초기화).
- `MqttTypeWrite`(`0x402cb7cc`): 요소를 오퍼레이션 4로 처리한 뒤, `ctx+0x438`이 0이고 플래그가 1이면 보고 관련 함수를 호출한다.
- 리소스 `/99/0/0`·`2`~`5`는 오퍼레이션을 검사하지 않아 `w`가 아닌 처리(예: `MqttTypeRead`도 같은 요소 처리 경로를 오퍼레이션 3으로 탄다)에서도 실행된다. 오퍼레이션 4(`w`)를 검사하는 것은 `/99/0/1`·`10`·`11`이다. 같은 분기에는 리소스 10·11·20도 있다. 10·11은 `w`이면 값 15바이트를 각각 `ctx+0xce`·`ctx+0xdd`에 복사하고 `0x4029ab2c`를 호출하며, 오퍼레이션과 관계없이 그 저장 값을 응답 값 버퍼에 복사한다. 20(`0x14`)은 `ctx` 앞 32바이트를 응답 값 버퍼에 복사한다. 이 셋의 의미는 확인하지 못했고, 그 밖의 리소스 번호는 처리하지 않는다. `0x4029ab2c`(의미 미확인)는 리소스 0·2·3·4에서는 오퍼레이션과 관계없이 처리 뒤 항상, 10·11에서는 `w`일 때만 호출되고, 1·5·20에서는 호출되지 않는다. 이 밖에 여러 리소스가 공통으로 `ctx+0x588`(1·10·11)과 응답 상태 버퍼(`ctx + idx*0x204 + 0xa80 + 0x11`)에 문자열을 기록한다(의미 미확인). `/99/0/0`은 송신 카운터를 0으로 되돌리고(다음 `tisyn` 송신이 늦어진다) 값을 숫자로 바꿔 `ctx+0x130`에 저장한다. `/99/0/2`·`3`·`4`는 값을 숫자로 바꿔 각각 `ctx+0x230`·`0x234`·`0x238`에 저장한다.
- 값이 담기는 JSON 키(`sv` 등)는 수신 파서에서 확인하지 못했다. 틱 단위(초 여부)도 확인하지 못했다.

이 결과를 근거 문서에 관찰·추정·미확인을 구분해 기록해, 서버 시간 동기 응답 구현의 근거로 쓴다. 서버 코드 변경과 실장비 확인은 범위 밖이다.

같은 근거 문서에 M130-W 관찰 절을 더하는 진행 중 작업(`docs/specs/mqtt-notify-short-op/`, 그 spec C4)이 있다. 그 작업이 더하거나 바꾸는 내용(M130-W 관찰 절, 3절 표의 `n` 행, 머리말 근거 줄의 실통신 관찰 관련 문장, 머리말 표기 줄의 관찰 정의에서 실장비 통신 로그 부분, 4절의 M130-W 관련 문장)은 이번 작업이 더하거나 지우지 않는다. 두 작업이 같은 줄(머리말, 3절 표, 4절)을 고치므로 나중에 반영하는 작업이 앞 작업의 내용을 보존해 합친다.

## 완료 조건

- C1. 근거 문서 3절 오퍼레이션 코드 표의 방향·의미가 위 분기 결과와 맞는다. `tisyn` 행은 장치 → 서버 요청이며 서버 → 장치 분기 목록에 없다고 적고, `rg`·`drg`·`r`·`w`·`e`·`d`·`chg`·`reb`의 분기 번호(1~8)와 서버 → 장치 수신 여부가 표나 본문에 있다. 지금 미확인으로 둔 `MqttTypeRead`/`Execute`/`Delete`의 `o` 코드(`r`·`e`·`d`)가 확인값으로 바뀌고 4절 미확인 항목에서도 빠진다.
- C2. 근거 문서에 시간 동기 절이 있고 다음을 근거 함수 주소와 함께 적는다. 디컴파일에 직접 나타난 동작(복사·플래그 설정, +32400 가산과 시·분·초·요일 계산, 문자열 1 증가, 주기·간격 상수, 카운터·저장 위치)은 **관찰**로, 그 동작의 의미 해석(값이 UTC 기준 Unix epoch 초라는 것, +9시간이 KST라는 것, `ctx+0x444`가 MQTT 연결 상태라는 것)은 **추정**으로 표기한다.
  - 서버가 `w`로 `/99/0/1`에 시간 값을 쓰면 장치가 시간 저장소에 복사하고 동기 완료 플래그를 1로 만든다.
  - 값은 UTC 기준 Unix epoch 초의 10진수 문자열이며 장치가 +9시간(KST)을 더해 시·분·초·요일을 계산하고, 이후 그 문자열을 스스로 1씩 올린다.
  - 송신 주기: 동기 후에도 7200틱마다 `tisyn`을 보낸다. 동기 전에는 간격마다 다시 보내며 `TimeSynCnt`를 남긴다. 부팅 시 간격 1·카운터 7199, MQTT 미연결 틱마다 카운터 7170·간격 30으로 두는 동작과, 그에 따른 두 간격 수열(첫 틱에 연결돼 있으면 2·4·…·512 다음 300, 미연결을 지나면 연결 30틱 뒤 첫 송신 후 60·120·240·480 다음 300)을 적는다. 수열은 상수와 분기에서 따라 나온 것이라 관찰로 적되, 어느 수열이 실제로 나타나는지(첫 틱 때 연결 여부)는 미확인으로 적는다.
  - `/99/0/0`: 송신 카운터를 0으로 되돌리고(다음 송신이 늦어짐) 값을 `ctx+0x130`에 숫자로 저장한다.
  - `MqttTypeWrite` 뒤 보고 함수 호출 조건(`ctx+0x438`이 0이고 플래그가 1).
- C3. 근거 문서에 시간 동기 절과 구분된 오브젝트 99 리소스 처리 절(새 절)이 있고, `0x402c9300`이 처리하는 리소스 전부(0~5, 10, 11, 20)에 대해 리소스마다 저장 위치, `w` 검사 여부(`w` 검사는 1·10·11), 응답 값 버퍼에 돌려주는 내용, `0x4029ab2c` 호출 여부(0·2·3·4는 항상, 10·11은 `w`일 때, 1·5·20은 없음)를 **관찰**로 적고, 10·11·20과 `0x4029ab2c`의 의미는 **미확인**으로 적는다. 공통 부수 기록(`ctx+0x588`, 응답 상태 버퍼 `+0xa80+0x11`)은 리소스별로 나누지 않고 한 줄로 묶어 의미 **미확인**으로 적는다. `/99/0/2`·`3`·`4`는 보고 조건 값으로 적되, 저장 위치와 비교 상대(`ctx+0x299c`, 전역 `0x3fff11dc`, `0x4029adc0` 인자), 부팅 함수 `0x4029c0dc`의 범위 검사·기본값(`0x230`: 1~3600 밖이면 300, `0x234`: 11~14400 밖이면 3500, `0x238`: 1~100 밖이면 20)과 로그 라벨 `MinTime`·`MaxTime`·`CheckPer`는 **관찰**, 보고 조건(최소·최대 보고 간격과 변화 기준)이라는 의미는 **추정**으로 표기하고, `/99/0/5`는 전역 카운터 값을 응답 값으로 기록한 뒤 0으로 만든다(읽은 뒤 초기화, **관찰**)고 적는다. 값이 담기는 JSON 키와 전체 응답 메시지 예는 **추정**으로, 틱 단위(초 여부)는 **미확인**으로 적고, 4절 미확인 항목에 남은 확인 사항(값 키, 틱 단위, 실장비 응답 확인)이 있다.
- C4. 근거 문서 머리말의 근거 줄이 이번 Ghidra 정적 분석(도구·버전·대상 슬롯·REA 미사용 이유·분석 날짜 2026-11-19)을 포함하도록 바뀌고, "코드 흐름 디컴파일은 하지 않았다"는 문장이 사실과 어긋나지 않는다. 머리말 표기 줄의 **관찰** 정의가 덤프 코드의 디컴파일에 직접 나타난 동작을 포함한다.
- C5. 근거 문서를 이번 작업이 고치기 직전 상태(그림자 저장소 기준점. 작업 문서 기준점 줄의 최초 기준점이며, 고치기 전에 M130-W 작업이 먼저 반영되면 고치기 직전에 기준점을 그 상태로 다시 잡아 작업 문서에 적는다)와 비교했을 때, 바뀐 곳은 C1~C4가 요구하는 곳(머리말 근거·표기 줄, 3절 오퍼레이션 표와 그 설명, 시간 동기 절, 새 오브젝트 99 리소스 처리 절, 4절 미확인 항목)뿐이다. 1·2절, 등록 메시지 절, 보고 함수 절은 같고, 위 「무엇을, 왜」에 적은 M130-W 작업의 내용은 더하거나 지우지 않는다.
- C6. 기준 spec `docs/features/mqtt-broker.md`의 이번 작업 diff는 이력 표에 이번 작업 한 줄(바꾼 요구 없음, 근거 문서 갱신)을 더하는 것뿐이고 요구 목록 줄은 바꾸지 않는다.
