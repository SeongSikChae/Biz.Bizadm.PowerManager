# B540 tisyn 시간 동기 응답(서버 → 장치) 분석 결과 기록 계획

## 요약

근거 문서 `docs/reference/b540-mqtt-topic.md`의 머리말·3절·4절을 Ghidra 정적 분석 결과로 고친다. 3절에는 서버 → 장치 수신 분기 설명, 시간 동기 절 확장, 오브젝트 99 리소스 처리 새 절을 더한다. 기준 spec `docs/features/mqtt-broker.md`에는 이력 한 줄만 더한다. 작업 시작 기준점(`d351344`, 근거 문서는 작업 문서 기준점 줄의 그림자 저장소 최초 기준점) 이후 M130-W 작업(`mqtt-notify-short-op`)이 같은 두 파일을 바꿨으므로(`mqtt-broker.md`는 커밋 `80f299c`, .gitignore 대상인 근거 문서는 작업 트리에만), 고치기 직전에 두 파일을 그림자 저장소 기준점으로 다시 잡고 그 상태와 비교해 검토한다.

## 바꿀 파일·구조

- 근거 문서(당시 .gitignore 대상인 로컬 분석 폴더에 있었음, 지금 `docs/reference/b540-mqtt-topic.md`)
  - 머리말 근거 줄: 1~3절 근거를 "B540 플래시 덤프의 정적 문자열·설정 섹터 바이트, 그리고 3절의 오퍼레이션 표 중 `r`·`e`·`d`·`tisyn`·`rg`·`drg` 수정과 수신 분기·시간 동기·오브젝트 99 절은 2026-11-19 Ghidra 12.2 headless(`Xtensa:LE:32`) 슬롯 B 정적 디컴파일(REA `open_binary`가 Xtensa를 허용하지 않아 Ghidra를 씀)"로 바꾸고, B540 실통신 관찰이 없다는 사실과 M130-W 5절 문장은 그대로 둔다(C4, C5).
  - 머리말 표기 줄: **관찰** 정의의 "덤프"를 "덤프(문자열·바이트, 그리고 디컴파일에 직접 나타난 동작)"로 넓히고 "또는 실장비 통신 로그" 부분은 그대로 둔다(C4, C5).
  - 3절 `### 오퍼레이션 코드` 표: `(미확인)` 행(`MqttTypeRead`/`Execute`/`Delete`)을 `r`·`e`·`d` 세 행으로 바꾸고, `tisyn` 행의 의미 칸에 "서버 → 장치 수신 분기에 없음"을, `rg`·`drg` 행의 의미 칸에 "서버 → 장치로도 수신(분기 1·2, 의미 미확인)"을 더한다. 나머지 행(`n` 행 포함)은 그대로 둔다(C1, C5).
  - 3절 표 바로 아래 새 하위 절 `### 서버 → 장치 수신 분기 (관찰, 디컴파일)`: `0x402c8890`의 번호(`rg`=1, `drg`=2, `r`=3, `w`=4, `e`=5, `d`=6, `chg`=7, `reb`=8, 그 밖 `0xffff`)와 이와 다른 실제 비교 순서(`rg`→`drg`→`chg`→`reb`→`r`→`w`→`e`→`d`), 각 비교가 ROM `0x40002ac8`을 상수 문자열에 부른 결과를 ROM `0x40002ab8`의 세 번째 인자로 넘기는 호출 구조(관찰), 두 ROM 함수가 `strncmp`·`strlen`이어서 상수 길이만큼만 보는 접두 비교가 되고 따라서 비교 순서가 판정에 영향을 준다는 점(추정), `tisyn` 없음, 수신 메시지 키(`o`·`r`·`e`·`reason`, `0x402c89cc`)를 적는다(C1).
  - 3절 `### 시간 동기 (관찰)` 절: 기존 요청 JSON은 그대로 두고 아래에 하위 항목을 더한다. 응답 흐름(`w` → `/99/0/1` → 시간 저장소·플래그), 값 해석(+32400, 요일 비트, 1 증가), 송신 주기(7200틱, 부팅 함수 `0x4029c0dc`의 간격 1·카운터 7199 설정, MQTT 미연결 틱의 카운터 7170·간격 30, 두 간격 수열 2·4·…·512 다음 300 / 연결 30틱 뒤 첫 송신 후 60·120·240·480 다음 300은 관찰, 어느 수열이 나타나는지는 미확인), `/99/0/0` 영향, `MqttTypeWrite` 뒤 보고 호출 조건, 응답 메시지 예(추정). 각 항목에 주소와 관찰/추정/미확인 표기를 붙인다. 제목은 `### 시간 동기 (요청 관찰, 응답 처리 디컴파일)`로 바꾼다(C2, C3).
  - 시간 동기 절 바로 뒤 새 하위 절 `### 오브젝트 99 리소스 처리 (관찰, 디컴파일)`: 경로 분기(`0x402ca708` → `0x402ca6c0` → `0x402c9300`)와 리소스 0~5·10·11·20의 표(저장 위치, `w` 검사, 응답 값 버퍼 내용, `0x4029ab2c` 호출), 공통 부수 기록 한 줄, `/99/0/2`~`4` 보고 판정(비교 상대와 부팅 함수 `0x4029c0dc`의 범위 검사·기본값·로그 라벨 `MinTime`·`MaxTime`·`CheckPer`는 관찰, 최소·최대 보고 간격과 변화 기준이라는 의미는 추정), `/99/0/5` 읽은 뒤 초기화(C3).
  - 4절: `MqttTypeRead`/`Execute`/`Delete`의 `o` 코드 줄을 지우고, 값 JSON 키, 틱 단위, B540 시간 응답의 실장비 확인을 더한다. M130-W 관련 문구가 든 기존 줄은 그대로 둔다(C1, C3, C5).
  - 1·2절, 등록 메시지 절, `### 장치 → 서버 보고`, `### 서버 → 장치 처리`, 5절은 바꾸지 않는다(C5).
- `docs/features/mqtt-broker.md`: 이력 표 끝에 `| 2026-11-19 | tisyn-response-doc | 없음(근거 문서 docs/reference/b540-mqtt-topic.md에 시간 동기 응답·서버 → 장치 수신 분기 분석 기록) | docs/specs/tisyn-response-doc/ |` 한 줄을 더한다. 요구 목록과 머리 설명은 바꾸지 않는다(C6).

## 결정

- 기준점을 고치기 직전에 다시 잡는다: spec C5가 정한 대로다. 작업 시작 기준점 이후 M130-W 작업이 근거 문서(작업 트리)와 `mqtt-broker.md`(커밋 `80f299c`)를 바꿨으므로, 두 파일을 그림자 저장소 기준점 커밋에 `--amend --only`로 덧붙여(근거 문서는 다시 담고 `mqtt-broker.md`는 새로 담음, .gitignore 때문에 `add -f`) 그 상태를 기준으로 삼는다. / 검토한 대안: `mqtt-broker.md`를 작업 문서 git 기준점 `d351344`와 비교 — 그 뒤 커밋 `80f299c`의 R4·R6 변경이 diff에 섞여 C6을 판정할 수 없어 고르지 않음. 지금 `HEAD`(`80f299c`)와 비교하는 방법도 되지만, 근거 문서와 같은 그림자 저장소 방식으로 두 파일을 한 번에 비교하는 쪽이 C5·C6 확인 절차가 하나로 같아 그쪽을 고름.
- 분기 번호는 표에 열을 더하지 않고 새 하위 절에 둔다: 표에 열을 더하면 M130-W 작업의 `n` 행도 고쳐야 해 C5(그 작업 내용을 더하거나 지우지 않음)와 부딪친다. / 검토한 대안: 표에 "수신 분기 번호" 열 추가 — 위 이유로 고르지 않음.
- 시간 동기와 오브젝트 99 리소스를 별도 절로 나눈다: spec C3이 정한 구분이며, `/99/0/2`~`5`·10·11·20은 시간 동기와 무관하다. / 대안 없음.
- 응답 메시지 예는 `{"sid":"0","msg":{"o":"w","e":[{"n":"/99/0/1","sv":"<epoch 초>"}]}}`로 적고 값 키 `sv`·`sid` 값은 추정으로 표기한다: 기존 3절 메시지 형식이 `sv`를 쓰고, 수신 파서에서 값 키를 확인하지 못했다. / 대안 없음.
- 분석 산출물(디컴파일 결과·Ghidra 스크립트)은 이번 작업에서 저장소나 로컬 분석 폴더로 옮기지 않는다: spec 범위 밖이다. 근거 문서에는 주소와 도구·설정(프로세서 `Xtensa:LE:32`, 세그먼트 배치)을 적어 다시 만들 수 있게 한다. / 검토한 대안: 스크립트를 로컬 분석 폴더에 보관 — spec에 없는 변경이라 고르지 않음(필요하면 별도 작업).

## 인터페이스·데이터

새 절에 적을 슬롯 B 메모리 배치(재현용): IROM 파일 `0x81010`~`0xd61a0` → `0x40281010`, IRAM `0xd61b0`(길이 `0x7bf0`) → `0x40100000`, DRAM `0xddda8`(`0xdac`) → `0x3ffe8000`, `0xdeb5c`(`0x212c`) → `0x3ffe8db0`.

## 오류·위험

- M130-W 작업은 커밋(`80f299c`)까지 끝났지만, 그 뒤 다른 작업이 두 파일을 다시 고칠 수 있다. 고치기 직전에 `git log`로 기준점 재설정 이후 두 파일을 바꾼 새 커밋이 없는지 보고 기준점을 다시 잡는다. 이번 작업이 두 파일을 마지막으로 고친 직후의 해시를 적어 두고 검증 직전 해시와 비교해, 다르면 멈추고 사용자에게 알린다.
- 근거 문서는 git 밖이라 커밋으로 보존되지 않는다. 이번 작업의 산출물 보존은 로컬 파일과 그림자 저장소뿐이다(기존 방식과 같음).
- 분석 산출물이 스크래치에 있어 재부팅 등으로 사라질 수 있다. 근거 문서의 주소·배치 정보로 재현할 수 있게 적는다.
- 디컴파일은 정적 분석이라 실제 장치 동작(틱 단위, 값 키)을 보장하지 않는다. 표기로 구분한다.

## 검증 전략

- C1: 근거 문서 3절 표에 `r`·`e`·`d` 행이 있고 `(미확인)` 행이 없는지, 새 수신 분기 절에 1~8 번호와 `tisyn` 없음이 있는지, 4절에서 `o` 코드 미확인 줄이 빠졌는지 읽어 확인한다(`grep`).
- C2: 시간 동기 절에 spec C2의 다섯 항목이 주소·표기와 함께 있는지 항목별로 대조한다.
- C3: 오브젝트 99 절의 표에 리소스 0~5·10·11·20 각 행과 네 항목이 있는지, 공통 기록 한 줄, `/99/0/2`~`5` 서술과 표기, 4절의 세 미확인 항목을 대조한다.
- C4: 머리말 근거·표기 줄을 읽어 Ghidra 도구·버전·슬롯·REA 미사용 이유·날짜와 관찰 정의 확장을 확인한다.
- C5: 그림자 저장소에서 `git -C "$W" --git-dir="$S" --work-tree="$W" add -f -A -- docs/reference/b540-mqtt-topic.md docs/features/mqtt-broker.md` 뒤 `git ... diff --cached <재설정한 기준점>`으로 근거 문서 diff를 내어(spec-driven 5절 그림자 저장소 방식. add 없이 `--cached`를 쓰면 빈 diff가 나온다), 바뀐 hunk가 머리말 근거·표기 줄, 3절 표와 새 하위 절, 시간 동기 절, 오브젝트 99 절, 4절에만 있고 M130-W 문구(5절, `n` 행, 근거 줄의 5절 문장, 표기 줄의 실장비 부분, 4절의 M130-W 괄호)가 지워지지 않았는지 확인한다.
- C6: 같은 방식으로 `mqtt-broker.md` diff가 이력 표 한 줄 추가뿐인지 확인한다.

## 원칙 점검

- 적용 규칙: 전역 `language-preference.md`(문서 문장은 한국어, 코드 표기만 영어), MCP `workflow/spec-driven.md`, `git/github-issue.md`(#18), 저장소 문서 관례(근거 문서의 관찰·추정·미확인 표기).
- 충돌: spec-driven은 git 저장소의 기준점을 작업 시작 커밋으로 잡고 구현 후 검토 diff를 `git diff <기준 커밋>`으로 만들라고 한다. 이번 대상 중 근거 문서는 .gitignore 대상이라 git diff에 나오지 않고, `mqtt-broker.md`는 기준점 `d351344` 이후 다른 작업의 커밋(`80f299c`)이 바꿔 git 기준점 diff에 그 변경이 섞인다. 그래서 두 파일은 그림자 저장소 기준점(고치기 직전 재설정)으로 비교하고, 이번 세 문서만 git `add -N` 후 `git diff d351344 -- docs/specs/tisyn-response-doc`으로 넣는다. 사용자가 이 방식(전체 절차, 별도 진행)을 정했다.
- 포터블 Python 규칙: 이번 작업은 Python을 쓰지 않는다.
