# MQTT 구독·전달 기록 로그

기능: mqtt-broker(기준 spec docs/features/mqtt-broker.md)
이슈: GitHub #23

## 무엇을, 왜

`tisyn` 시간 동기 응답(GitHub #21) 실장비 확인에서 장비가 서버 → 장치 메시지에 반응하지 않았다. 장비는 응답 뒤에도 동기 전 간격으로 `tisyn`을 다시 보낸다.

- 서버의 `tisyn` 응답 `w` `/99/0/1`(접미 없는 토픽)에는 M130-W 3대와 B540 1대가 모두 반응하지 않았다.
- 읽기 요청 `r`(접미 없는 토픽)과 다원 실서버와 같은 접미 토픽 `/write/json`은 B540에, `/read/json`은 B540과 M130-W 1대에 보냈고 역시 반응이 없었다.

브로커가 이 메시지를 받은 것은 서버 로그(R7 통과 로그)로 확인된다. #21 실장비 확인 뒤 펌웨어를 다시 분석(B540 1.01.34 슬롯 B 재디컴파일, M130-W 2.01.58 분석)해 다음을 확인했다. 이 결과는 아직 근거 문서 `docs/reference/b540-mqtt-topic.md`에 반영하지 않았고(그 문서는 QoS·`sv`를 미확인·추정으로 둔다), 이 작업에서도 근거 문서에 반영하지 않으며, 반영은 따로 할 후속 작업으로 둔다(D004).

- 장치는 접속 직후 `{prefix}.v1/iot-server/{장치 키}/#`를 QoS 0으로 구독한다.
- 받은 메시지는 토픽을 검사하지 않고 해석한다.
- 서버 응답 형식(`o` `w`, 요소 `n`·`sv`)은 해석 경로에 맞는다.

다만 실장비 B540은 펌웨어 1.01.36으로 분석본과 다르고, `w`·`r` 공통 처리의 점프 표는 복원하지 못했다. 그래서 원인 후보에는 전달 문제와 함께 장비 쪽(펌웨어 차이, 복원하지 못한 구간)도 남아 있다. 이 작업은 그중 장비가 서버 → 장치 토픽을 구독했는지와, 브로커가 그 메시지를 장비 클라이언트 큐에 넣었는지를 서버 로그로 가린다. 큐에 넣은 뒤 실제 송신과 장비 수신(QoS 0이라 수신 확인 없음)은 이 로그로 가리지 못하는 남은 구간이다. 지금 서버 로그에는 두 가지가 남지 않아 이것을 가릴 수 없다.

- 클라이언트가 무엇을 구독했는지
- 브로커가 서버 → 장치 메시지를 어느 클라이언트에게 넘겼는지

내장 브로커가 다음을 로그로 남기게 한다.

- 클라이언트의 구독·구독 해제(토픽 필터·QoS)
- 서버 → 장치 메시지의 전달: 어느 클라이언트에게 넣었는지, 구독자가 없어 아무에게도 가지 않았는지(D001, D002)

장치 → 서버 메시지는 서버 핸들러만 받으므로 전달 로그를 남기지 않는다. 브로커의 구독·전달 동작은 바꾸지 않고 기록만 더한다.

## 완료 조건

- C1. 클라이언트가 SUBSCRIBE를 보내면, 그 안의 토픽 필터마다 Information 로그 항목 하나를 남긴다. 항목에는 ClientId, 토픽 필터, 요청 QoS가 들어간다. 구독을 거부하거나 바꾸지 않는다. SUBACK 결과와 그 뒤 메시지 전달은 이 변경 전과 같다.
- C2. 클라이언트가 UNSUBSCRIBE를 보내면, 그 안의 토픽 필터마다 Information 로그 항목 하나를 남긴다. 항목에는 ClientId와 토픽 필터가 들어간다. 구독 해제를 거부하지 않는다.
- C3. 서버 → 장치 토픽 메시지를 브로커가 구독 클라이언트의 큐에 넣을 때마다, 받는 클라이언트마다 Information 로그 항목 하나를 남긴다(D002).
  - 서버 → 장치 토픽: 빈 토큰을 빼고 토큰이 3개 이상이며, 첫 토큰이 `.v1`로 끝나고 그 앞 접두가 비지 않으며, 둘째 토큰이 `iot-server`인 토픽. R2의 `{prefix}.v1/iot-server/{deviceKey}`와 그 뒤에 접미가 붙은 형태를 모두 포함한다.
  - 항목에는 보낸 ClientId(서버가 주입한 메시지는 `power-manager`), 받는 ClientId, 토픽이 들어간다.
- C4. 서버 → 장치 토픽(C3) 메시지에 맞는 구독이 없어 아무 클라이언트에게도 가지 않으면, Warning 로그 항목 하나에 보낸 ClientId와 토픽을 남긴다.
- C5. 서버 → 장치 토픽이 아닌 메시지(장치 → 서버 토픽, `/lwt` 등)에는 C3·C4 로그를 남기지 않는다. 기존 동작(R1~R9의 해석·분배·전달·로그)은 바뀌지 않는다.
- C6. 기준 spec `docs/features/mqtt-broker.md`에 C1~C5를 요구로 더한다. 머리말에 구독·전달 로그를 적고, `파일:` 줄을 이번에 더하거나 바꾼 파일에 맞추고, 이력에 이번 작업 한 줄을 더한다.
- C7. `dotnet build`가 경고 0으로 끝나고 `dotnet test` 전체에서 실패가 없다. C1~C5는 자동 테스트로 확인한다.
- C8. 이 빌드를 서버 로컬 배포 폴더에 반영해 실장비로 확인한다.
  - 배포 전에 배포 `config.yaml`에서 `DawonRelay` 섹션을 지운다. #20 이후 빌드는 이 섹션이 있으면 시작하지 않는다.
  - 서버를 멈추고 다시 시작하는 일과 설정 수정은 사용자에게 알리고 승인을 받은 뒤에 한다.
  - M130-W와 B540이 접속한 뒤 다음을 서버 로그에서 모아 작업 문서에 적는다. 실장비 MAC 전체는 저장소에 적지 않는다.
    - 장비마다 구독 로그(토픽 필터·QoS)
    - 첫 `tisyn` 응답의 전달 로그 또는 구독자 없음 로그
  - 판정을 함께 적는다. 구독 토픽 필터가 그 장비의 서버 → 장치 토픽에 맞는가. 응답이 그 장비 ClientId 큐에 넣어졌는가.
