# MQTT 구독·전달 기록 로그 결정

### D001 구독 로그에 서버 → 장치 메시지 전달 로그를 더한다
- 단계: spec
- 질문: 이 작업의 범위. 목표는 서버가 보낸 서버 → 장치 메시지(`tisyn` 응답 `w` `/99/0/1`)가 장비까지 가는지 서버 로그로 가리는 것이다. 이슈 #23 처음 범위는 클라이언트의 구독·구독 해제 기록뿐이었다. 그런데 구독 기록만으로는 "구독이 있다"까지만 알 수 있고, 브로커가 그 메시지를 장비 클라이언트에게 실제로 넘겼는지는 알 수 없다. MQTTnet 5.2에는 메시지를 어느 구독 클라이언트의 큐에 넣었는지·버렸는지 알려 주는 이벤트(`ApplicationMessageEnqueuedOrDroppedAsync`)와 구독자가 없어 아무에게도 가지 않았음을 알려 주는 이벤트(`ApplicationMessageNotConsumedAsync`)가 있다.
- 선택지:
  - A. 구독 + 전달 로그: 구독·구독 해제 로그에 더해, 서버 → 장치 토픽 메시지가 어느 클라이언트에게 넣어졌는지/버려졌는지, 구독자가 없어 아무에게도 가지 않았는지를 로그로 남긴다. 장치 → 서버 메시지는 서버 핸들러만 받으므로 전달 로그를 남기지 않는다. 이슈 #23 제목·본문을 범위에 맞게 고친다.
  - B. 구독 로그만: 이슈 #23 처음 범위대로 구독·구독 해제만 남긴다.
- 결정: A
- 이유: A는 구독이 있는데도 장비가 반응하지 않을 때 "브로커가 장비 ClientId에게 넘겼다"까지 서버 로그로 확인되어, 남은 원인을 장비 쪽(수신 처리)으로 좁힐 수 있다. 장치 → 서버 메시지를 빼므로 로그가 크게 늘지 않는다. B는 구독이 확인된 뒤에도 전달 여부를 UART 같은 다른 방법으로 다시 확인해야 해 목표를 한 번에 채우지 못한다.
- 반영: spec.md 무엇을·왜, C3·C4

### D002 전달 로그에서 버림을 빼고 큐에 넣은 것만 남긴다
- 단계: spec
- 질문: spec 검토 1회차 지적 1. 검토 의견: C3이 서버 → 장치 메시지를 "버렸으면 Warning"으로 남기라고 했지만, MQTTnet 5.2는 넘침 정책이 `DropOldestQueuedMessage`이면 큐에 넣기가 늘 성공하고, 밀려 버려지는 이전 메시지는 별도 이벤트 `QueuedApplicationMessageOverwrittenAsync`로만 알려진다(`MQTTnet.Server.xml`의 `MqttSessionStatus.TryEnqueueApplicationMessage` 설명). 서버는 넘침 정책·큐 크기를 정하지 않아 MQTTnet 기본값을 쓰므로 C3의 Warning 경로는 일어나지 않고, 자동 테스트로 확인하려면 브로커 옵션을 바꿔야 해 "동작을 바꾸지 않는다"(C5)와 부딪힌다. 확인할 수 없는 완료 조건이 남는 것이 문제다.
- 선택지:
  - A. 버림을 빼고 넣음만: C3을 "큐에 넣을 때마다 받는 클라이언트마다 Information 로그(보낸 ClientId, 받는 ClientId, 토픽)"로 줄이고 버림 여부·Warning을 뺀다.
  - B. 덮어쓰기까지 Warning: 버림을 "큐에 넣지 못함 또는 큐에 있던 메시지가 새 메시지에 밀려 버려짐"으로 정의해 둘 다 Warning으로 남기고, 버림 경로는 테스트에서만 큐 크기를 작게 준 브로커로 확인하며, C5의 "동작을 바꾸지 않음"은 운영 설정 기준으로 한정한다.
- 결정: A
- 이유: A를 고른 이유는 버림이 한 클라이언트 큐에 메시지가 기본 한도만큼 쌓여야 생기는 드문 상황이고, 이번 목표(서버 → 장치 메시지가 장비까지 가는지)는 넣음 로그와 구독자 없음 로그(C4)로 채워지기 때문이다. B는 드문 상황을 위해 요구와 테스트용 설정 주입 경로를 늘리고 C5 문구까지 한정해야 해 고르지 않았다.
- 반영: spec.md 무엇을·왜, C3. D001의 "넣었는지·버렸는지"는 이 결정으로 "넣었는지"가 된다.

### D003 B540 분석 결과의 출처를 바로 적고 근거 문서 반영은 #21에 맡긴다
- 단계: spec
- 질문: spec 검토 2회차 지적 1. 검토 의견: 「무엇을, 왜」가 B540의 세 항목(접속 직후 QoS 0 구독, 받은 메시지 토픽 무검사, 응답 형식 `n`·`sv`가 해석 경로에 맞음)의 근거로 `docs/reference/b540-mqtt-topic.md`를 들었지만, 그 문서는 QoS를 "토픽별 QoS 값은 미확인", `sv`를 "수신 파서에서 확인하지 못했다(추정)"로 적고 토픽 무검사는 적지 않았다. 세 항목은 #21 실장비 확인 뒤 B540 슬롯 B를 다시 디컴파일한 결과로, 저장소 밖 작업 기록에만 있다. 저장소만 보는 사람은 "확인했다"와 반대되는 서술을 보게 되는 것이 문제다.
- 선택지:
  - A. 인용 바꾸기: spec에서 근거 문서 인용을 빼고 "#21 실장비 확인 뒤 다시 분석(B540 1.01.34 슬롯 B 재디컴파일, M130-W 2.01.58 분석)해 확인했고, 근거 문서에는 아직 반영하지 않았으며 #21의 근거 문서 반영 작업에서 적는다"로 적는다.
  - B. 근거 문서에 반영: 이 작업의 바꿀 파일에 `docs/reference/b540-mqtt-topic.md`를 더해 분석 결과를 관찰/추정 표기로 적고, 그 반영을 완료 조건으로 더한다.
- 결정: A
- 이유: A를 고른 이유는 근거 문서 반영이 원래 #21의 작업(T011)이라 이 작업(로그 추가) 범위를 키우지 않으면서 인용과 내용이 어긋나는 문제를 없애기 때문이다. 저장소 밖 작업 기록 경로는 저장소 내용 규칙상 spec에 적지 않는다. B는 #21 T011과 겹치고 이 작업 범위를 키워 고르지 않았다.
- 반영: spec.md 무엇을·왜

### D004 재분석 결과의 근거 문서 반영을 후속 작업으로 둔다
- 단계: spec
- 질문: D003 대체. spec 검토 3회차 지적 1. 검토 의견: D003으로 spec이 B540 재분석 결과(접속 직후 QoS 0 구독, 토픽 무검사, 응답 형식 `n`·`sv`)와 M130-W 2.01.58 분석 결과를 "#21의 근거 문서 반영 작업(T011)에서 적는다"고 했지만, `docs/specs/tisyn-response/tasks.md`의 T011은 T010의 실장비 판정 결과를 근거 문서 4절 시간 동기 미확인 항목(응답 값 키·`sid`, 동기 뒤 재송신 여부)과 5절 M130-W 관찰에 적는 작업이다. 그래서 QoS 0 구독·토픽 무검사·M130-W 펌웨어 분석은 어느 작업에도 들어 있지 않고, spec이 지켜지지 않을 약속을 하며 근거 문서의 "QoS 미확인"이 계속 남을 수 있다. D003 이유의 "근거 문서 반영이 원래 #21의 작업(T011)"도 T011 문구와 맞지 않는다.
- 선택지:
  - A. 후속 작업으로 둔다: spec 문구를 "이 작업에서도 근거 문서에 반영하지 않으며, 반영은 따로 할 후속 작업으로 둔다"로 바꾸고, 후속 작업(근거 문서에 B540 재분석·M130-W 분석 반영)을 작업 기록에 남긴다.
  - B. 이 작업에서 반영: 바꿀 파일에 `docs/reference/b540-mqtt-topic.md`를 더하고, 재분석·M130-W 분석 결과를 관찰/추정 표기로 적는 완료 조건을 더한다.
- 결정: A
- 이유: A를 고른 이유는 이 작업(로그 추가)의 범위를 지키면서 문서의 약속을 사실과 맞추기 때문이다. 근거 문서 반영은 #21을 마무리할 때 실장비 판정과 함께 하기 좋다. B는 이 작업의 범위와 검토 대상을 키우고, D003에서도 같은 이유로 고르지 않았다.
- 반영: spec.md 무엇을·왜

### D005 C1 테스트는 필터를 QoS가 높은 순서로 보내 필터마다 승인 결과를 단언한다
- 단계: plan
- 질문: plan 검토 2회차 지적 1. 검토 의견: plan 검증 전략 C1은 한 SUBSCRIBE에 QoS 0·1 필터를 보내고 필터마다 요청 QoS대로 승인(`GrantedQoS0`·`GrantedQoS1`)되는지 확인한다고 했다. 그런데 MQTTnet 5.2 서버는 필터를 QoS 내림차순으로 처리하며 SUBACK 결과 코드를 그 순서로 담고(디컴파일 `MqttClientSubscriptionsManager.Subscribe`의 `OrderByDescending`), 클라이언트는 결과 코드를 요청 필터 순번대로 짝짓는다(`MqttClientSubscribeResultFactory`). 그래서 QoS 0, 1 순서로 요청하면 결과가 뒤바뀌어 보인다. 이번 변경과 무관한 기존 동작이라, 적힌 대로 테스트하면 변경과 관계없이 C1 테스트가 실패해 C7을 채우지 못한다.
- 선택지:
  - A. QoS가 높은 순서로 요청: 필터를 QoS 1, QoS 0 순서로 보내 순번과 처리 순서를 맞추고, 필터마다 결과 코드를 단언한다. 로그 순서는 단언하지 않는다.
  - B. 결과 코드 집합 비교: 요청 순서는 그대로 두고 결과 코드 집합이 {`GrantedQoS0`, `GrantedQoS1`}인지만 본다.
- 결정: A
- 이유: A를 고른 이유는 필터마다 요청 QoS대로 승인됨을 정확히 확인하면서 기존 순서 동작에 걸리지 않기 때문이다. B는 필터와 결과가 뒤바뀌어도 통과해 "필터마다 요청 QoS대로 승인"을 확인하지 못해 고르지 않았다.
- 반영: plan.md 검증 전략 C1
