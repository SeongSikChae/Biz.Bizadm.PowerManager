# B540 FOTA 요청 경로 펌웨어 분석

기능: 없음(분석 기록 `docs/reference/b540-fota.md`를 바꾼다. `docs/features`의 제품 기능이 아니다)
이슈: GitHub #24(이 분석의 계기. 별도 이슈를 열지 않고 이 작업의 결과는 참조 문서에만 반영한다)

## 무엇을, 왜

B540 장치가 다원에서 받은 FOTA URL을 실제로 어떤 HTTP 요청으로 바꾸는지 펌웨어 덤프(`docs/.tmp/b540-dump1.bin`)의 정적 분석으로 밝힌다.

#24 가짜 장비의 2026-11-20 실행에서 다원은 MQTT `w` `/5/0/1`로 `http://dwapi.dawonai.com:18446/DAWONDNS/B540_W/1.01.34`를 보냈다. 가짜 장비가 이 URL을 그대로 써서 보낸 `GET {URL}/version`과 `GET {URL}`은 둘 다 404였다. 추측 경로(`user1.bin`·`user2.bin`)도 404였다. 근거 문서 `docs/reference/b540-fota.md`는 FOTA 흐름을 펌웨어의 정적 문자열만으로 추정했고, URL을 호스트·포트·경로로 어떻게 나누는지, 이미지 요청(`GET %s%s`)의 두 `%s`에 무엇이 들어가는지는 "미확인"으로 남겼다. 그 공백을 메워, 가짜 장비(나중에 실장비 대조)로 실제 펌웨어를 받을 수 있는 정확한 경로를 알아내는 것이 목적이다.

분석은 정적(디컴파일)만 한다. 장치를 실행하거나 다원에 실제 요청을 보내는 것은 이 작업의 범위가 아니다(결과 경로를 가짜 장비로 시험하는 것은 사용자 확인 뒤 별도).

## 완료 조건

- C1. 덤프에서 FOTA URL을 파싱하는 함수(`UpdateUrlParser` 등)를 찾아, 받은 URL 문자열을 어떤 조각(스킴·호스트·포트·경로·버전 등)으로 나누는지 디컴파일 근거와 함께 밝힌다. 밝히지 못한 조각은 "미확인"으로 남긴다.
- C2. 버전 확인 요청(`GET %s/version HTTP/1.1`)의 `%s`에 들어가는 값이 받은 URL의 어느 부분인지 밝힌다. 가짜 장비가 보낸 `{URL}/version`과 다른지 같은지 판정한다. 덤프에서 정할 수 없으면 "미확인"으로 남긴다.
- C3. 이미지 요청(`GET %s%s HTTP/1.1`)의 두 `%s`에 각각 들어가는 값을 밝힌다. 두 번째 조각에 파일 이름(슬롯별 이름 포함)이 붙는지, 붙는다면 그 이름이 어떻게 정해지는지(상수 문자열·버전·슬롯 번호 등)를 디컴파일 근거와 함께 밝히거나, 덤프에서 정할 수 없으면 "미확인"으로 남긴다.
- C4. `/version` 응답을 장치 버전과 비교해 받기를 시작하는 규칙(`CheckVersion` 등)을 밝히거나 "미확인"으로 남긴다.
- C5. MQTT `w`/`chg`의 `/5/0/*`를 FOTA 설정으로 받는 처리(`Set_UpgradeResourceData`)가 `/5/0/1`에 받은 값을 URL로 쓰는지 확인하고, 받은 리소스 번호를 밝힌다. 덤프에서 정할 수 없으면 "미확인"으로 남긴다.
- C6. 위 결과로 다원 URL `http://dwapi.dawonai.com:18446/DAWONDNS/B540_W/1.01.34`에 대해 장치가 실제로 보낼 요청 경로의 예를 적는다(밝혀진 범위 안에서. 미확인이 남으면 무엇이 비어 있어 경로를 확정할 수 없는지 적는다).
- C7. 위 내용을 `docs/reference/b540-fota.md`에 관찰·추정·미확인 표기 규칙대로 반영하고, 근거(함수 주소·형식 문자열·오프셋)를 적는다. 다원 서버 호스트·포트는 다른 참조 문서와 같이 그대로 적고, 실장비 mac·계정·키와 덤프 경로만 뺀다.
