# B540 FOTA 요청 경로 펌웨어 분석 결정

### D001 분석을 끝까지(인자 추적) 하고, 주소 모델을 경험적으로 바로잡는다
- 단계: plan
- 질문: plan 검토 1회차 지적. plan의 슬롯 B 주소 매핑이 틀렸다(검토 의견: 검증된 적재 규칙과 0x80000 어긋남). 메인이 원격 `.dis`로 확인하니 핵심은 맞으나 원인이 달랐다 — FOTA 형식 문자열(`GET %s%s` 등)은 irom이 아니라 DRAM(`0x3ffe9a17`)이고, 기존 `appB-irom.dis`는 그 문자열을 `l32r`로 싣는 코드를 포함하지 않는다(요청 생성이 SDK `upgrade_lib`이거나 앱이 완성 url을 넘기는 방식). 매핑과 분석 깊이를 정해야 했다.
- 선택지:
  - A. 깊게: plan 주소 모델을 이미지 세그먼트 헤더에서 도출한 값으로 바로잡고, 필요한 범위를 다시 디스어셈블해 `GET %s%s`의 두 조각을 끝까지 추적한다.
  - B. 구조만: 깊은 인자 추적은 접고, 이미 확인한 구조적 사실(FOTA 흐름·설정 키·URL 분할·문자열 DRAM 위치·404는 서버에 테스트 장치용 이미지가 없을 가능성)만 `b540-fota.md`에 반영하고 정확한 `%s`는 미확인으로 둔다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: spec C1~C6을 실제로 충족하려면 정확한 요청 경로가 필요하고, 사용자가 404 원인을 끝까지 보기를 원했다. B는 빠르지만 "왜 404인가"의 정확한 답(경로 구성)을 못 준다.
- 경험적으로 확정한 매핑(이미지 세그먼트 헤더, 바깥 EA 0x81000 + 안쪽 E9 0xd61a0):
  - irom0: 파일 0x81010~0xd61a0. 기존 `appB-irom.dis`는 0x40201000에 감쌈(`.dis` 주소 = 파일 + 0x40180000). 펌웨어 참 링크 주소 = 파일 + 0x40200000(= `.dis` 주소 + 0x80000), `b540-mqtt-topic.md`의 0x402cxxxx 표기와 같은 기준.
  - IRAM: vaddr 0x40100000, 파일 0xd61b0, 길이 0x7bf0(`appB-iram.dis`).
  - DRAM: seg2 vaddr 0x3ffe8000(파일 0xddda8), seg3 vaddr 0x3ffe8db0(파일 0xdeb5c). FOTA 문자열은 seg3.
- 반영: plan.md 요약·결정·인터페이스·데이터·검증 전략

### D002 깊은 인자 추적은 objdump 수동 판독을 먼저 하고, 막히면 Ghidra를 설치해 쓴다
- 단계: plan
- 질문: plan 검토 3회차 지적 1. C2·C3의 핵심(형식 문자열의 베이스+오프셋 간접 참조, sprintf 인자 데이터플로)은 디컴파일러가 결정적으로 유리한데 plan은 objdump 수동 판독만 전제했다(검토 의견). 자매 문서 b540-mqtt-topic.md는 같은 작업을 Ghidra 12.2 headless(Xtensa:LE:32)로 했다. 메인 확인: 그 Ghidra는 이 원격 서버에 없고(analyzeHeadless·Xtensa 모듈 없음, Java 21만), 쓰려면 Ghidra + 서드파티 Xtensa 프로세서 모듈 설치가 필요하다.
- 선택지:
  - A. 단계적: objdump로 먼저 추적하고, 베이스+오프셋이 손으로 안 풀리면 그때 Ghidra+Xtensa를 설치해 디컴파일로 넘어간다.
  - B. 지금 설치: Ghidra+Xtensa를 먼저 설치해 C2·C3를 처음부터 디컴파일로 한다.
- 결정: A(사용자 선택, 2026-11-20)
- 이유: 요청 생성 함수 하나의 sprintf 인자(베이스 l32r + addi 오프셋)는 objdump로도 읽을 만하고, 막힐 때만 설치하면 설치 수고를 아끼면서 "C2·C3 미확인" 위험을 없앤다. B는 proven이지만 설치가 먼저 든다.
- 반영: plan.md 결정·인터페이스·데이터·검증 전략·원칙 점검

### D004 LFota_* 키→버퍼 매핑을 원격 디스어셈블로 재확인해 적는다
- 단계: 구현
- 질문: 구현 후 검토 1회차 지적 2. b540-fota.md 3절 2항이 "LFota_Url→host, LFota_Addr→path"를 관찰로 단정했는데 2절 추정 의미(Url=이미지 URL/경로, Addr=서버 주소)와 반대이고 작업 기록에 개별 매핑 근거가 약했다(검토 의견).
- 선택지:
  - A. 일반화·추정 표기: 개별 host/path 귀속을 빼고 "같은 버퍼로 수렴"으로 일반화, 귀속은 추정.
  - B. 원격 재확인: 원격 디스어셈블로 각 키의 strncpy 대상 버퍼와 그 버퍼의 역할을 다시 확인해 정확히 적는다.
- 결정: B(사용자 선택, 2026-11-20)
- 재확인 결과(관찰): 설정 파서 0x4029d1a5가 LFota_Url→0x3fff1750, LFota_Addr→0x3fff17b5, LFota_Port→0x3fff181a, LFota_Version→0x3fff1820에 strncpy(각 키 l32r 4021d1a5/4021d219/4021d2cd 부근에서 버퍼 l32r 4021d1da/4021d24b/4021d2a6/4021d2ff). GET 빌더(4021e154)가 a4(첫 %s=GET 경로)=0x3fff17b5, a6(Host)=0x3fff1750을 쓰므로 0x3fff17b5=경로·0x3fff1750=host. 따라서 LFota_Url 값→host 필드, LFota_Addr 값→GET 경로 필드로 키 이름과 역할이 반대다. 2절 추정 의미를 이 관찰로 정정.
- 반영: b540-fota.md 2절 표·3절 2항
