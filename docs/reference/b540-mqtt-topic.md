# B540 MQTT 토픽 및 메시지

- 작성: 2026-11-03 (KST)
- 근거: 1~3절은 B540 플래시 덤프의 정적 문자열·설정 섹터 바이트. 3절 오퍼레이션 표의 `r`·`e`·`d`·`tisyn`·`rg`·`drg` 수정과 「서버 → 장치 수신 분기」·「시간 동기」·「오브젝트 99 리소스 처리」 세 절은 2026-11-19 Ghidra 12.2 headless(프로세서 `Xtensa:LE:32`)로 슬롯 B를 정적 디컴파일한 결과다(REA `open_binary`는 Xtensa를 허용하지 않아 Ghidra를 썼다. 메모리 배치는 「서버 → 장치 수신 분기」 절). 그 밖의 B540 코드 흐름 디컴파일과 B540 실제 브로커 통신 관찰은 하지 않았다. 5절은 M130-W 실장비 3대가 내장 브로커(`MqttBrokerHostedService`)에 보낸 메시지 로그(2026-11-19).
- 표기: **관찰**(덤프(문자열·바이트, 그리고 디컴파일에 직접 나타난 동작) 또는 실장비 통신 로그에 직접 존재), **추정**(관찰을 동작과 연결한 해석), **미확인**. 개인정보·키 값은 마스킹했다.
- 관련 문서: [REST API](b540-rest-api.md), [FOTA](b540-fota.md), [TCP 설정 수신](b540-tcp-config.md), [분석 색인](b540-rea-analysis.md)

추정 치환값:

- 첫 `%s`: 설정 섹터 `0x7c0ec`의 `dwd` → `dwd.v1/...`. 설정 키 `topic`(TCP 설정 수신)으로 바뀔 수 있다.

조합 예(추정): 구독 `dwd.v1/iot-server/DAWONDNS-B540_W-<mac>/#`, 발행 `dwd.v1/DAWONDNS-B540_W-<mac>/iot-server/json`.

## 3. 메시지 형식

LwM2M SenML 유사 JSON이다.

```json
{"sid":"0","msg":{"o":"<operation>","e":[{"n":"<path>","sv":"<string value>"}]}}
```

- `sid`: 세션/요청 ID 추정
- `o`: 오퍼레이션 코드
- `e`: 리소스 요소 배열, `n`은 `/<object>/<instance>/<resource>` 경로(`/%d/%d/%d` 파싱 문자열 관찰), `sv`는 문자열 값

### 오퍼레이션 코드

| `o` 값 | 관찰 위치 | 대응 함수 이름(관찰) | 추정 방향·의미 |
|---|---|---|---|
| `rg` | 등록 JSON | `MqttTypeRegister` | 장치 → 서버, 등록. 서버 → 장치로도 수신(분기 1, 의미 미확인) |
| `drg` | `0xe0842` | `MqttTypeDeregister`, `deregister` | 등록 해제. 서버 → 장치로도 수신(분기 2, 의미 미확인) |
| `tisyn` | 타임싱크 JSON | `timesync` | 장치 → 서버, 시간 동기 요청. 서버 → 장치 수신 분기에 없음(응답은 `w`, 「시간 동기」 절) |
| `w` | `0xe084e` | `MqttTypeWrite` | 서버 → 장치, 리소스 쓰기 |
| `chg` | `0xe0846` | `MqttTypeChange` | 서버 → 장치, 변경 |
| `reb` | `0xe084a` | `MqttTypeReboot` | 서버 → 장치, 재부팅 |
| `notify` | `0xe0881` | `ElmentsSendNotifcation`, `Report` | 장치 → 서버, 상태 보고 |
| `n` | M130-W 실통신(5절) | — | 장치 → 서버, 상태 보고(추정: `notify`의 짧은 형태. 토픽 접미가 `notify/json`) |
| `r` | 디컴파일 `0x402c8890`(문자열 `"r"`) | `MqttTypeRead`, `Request_Read` | 서버 → 장치, 읽기(분기 3) |
| `e` | 디컴파일 `0x402c8890`(문자열 `"e"`) | `MqttTypeExecute` | 서버 → 장치, 실행(분기 5). 추정: 함수 이름과 번호 대응 |
| `d` | 디컴파일 `0x402c8890`(문자열 `"d"`) | `MqttTypeDelete` | 서버 → 장치, 삭제(분기 6). 추정: 함수 이름과 번호 대응 |

### 서버 → 장치 수신 분기 (관찰, 디컴파일)

슬롯 B 메모리 배치(재현용): IROM 파일 `0x81010`~`0xd61a0` → `0x40281010`(외부 링크 주소 = `0x40200000` + 파일 오프셋), IRAM 파일 `0xd61b0`(길이 `0x7bf0`) → `0x40100000`, DRAM 파일 `0xddda8`(`0xdac`) → `0x3ffe8000`, `0xdeb5c`(`0x212c`) → `0x3ffe8db0`. 이하 주소는 이 배치의 링크 주소다.

- 수신 메시지 처리 `0x402c89cc`(로그 함수 이름 `ServerToDevice_MessageSet`)는 `msg` 안의 키 `o`·`r`·`e`·`reason`을 비교하고, `o` 값을 오퍼레이션 분기 `0x402c8890`에 넘긴다.
- `0x402c8890`이 정하는 번호: `rg`=1, `drg`=2, `r`=3, `w`=4, `e`=5, `d`=6, `chg`=7, `reb`=8, 그 밖은 `0xffff`. `tisyn`·`notify`·`n`은 이 분기에 없다.
- 실제 비교 순서는 번호와 다르다: `rg` → `drg` → `chg` → `reb` → `r` → `w` → `e` → `d`.
- 각 비교는 ROM `0x40002ac8`을 상수 문자열에 부른 결과를 ROM `0x40002ab8`의 세 번째 인자로 넘기는 구조다(관찰). 추정: 두 ROM 함수는 `strlen`·`strncmp`이고, 따라서 상수 길이만큼만 보는 접두 비교라 비교 순서가 판정에 영향을 준다(예: `reb`를 `r`보다 먼저 비교).

### 등록 메시지 (관찰)

```json
{"sid":"0","msg":{"o":"rg","e":[
 {"n":"/3/0/0","sv":"%s"},{"n":"/3/0/1","sv":"%s"},{"n":"/3/0/2","sv":"%s"},
 {"n":"/3/0/3","sv":"1.01.34"},
 {"n":"/3/0/997","sv":"1"},{"n":"/3/0/998","sv":"1.0"},{"n":"/3/0/999","sv":"1"}]}}
```

`/3/0/*`는 LwM2M Device 객체 경로와 일치한다(0 제조사, 1 모델, 2 시리얼, 3 펌웨어 버전). `997~999`는 제조사 확장으로 추정. `/3/0/3`의 고정 버전은 슬롯 A `1.01.30`, 슬롯 B `1.01.34`이며, 설정 섹터 `0x7c2f5` 버전은 `1.01.34`다.

### 시간 동기 (요청 관찰, 응답 처리 디컴파일)

```json
{"sid":"0","msg":{"o":"tisyn","e":[]}}
```

장치 → 서버 요청은 위 고정 문자열이고(관찰), 토픽 접미는 `timesync/json`이다(`0x4029a95c`·`0x4029ae54`가 형식 `%s%s/json`에 발행 접두와 `timesync`를 넣어 토픽을 만든다, 관찰. 2절 표의 두 문자열). 서버 → 장치 수신 분기에 `tisyn`은 없고, 응답은 `w`(리소스 쓰기)로 받는다.

- **응답 처리**(관찰): 서버가 `w`로 `/99/0/1`에 값을 쓰면 `0x402c9300`이 값 문자열을 시간 저장소(`ctx+0x298c`, `0x4029b5c4`)에 복사하고 동기 완료 플래그(`ctx+0x43c`)를 1로 만든다. 이 플래그를 1로 쓰는 곳은 디컴파일한 함수 전체(2415개)에서 이 한 곳이고, 0으로 되돌리는 곳은 찾지 못했다. 오브젝트 99·인스턴스 0·리소스 1 경로는 「오브젝트 99 리소스 처리」 절.
- **값 해석**: `0x4029b0e0`이 저장 값(숫자로 변환)에 `0x7e90`(32400)을 더한 뒤 ROM `0x4000e21c`·`0x4000e268`을 상수 3600·24, 60·60, 60, 86400·7과 함께 불러 시·분·초(`ctx+0x29a1`~`0x29a3`)와 요일 비트(`ctx+0x29a0`)를 만든다(관찰). 두 ROM 함수를 나눗셈·나머지로 보면(추정) 시 = (t/3600)%24, 분 = (t/60)%60, 초 = t%60, 요일 번호 = (t/86400)%7이고, 요일 번호 0~6을 비트 `0x04`·`0x02`·`0x01`·`0x40`·`0x20`·`0x10`·`0x08`로 바꾼다(관찰). `0x4029b188`은 저장된 10진수 문자열을 끝자리부터 1 올린다(관찰). 추정: 값은 UTC 기준 Unix epoch 초의 10진수 문자열이고, +32400초는 KST(+9시간) 보정이며, 장치는 받은 뒤 이 문자열을 스스로 올려 시계를 유지한다. 요일 비트를 일=`0x40`부터 토=`0x01`까지의 순서로 보면 요일 번호 0이 목요일이 되어 epoch 0일(1970-01-01, 목요일)과 맞는다.
- **송신 주기**(`0x4029ae54`, 로그 함수 이름 `CheckReport_timer`, 관찰): 틱마다 송신 카운터(`ctx+0x29a4`)를 올리고 `0x1c1f`(7199)를 넘으면 동기 플래그와 관계없이 `tisyn`을 보내고 카운터를 0으로 둔다.
  - 동기 플래그가 1이면 그대로 두므로 다음 송신은 7200틱 뒤다. 즉 동기 후에도 7200틱마다 `tisyn`을 보낸다.
  - 동기 플래그가 1이 아니면 간격 값(전역 `0x3ffe8774`)을 300 미만일 때 두 배로, 300 이상일 때 300으로 바꾸고 `TimeSynCnt %d` 로그를 남기며 카운터를 `7200 − 간격`으로 맞춰 간격만큼 뒤에 다시 보낸다.
  - `ctx+0x444`가 1이 아니면 그 틱에는 카운터를 `0x1c02`(7170), 간격을 30으로 두고 끝낸다. 추정: `ctx+0x444`는 MQTT 연결 상태.
  - 부팅 함수 `0x4029c0dc`(로그 `mainmode_Boot`)는 간격을 1, 카운터를 `0x1c1f`(7199)로 둔다(DRAM 초기값 30을 덮어씀).
  - 위 상수와 분기에서 나오는 동기 전 송신 간격 수열(관찰): 부팅 뒤 첫 틱에 이미 `ctx+0x444`가 1이면 곧바로 보내고 간격이 2·4·8·…·256·512 다음 300을 유지한다. 미연결 틱을 지나면 연결 뒤 30틱 만에 첫 송신을 하고 간격이 60·120·240·480 다음 300을 유지한다. 실제로 어느 수열이 나타나는지(부팅 뒤 첫 틱 때 연결 여부)는 미확인이다.
  - `0x4029a95c`도 `ctx+0x444`가 1일 때 같은 `tisyn`을 보낸다(관찰, 호출 시점은 미확인).
- **`/99/0/0`**(관찰): 오퍼레이션과 관계없이 송신 카운터를 0으로 되돌리고(다음 `tisyn` 송신이 늦어진다) 값의 변환 결과를 `ctx+0x130`에 저장한다.
- **`MqttTypeWrite` 뒤 보고**(`0x402cb7cc`, 관찰): 요소를 오퍼레이션 4로 처리한 뒤 `ctx+0x438`이 0이고 동기 플래그가 1이면 보고 관련 함수(`0x402ca8f0`·`0x402ca7b8`)를 부른다.
- **응답 메시지 예**(추정, 예 전체): `{"sid":"0","msg":{"o":"w","e":[{"n":"/99/0/1","sv":"1795000000"}]}}`. 값이 `sv` 키로 담긴다는 것과 `sid` 값은 수신 파서에서 확인하지 못했다(3절 메시지 형식에 따른 추정).
- **틱 단위**(미확인): `0x4029ae54`를 부르는 타이머 주기를 확인하지 못했다. 1초라면 동기 후 송신 주기는 2시간이다(추정).

### 오브젝트 99 리소스 처리 (관찰, 디컴파일)

요소마다 `0x402ca708`이 오브젝트 번호가 99(`0x63`)이면 `0x402ca6c0`을, 거기서 인스턴스가 0이면 `0x402c9300`을 불러 리소스 번호로 나눈다(관찰). 같은 분기에서 오브젝트 3·4·5·100은 다른 처리 함수로 간다. 요소 처리는 `MqttTypeWrite`(오퍼레이션 4)와 `MqttTypeRead`(`0x402cb548`에 오퍼레이션 3) 등 오퍼레이션 번호를 넘겨 같은 경로를 탄다.

| 리소스 | 저장 위치 | `w` 검사 | 응답 값 버퍼(`ctx + idx*0x204 + 0x980 + 0x12`) | `0x4029ab2c` 호출 |
|---|---|---|---|---|
| 0 | 변환 결과 → `ctx+0x130`, 송신 카운터 `ctx+0x29a4` = 0 | 없음 | 쓰지 않음 | 항상 |
| 1 | 값 문자열 → 시간 저장소 `ctx+0x298c`, 동기 플래그 `ctx+0x43c` = 1 | 있음(`w`일 때만 저장) | 쓰지 않음 | 없음 |
| 2 | 변환 결과 → `ctx+0x230` | 없음 | 쓰지 않음 | 항상 |
| 3 | 변환 결과 → `ctx+0x234` | 없음 | 쓰지 않음 | 항상 |
| 4 | 변환 결과 → `ctx+0x238` | 없음 | 쓰지 않음 | 항상 |
| 5 | 없음. 전역 카운터 `0x3fff11dc` = 0 | 없음 | 전역 카운터의 0 전 값(문자열) | 없음 |
| 10 | 값 15바이트 → `ctx+0xce` | 있음(`w`일 때만 저장) | `ctx+0xce` 15바이트 | `w`일 때 |
| 11 | 값 15바이트 → `ctx+0xdd` | 있음(`w`일 때만 저장) | `ctx+0xdd` 15바이트 | `w`일 때 |
| 20 | 없음 | 없음 | `ctx` 앞 32바이트 | 없음 |

- 그 밖의 리소스 번호는 처리하지 않는다(관찰).
- 공통 부수 기록(의미 미확인): 리소스 1·10·11은 `ctx+0x588`에 `ctx+0x1db8` 문자열을, 1을 뺀 리소스는 응답 상태 버퍼(`ctx + idx*0x204 + 0xa80 + 0x11`)에 전역 `0x3fff3fa4` 문자열을 기록한다.
- "변환 결과"는 포인터 리터럴 `0x4029c8f4`가 가리키는 함수의 반환값이다. 추정: 문자열 → 정수 변환.
- `/99/0/2`·`3`·`4`(보고 조건 값): `0x4029ae54`는 `tisyn`을 보내지 않는 틱(카운터 ≤ 7199)에 `ctx+0x438`이 1이면 보고 판정을 한다. 별도 카운터 `ctx+0x299c`를 `ctx+0x230`과, 전역 카운터 `0x3fff11dc`를 `ctx+0x234`와 비교하고, `ctx+0x238`은 비교 함수 `0x4029adc0`의 인자로 넘겨 보고 함수(`0x402ca7b8`)를 부를지 정한다(관찰). 부팅 함수 `0x4029c0dc`는 세 값을 범위 검사해 기본값을 넣고(`0x230`: 1~3600 밖이면 300, `0x234`: 11~14400 밖이면 3500, `0x238`: 1~100 밖이면 20) `MinTime = %d MaxTime = %d CheckPer = %d` 로그를 남긴다(관찰). 추정: 세 값은 보고 조건으로, `MinTime`·`MaxTime`은 최소·최대 보고 간격, `CheckPer`는 변화 기준이다.
- `/99/0/5`: 전역 카운터 `0x3fff11dc`의 현재 값을 응답 값 버퍼에 문자열로 기록한 뒤 0으로 만든다(읽은 뒤 초기화, 관찰).
- 리소스 10·11·20과 `0x4029ab2c`의 의미는 미확인이다.

- 시간 동기 응답 값이 담기는 JSON 키(`sv` 추정)와 `sid` 값(서버 → 장치 수신 파서에서 요소 값 키를 확인하지 못함). M130-W는 `sv` 키와 요청 `sid`(`"0"`)로 보낸 응답으로 동기됨을 관찰했다(5절 「시간 동기 응답」). B540은 응답 뒤 재요청이 멈춘 것만 관찰했다(아래 항목)

### 시간 동기 응답 (2026-11-21)

서버가 `tisyn`마다 서버 → 장치 토픽 `dwd.v1/iot-server/DAWONDNS-M130-W-{mac}`에 retain 없이 `{"sid":"0","msg":{"o":"w","e":[{"n":"/99/0/1","sv":"<UTC Unix epoch 초>"}]}}`를 보내고(GitHub #21), 서버 로그로 장치 1·2·3의 `tisyn` 시각을 봤다.

- 응답 형식은 3절 「시간 동기」의 추정(`w`, `/99/0/1`, 값 키 `sv`, 요청 `sid`)대로 받아들여졌다(관찰). 서버 시작 직후 장치마다 `tisyn` 한 번에 응답한 뒤, 세 대 모두 정확히 약 3600초 동안 `tisyn`을 보내지 않았고 그 뒤 다시 한 번씩 보냈다(관찰. 그 사이 접속 끊김 기록 없음). 동기 전에는 응답을 보내도 2·4·8·16초 간격으로 다시 요청했다(2026-11-20 관찰).
  판정(GitHub #21 C7): 장치마다 첫 응답 로그 시각부터 60분을 구간으로 두고, 구간 시작부터 첫 `tisyn`까지·이웃한 `tisyn` 사이·마지막 `tisyn`부터 구간 끝까지의 간격 가운데 하나라도 20분을 넘으면 동기 완료로 본다. 구간 안에 접속 끊김 기록은 없었다.

  | 장치 | 첫 응답 로그 | 구간 안 `tisyn` | 구간 시작 → 첫 `tisyn` | 판정 |
  |---|---|---|---|---|
  | 장치 1 | 12:55:57.425 | 13:55:57.350 | 약 3599.9초 | 동기 완료 |
  | 장치 2 | 12:55:57.423 | 13:55:57.345 | 약 3599.9초 | 동기 완료 |
  | 장치 3 | 12:55:58.109 | 13:55:58.068 | 약 3599.96초 | 동기 완료 |

- 동기 뒤 재요청 주기는 약 3600초다(관찰, 한 주기만 봄). 추정: 1초 틱으로 3600틱 주기. B540 분석본(3절)의 7200틱과 다르다.
- 2026-11-20~21에는 같은 형식의 응답에도 장치가 반응하지 않았다. 서버(MQTTnet 브로커)가 PUBLISH 하나를 머리와 페이로드로 나눠 TLS 레코드 두 개로 보내고 있었고(TLS 포트 패킷 캡처로 관찰), 분할을 끄자(GitHub #25) 위처럼 동기됐다. 추정: 장치 MQTT 라이브러리(B540은 1절의 esp_mqtt 계열 추정)가 여러 수신에 걸친 패킷을 합치지 않는다. 장치 펌웨어에서 직접 확인하지는 않았다.
