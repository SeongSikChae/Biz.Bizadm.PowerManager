## 9. 심층 분석 재개: 실행 경계와 B540-09

### 진행 원칙 및 우선순위

- 사용자가 별도 Rocky Linux에서 명령을 실행한다. 에이전트는 SSH 또는 Linux MCP로 직접 접속하지 않는다.
- 실행 안내는 단계 ID·목적·복사 가능한 명령·부작용·필요한 결과를 채팅 응답에 직접 제공한다. 문서는 승인·증거·판단·진행 상태를 병행 기록하는 용도로 갱신하며, 명령 실행을 위해 문서만 찾아보도록 안내하지 않는다.
- 기존 Node.js `22.22.0`, REA `6.5.0`, Rust/Cargo, Binwalk `3.1.0` 설치와 B540-06~08 증거를 재사용한다. 설치·시그니처 검사·전체 문자열 집계를 반복하지 않는다.
- 이전 실행 EUID는 `0`이다. 사용자 홈 아래의 경로는 산출물 위치를 뜻할 뿐 일반 사용자 실행을 뜻하지 않는다. 계정 전환, sudo, chown, 시스템 설정 변경은 하지 않는다.
- 조사 순서: 부트 선택 메타데이터와 부트로더 분기 → 검증된 슬롯별 주소 매핑 및 버전·코드 차이 → MQTT/TLS → GPIO·UART·계량·보정. 필요한 코드 분석 환경의 추가 승인은 별도로 받는다.
- EA 헤더의 네 번째 바이트 `1`과 `2`는 관찰값이며 현재 활성 슬롯을 나타내는 플래그로 채택하지 않는다. SDK 시스템 설정 후보와 부트로더의 실제 읽기·검증·선택 분기가 연결되어야 덤프 기준 선택을 판단할 수 있다.
- 덤프에서 선택 규칙을 확인하더라도 실제 장치의 현재 실행 슬롯과 동일하다고 단정하지 않는다. UART 부팅 로그 등 시점이 확인되는 실행 증거가 필요하다.

### B540-09: 부트 선택 조사를 위한 최소 영역 파일화 — manifest 검토 완료

**승인 관찰:** 사용자가 제시한 B540-09 범위만 승인했다. 아래 네 영역 및 manifest 생성에 한정하며 다른 영역 추출, 도구 설치, 장치 실행, 외부 접속 승인은 포함하지 않는다.

**목적:** 기존에 구조를 확인한 부트 이미지와 아직 해석하지 않은 후미 시스템 설정 후보를 오프라인 코드·메타데이터 분석에 사용할 수 있도록 분리한다. 이번 단계만으로 활성 슬롯을 결정하지 않는다.

**원본:** 분석 호스트의 덤프 사본, 덤프 기대 SHA-256.

**제안하는 정확한 파일화 범위:** 모든 범위는 파일 오프셋이며 끝은 exclusive이다.

- `[0x00000, 0x00f10)`: `3,856`바이트, 기존 검증 E9 부트 이미지 → 부트 E9 추출본.
- `[0xfd000, 0xfe000)`: `4,096`바이트, 시스템 설정 레코드 후보 → fd 설정 레코드 추출본.
- `[0xfe000, 0xff000)`: `4,096`바이트, 시스템 설정 레코드 후보 → fe 설정 레코드 추출본.
- `[0xff000, 0x100000)`: `4,096`바이트, 후미 선택 메타데이터 후보 → ff 후미 제어 추출본.
- 총 `16,144`바이트. 후미 세 섹터의 역할은 ESP8266 SDK 레이아웃에 비춘 **작업 가설**이며 덤프의 코드 참조로 확인하지 않았다. `0xfb000`, `0xfc000`, `0x7e000`, 두 앱 이미지 및 제품 설정 섹터는 이번 추출 범위에서 제외한다. 필요하면 근거와 함께 별도 승인을 요청한다.

**출력 경로:** 작업 폴더 아래 새 B540-09 결과 폴더 아래 위 네 `.bin`과 manifest JSON. 기존 파일을 덮어쓰지 않는다.

**권한·부작용:** 새 디렉터리 `0700`, 파일 `0600`으로 생성하며 소유자는 실제 실행 EUID를 따른다. EUID 0으로 실행하면 root 소유 파일이다. 원본은 읽기만 한다. 설정 후보에는 Wi-Fi 자격증명·장치 식별자가 들어 있을 수 있으므로 `.bin` 원문은 채팅에 전달하지 않는다. 설치, 다운로드, 외부 서버 접속, 펌웨어 실행, 장치 접근, 계정·소유권 변경은 포함하지 않는다.

**승인 후 실행할 명령:** 다음은 제안 명령이며 현재 실행 결과가 아니다. Python 표준 라이브러리만 사용한다. 셸 터미널 기록은 별도로 남을 수 있다.

```bash
/bin/python3 - <<'PY'
import hashlib
import json
import os
from pathlib import Path
import tempfile

source = Path('<덤프 사본>')
base = Path('<작업 폴더>')
expected = '<덤프 SHA-256>'
blob = source.read_bytes()
digest = hashlib.sha256(blob).hexdigest()
if len(blob) != 1048576 or digest != expected:
    raise SystemExit('중단: 원본 크기 또는 SHA-256 불일치. 추출 파일을 생성하지 않았습니다.')
if not base.is_dir():
    raise SystemExit('중단: 기존 분석 디렉터리가 없습니다. 설치 또는 경로 생성을 하지 않습니다.')

os.umask(0o077)
out = Path(tempfile.mkdtemp(prefix='B540-09-', dir=str(base)))
ranges = [
    ('<부트 E9 추출본>', 0x00000, 0x00f10),
    ('<fd 설정 레코드 추출본>', 0xfd000, 0xfe000),
    ('<fe 설정 레코드 추출본>', 0xfe000, 0xff000),
    ('<ff 후미 제어 추출본>', 0xff000, 0x100000),
]
manifest = {
    'action_id': 'B540-09',
    'kind': 'Python 보조 추출 기록; REA Evidence 아님',
    'euid': os.geteuid(),
    'source': str(source),
    'source_size': len(blob),
    'source_sha256': digest,
    'output_directory': str(out),
    'files': [],
}
for name, start, end in ranges:
    part = blob[start:end]
    target = out / name
    with target.open('xb') as stream:
        stream.write(part)
    manifest['files'].append({
        'name': name,
        'start': hex(start),
        'end_exclusive': hex(end),
        'size': len(part),
        'sha256': hashlib.sha256(part).hexdigest(),
        'mode': oct(target.stat().st_mode & 0o777),
    })

post_digest = hashlib.sha256(source.read_bytes()).hexdigest()
manifest['source_sha256_after'] = post_digest
manifest['source_identity_ok'] = post_digest == expected
text = json.dumps(manifest, ensure_ascii=False, indent=2)
with (out / '<manifest>').open('x', encoding='utf-8') as stream:
    stream.write(text + '\n')
print(text)
if not manifest['source_identity_ok']:
    raise SystemExit('중단: 종료 시 원본 해시 불일치. 산출물을 확정 증거로 사용하지 마십시오.')
PY
```

**필요한 결과:** 승인 후 실행한 manifest JSON 내용, 명령 성공/실패 여부, 오류가 있으면 오류 출력. 원시 `.bin`과 설정값은 전달하지 않는다. 전후 해시 검사는 새 산출물의 동일성을 위한 검사이며 기존 형식·시그니처 분석을 재실행하는 것이 아니다. 두 번의 해시 일치가 원자적 파일 잠금이나 덤프 획득 시점의 장치 상태를 증명하지는 않는다.

**다음 판단:** 승인 여부와 실행 결과를 받은 뒤 부트로더의 실제 Xtensa 코드 분석 방법을 결정한다. 제한된 파일화만으로 명령어 디코딩·함수 흐름·활성 슬롯을 확인했다고 기록하지 않는다. Java/Ghidra 또는 Xtensa 도구 설치가 필요하면 버전·다운로드 출처·설치 경로·임시/캐시 경로·권한·추가 분석 산출물 범위를 별도로 제안하고 승인받는다. 문서에 기록된 REA의 x86/6502 제한을 우회하기 위해 잘못된 아키텍처 프로필을 사용하지 않는다.

**런타임 증거 가용성:** 사용자는 현재 보유한 실제 B540 장치·UART 부팅/작동 로그·네트워크 캡처가 없다고 답했다. 따라서 현재는 정적 코드와 덤프 메타데이터로 분석하며 실제 실행 슬롯·통신·물리 핀 동작의 런타임 검증은 할 수 없다. 향후 각 미확인 항목에 필요한 증거를 명시한다. 새 장치 실행, UART 연결, 패킷 수집, 인터넷 통신을 요청하거나 승인된 것으로 취급하지 않는다.

### B540-09 결과 검토

**관찰:** 사용자가 manifest JSON 전체를 채팅으로 전달했다. Python 보조 결과이며 새로운 REA Evidence는 아니다.

- 결과 디렉터리: B540-09 결과 폴더.
- EUID `0`, 원본 크기 `1048576`바이트, 전후 SHA-256은 모두 기존 기대값과 일치. `source_identity_ok: true`.
- 부트 E9 추출본: `[0x00000, 0x00f10)`, `3856`바이트, SHA-256 `ef768550462a47fe486715f6e78494cb862d269c4ca700882e5abf0e83747d9c`.
- fd 설정 레코드 추출본: `[0xfd000, 0xfe000)`, `4096`바이트, SHA-256 값은 적지 않음(개인 설정 영역).
- fe 설정 레코드 추출본: `[0xfe000, 0xff000)`, `4096`바이트, SHA-256 값은 적지 않음(개인 설정 영역).
- ff 후미 제어 추출본: `[0xff000, 0x100000)`, `4096`바이트, SHA-256 `e68e0f2efafe0bf8e431a4649e2daef80d60577f993945fd9b263e752af29474`.
- 네 파일 mode는 모두 `0o600`. 디렉터리 mode와 개별 파일 UID는 manifest에 없어 직접 검증하지 않았다. EUID 0으로 생성했으므로 root 소유로 예상하되 일반 사용자 권한으로 실행했다고 표현하지 않는다.
- 명령 종료 코드는 이번 메시지에 포함되지 않았다. JSON이 끝까지 생성된 점과 명시적 해시 검증 결과는 관찰했지만 종료 코드 `0`을 전달받았다고 기록하지 않는다.
- 로컬에 바이트 동일한 원본 manifest를 첨부받지는 않았다. 이후 결과도 산출물 자체의 식별 해시를 포함한다.

**해석과 한계:** `fd`/`fe` 두 섹터의 해시가 서로 다르므로 바이트 동일하지 않다. 최신성, 선택 순번, 체크섬 유효성, 부트 슬롯은 해시만으로 판단할 수 없다. 승인된 파일화는 완료된 것으로 보고 재실행하지 않는다.

### B540-10: 후미 제어 후보와 부트 상수 위치 조사 — 결과 검토 완료

**목적:** 기존 B540-09 파일만 읽어 후미 제어 후보의 구조 단서를 확보하고, 부트로더에서 슬롯/섹터 관련 값이 나타나는 위치를 좁힌다. 실제 명령어 참조·함수 흐름 검증이 아니라 다음 Xtensa 디스어셈블 범위를 정하기 위한 보조 조사이다.

**입력 범위:** B540-09의 네 파일. 원본 전체·다른 영역을 다시 추출하지 않는다. 파일별 기대 크기·해시를 검사해 입력 동일성을 검증한다.

**출력 범위:** ff 후미 제어 추출본 첫 32바이트의 상대 위치별 little-endian 32비트 값과 hex. 출력 창과 겹치는 길이 4 이상의 printable ASCII 연속 영역은 마스킹하고 해당 32비트 값도 생략한다. 필터가 모든 민감정보를 탐지하는 것은 아니므로 전달 전에 사용자가 검토한다. `fd`/`fe`는 전부 FF 여부, 후미 FF 시작, 첫 32바이트의 동일 여부, 전체 차이 바이트 수 및 최대 32개의 차이 오프셋만 출력하며 값은 출력하지 않는다.

**부트 조사 범위:** 검증된 부트 세그먼트 데이터 범위 안에서 `0x1000`, `0x81000`, `0x80000`, `0x100000`, `0xfd000`, `0xfe000`, `0xff000`, `0xfd`, `0xfe`, `0xff`의 little-endian 32비트 바이트열 위치를 찾는다. 정렬 여부와 해당 세그먼트의 헤더 기반 로드 주소를 기록한다. 바이트 일치는 리터럴·명령어·우연한 데이터 중 무엇인지 판별하지 못하며 코드 xref 또는 실행 중 플래시 읽기로 취급하지 않는다. 1 MiB라는 이유만으로 실제 부트로더가 상수 형태로 같은 섹터 주소를 사용한다고 가정하지 않는다.

**명령 제공:** 실행 가능한 Python 표준 라이브러리 명령은 채팅에 직접 제공한다. 작업 폴더 아래 새 B540-10 결과 폴더의 결과 JSON만 생성한다. 디렉터리 `0700`, 파일 `0600`, 소유자는 실제 실행 EUID를 따른다. 입력 파일 변경·신규 추출·설치·다운로드·외부 접속·장치 실행은 없다.

**필요한 결과:** 결과 JSON 출력 전체, 결과 파일 SHA-256, 종료 코드와 오류 출력. 설정 후보 원문은 전달하지 않는다. 입력 검증이나 실행이 실패하면 재실행하지 않고 오류를 먼저 전달한다.

**판단 기준:** 제어 후보의 값이 전형적인 SDK 구조와 닮아도 선택 필드를 자동 확정하지 않는다. 체크섬/순번 해석과 부트로더의 실제 분기를 연결해야 한다. 결과 수신 뒤 오프라인 Xtensa 코드 분석에 필요한 최소 도구·버전·경로·권한 및 산출물 범위의 별도 승인안을 정한다. 현재 장치·UART 로그·네트워크 캡처가 없으므로 실제 실행 관찰을 대체할 수 없다.

### B540-10 결과 검토

**증거 식별 및 실행 관찰:**

- 사용자 전달 JSON 전체, 결과 디렉터리 B540-10 결과 폴더.
- 사용자 보고 결과 JSON SHA-256: `3fa7d8184e168523a826df5d309c36137a4ec359089fe19ad67464e85348f05e`. 바이트 동일한 원본 파일을 로컬에 첨부받지는 않았다.
- 종료 코드 `0`, EUID `0`, 입력 네 파일의 크기·해시는 B540-09와 일치, `input_identity_ok: true`.
- Python 보조 검사이며 새로운 REA Evidence가 아니다.

**제어 후보 및 레코드 비교 관찰:**

- `fd`/`fe`는 전체 4096바이트에서 상대 `+0x8` 한 바이트만 다르다. 원본 위치는 `0xfd008`/`0xfe008`. 실제 차이값은 이번 출력 범위에서 생략했으며 미확인이다.
- 두 섹터의 최종 연속 FF 시작은 상대 `0x492`, 길이 `2926`바이트. 이를 유효 구조 길이 또는 payload 길이라고 확정하지 않는다.
- 제어 후보의 최종 연속 FF 시작은 상대 `0x20`, 길이 `4064`바이트.
- 제어 후보 `[0xff000, 0xff020)`의 little-endian 32비트 관찰값: `+0x00=0xffffff01`, `+0x04=0x55aa55aa`, `+0x08=0x45b`, `+0x0c=0x20`, `+0x10=0x20`, `+0x14=0xf7`, `+0x18=0xf5`, `+0x1c=0xaa55aa55`.
- `+0x00`의 첫 바이트는 `01`, 이후 3바이트는 `ff`이다. 32비트 값으로 출력했지만 실제 구조체 필드 폭은 미확인이다.

**부트 상수 위치 관찰:**

- 정렬된 `0x1000` 바이트열: 원본 파일 `0xdc`, 헤더 기반 메모리 주소 `0x401000cc`.
- 정렬된 `0x100000` 바이트열: 원본 `0x268`, 메모리 `0x40100258`.
- 정렬된 `0xff` 바이트열: 원본 `0x974`, 메모리 `0x40100964`.
- 비정렬 일치 `0x1000@0x269`, `0x100000@0xdb`는 각각 위 정렬 일치와 겹친다. 별개의 독립된 의미상 상수로 집계하지 않는다.
- `0x81000`, `0x80000`, `0xfd000`, `0xfe000`, `0xff000`, `0xfd`, `0xfe`의 지정 32비트 바이트열은 검색 세그먼트 안에서 미검출. 계산된 주소·즉시값·다른 폭으로 구현되었을 수 있어 관련 동작 부재를 뜻하지 않는다.

**작업 가설:** 두 매직값을 가진 제어 레코드가 인접한 두 저장본의 선택·검증을 관리할 가능성이 높다. `+0x00`의 `01`은 저장본 선택 후보이지 앱 슬롯 1의 증거가 아니다. `0x45b`는 순번 후보, 두 `0x20`은 길이 후보, `0xf7`/`0xf5`는 저장본별 검증값 후보로 둘 수 있지만 모두 미검증이다. `fd`/`fe` 첫 부분의 단일 바이트 차이가 부트 관련 필드일 수 있으나 실제 차이값·읽기 폭·비트 마스크·검증 루틴을 확인하기 전에는 OTA 상태나 부트 선택으로 해석하지 않는다.

**다음에 필요한 실제 코드 증거:** 부트 진입 `0x40100438`에서 플래시 크기 결정 → 후미 섹터 주소 계산 → 제어 레코드 magic/선택/검증 검사 → `fd`/`fe` 중 읽기 대상 선택 → 레코드 `+0x8`의 읽기/마스크 → 앱 시작 오프셋 계산 → 정상/실패 복구 분기를 연결해야 한다. 현재는 이 경로를 디코딩·검증하지 않았다.

### B540-11: 최소 Xtensa 디스어셈블러 준비 — 결과 검토 완료

**승인 관찰:** 사용자가 제시한 B540-11 범위를 승인했다. GNU Binutils `2.43.1` 다운로드·서명 검증·Xtensa 소스 빌드, 기존 부트 IRAM 2408바이트의 하위 범위 파일화·디스어셈블에 한정한다. 실제 실행 계정의 권한으로 빌드되며 EUID 0이면 root 권한 실행임을 안내했다.

**선택 이유:** 더 이상의 문자열·상수만으로 선택 로직을 확정하지 않고 실제 명령어 분석으로 전환한다. Java/Ghidra 전체 환경 대신 GNU Binutils의 `objdump`·`objcopy`를 우선 준비해 부트로더 2408바이트의 코드를 분석한다. 기존 GCC/G++ `11.5.0` 및 Make `4.3`을 재사용하며 Node.js·REA·Rust/Cargo·Binwalk를 재설치하지 않는다.

**승인을 요청하는 범위:**

- 버전/대상: GNU Binutils `2.43.1`, `--target=xtensa-elf`, binutils 구성요소 소스 빌드. 전체 GCC 툴체인·Java/Ghidra·Xtensa 외부 플러그인은 설치하지 않는다.
- 다운로드 출처: `https://ftp.gnu.org/gnu/binutils/binutils-2.43.1.tar.xz`, 같은 파일의 `.sig`, `https://ftp.gnu.org/gnu/gnu-keyring.gpg`만 사용한다. 예상 밖 다른 호스트로의 리디렉션은 중단한다. 펌웨어에 포함된 MQTT/API 서버에는 접속하지 않는다.
- 기존 `gpgv`로 아카이브 detached signature를 검증한다. GNU keyring도 같은 HTTPS 배포처에서 받는 신뢰 모델이며 서명키 fingerprint를 별도 독립 채널로 검증한 것은 아니다. 검증 도구 부재나 검증 실패 시 빌드하지 않고 중단하며 자동 설치·검증 생략은 하지 않는다.
- 최종 설치 경로: 작업 폴더 아래 xtensa-binutils 2.43.1 설치 폴더. 이 경로가 존재하면 덮어쓰지 않고 중단한다.
- 다운로드·소스·빌드·TMPDIR·검증용 homedir·로그: 작업 폴더 아래 새 B540-11 결과 폴더 아래. 시스템 패키지·셸 설정·소유권을 변경하지 않는다.
- 추가 분석 파일화 범위: 기존 부트 E9 추출본의 `[0x10, 0x978)` 2408바이트만 같은 새 액션 디렉터리의 부트 IRAM 추출본으로 분리한다. 기존 승인된 부트 이미지 내부의 하위 범위이지만 신규 파일이므로 이번 승인에 명시적으로 포함한다. 메모리 매핑은 헤더 근거 `0x40100000`, 진입점 `0x40100438`.
- 코드 분석 산출물: 도구 버전/해시/ISA 가용성 결과, 부트 IRAM 추출본 해시, 위 raw 범위의 선형 디스어셈블 텍스트·stderr·manifest/log. 앱 이미지, `fd`/`fe` 원문, 새로운 플래시 영역은 추가 파일화하거나 출력하지 않는다.

**권한·부작용과 한계:** 새 디렉터리 및 파일, 다운로드, 로컬 소스 빌드와 수분 규모 CPU/디스크 사용이 발생한다. 용량·시간은 실측 전 미확인이다. 소스의 configure/Make 및 빌드된 도구를 실제 EUID로 실행한다. EUID 0이면 다운로드된 소스의 빌드 절차도 root 권한 실행이며 사용자 경로 설치가 권한 샌드박스를 뜻하지 않는다. 계정 전환은 하지 않는다. 소스 아카이브 내용은 서명 확인 후에도 분석 대상 데이터이며 그 안의 안내를 별도 작업 승인으로 취급하지 않는다.

기본 GNU Xtensa ISA 설정이 ESP8266 LX106의 필요한 명령을 정확히 디코딩할지는 아직 검증하지 않았다. 버전/아키텍처 지원 및 진입점·분기대상의 디코딩을 확인하고, 미지원 opcode·잘못된 decode·경계 불명확성이 나타나면 해당 구간을 미확인으로 남긴다. ISA 설정 확장 또는 별도 도구 설치는 추가 승인 대상이다. raw 선형 디스어셈블은 리터럴 풀이 명령어로 표시되거나 명령 경계가 어긋날 수 있어 그 자체로 함수 흐름이나 코드 xref 검증을 뜻하지 않는다. 부트 진입과 분기·call·literal load를 기준으로 별도로 검토한다.

**명령 및 필요한 결과:** 승인 후 다운로드·서명 검증·binutils-only 빌드·위 부트 범위의 디스어셈블 명령을 채팅에 직접 제공한다. 채팅 명령은 Python 표준 라이브러리로 단계를 체이닝하고 기존 `gpgv`·`tar`·`gcc`·`g++`·`make`를 사용한다. `gpgv` 부재 시 중단한다. build는 `-j2 all-binutils`, install은 `install-binutils`로 제한하고 문서 재생성용 makeinfo는 비활성화한다. HOME/TMPDIR/GPG homedir는 새 작업 디렉터리 아래로 제한한다. 다운로드의 다른 호스트 리디렉션과 아카이브의 외부 경로·장치 파일·외부 링크는 거부한다. 기존 설치 경로가 있으면 덮어쓰지 않으며 실패 산출물도 자동 삭제하지 않는다.

산출물은 실행 로그, 서명 검증 로그, 아키텍처 목록 텍스트, 부트 선형 디스어셈블 텍스트, 부트 진입점 디스어셈블 텍스트, manifest JSON 및 승인된 다운로드·소스·빌드·설치·IRAM 파일이다. raw 선형 출력은 `0x40100000` 기준이며 별도로 진입점 `0x40100438`부터 출력해 리터럴 풀 선행 영역의 오디코딩 영향을 줄인다. 두 출력 모두 도달 가능 코드와 데이터 구분은 추가 검토가 필요하다. manifest 및 해시·서명 검증 결과·아키텍처 가용성·진입점 디스어셈블·종료 코드를 먼저 전달받는다. 준비가 실패하면 기존 경로를 삭제하거나 재설치하지 않고 실패 지점부터 진단한다.

- `0x40100477~0x4010047b`: 스택 선두 32비트의 비트 `24..27`을 추출한다. 호출이 헤더를 읽는다면 flash-frequency nibble과 부합하지만 현재는 가설이다.
- `0x401004ac`: 스택 `+2` 바이트를 읽어 분기한다. 호출이 헤더 읽기라면 flash mode 바이트와 부합한다.
- `0x401004fa~0x40100522`: 스택 선두 32비트의 비트 `28..31`을 추출하고 값 `0..6`에 따라 분기한다. 기존 덤프 헤더 네 번째 바이트 `0x20`을 읽었다면 추출값은 `2`이고 분기 목적지는 `0x401007e9`이다. 해당 목적지 및 합류점은 아직 전문 미수신으로 분석하지 않았다.
- 기본/미인식 경로 `0x4010052e`는 `a12=124 (0x7c)`를 설정한다. `0x40100531~0x40100536`에서 `a3=a1+8`, `a2=a12<<12`, `a4=4`를 설정한다. 이 경로의 계산값은 `0x7c000`이지만 실제 덤프의 크기 분기가 어떤 값을 설정하는지 아직 모른다. 실제 경로가 `0x7c000` 설정을 읽는다고 결론 내리지 않는다.
- 여러 `l32r a2`가 부트 DRAM 로드 범위의 `0x3ffe83xx/0x3ffe84xx`를 참조하고 뒤이어 `0x400024cc`를 호출한다. 문자열 인자·출력 함수 후보이나 다음 단계에서 실제 매핑된 문자열을 확인한다. ROM 주소만으로 확정 함수명을 붙이지 않는다.

**판단:** 부트 코드가 헤더 후보의 크기 필드와 계산된 플래시 주소에 따라 분기하는 정적 증거를 확보했다. 후미 제어의 `01`과 앱 슬롯의 관계, fd/fe `+0x8` 비트 의미, EA 선택·검증 및 복구 규칙은 아직 미확인이다. 함수·호출 경로를 전체 부트 코드로 이어야 한다.

### B540-12: 기존 부트 디스어셈블 전문 및 코드 참조 데이터 전달 — 결과 검토 완료

**목적:** B540-11의 기존 부트 선형 디스어셈블 텍스트를 재사용해 분기 목적지·합류점·호출대상과 literal load를 분석한다. Binwalk/문자열 전체 검사·빌드·설치는 반복하지 않는다.

**범위·명령:** 채팅의 Python 명령으로 기존 부트 선형 디스어셈블 텍스트, 부트 IRAM 추출본, 부트 E9 추출본의 기대 크기·해시를 확인한다. 전문에 표시된 `l32r`의 IRAM 주소가 정렬된 실제 입력 범위에 있으면 입력에서 u32를 읽어 표시 결과와 대조한다. 그 값이 기존 부트 DRAM 세그먼트 로드 범위 안을 가리키면 최대 160바이트의 NUL 종료 printable ASCII만 문자열 후보로 출력한다. 부트 코드·리터럴·참조 문자열 이외의 펌웨어 영역은 읽거나 추출하지 않는다. printable 검사 불합격은 원문 대신 상태만 출력한다. 참조 문자열에도 민감정보가 있을 수 있으므로 사용자가 전달 전 검토한다. 문자열을 독립 기능 증거로 확정하지 않는다.

**산출물·부작용:** 입력 파일은 읽기만 한다. 작업 폴더 아래 새 B540-12 결과 폴더의 결과 JSON만 `0600`으로 생성하고 디렉터리는 `0700`이다. EUID 0이면 새 결과도 root 권한으로 생성된다. objdump 재실행·기존 산출물 수정·신규 raw 추출·다운로드·장치 실행·외부 접속은 없다.

**필요한 결과:** 결과 JSON·SHA-256·종료 코드·기존 부트 선형 디스어셈블 텍스트 전체 출력. 약 40 KiB 전문은 채팅이 길면 부트 텍스트 파일만 첨부하거나 순서대로 나누어 전달한다. fd 설정 레코드 추출본/fe 설정 레코드 추출본 등 설정 파일 원문을 첨부하지 않는다. 실패 시 재실행하지 말고 오류를 전달한다.

**다음 판단:** 전문의 코드/리터럴 경계와 크기 값 `2`의 경로를 검토한다. 선형 출력이 branch target에서 경계가 맞지 않으면 기존 도구로 그 실제 target부터 제한된 디스어셈블을 추가한다. 부트의 필드 read/width/checksum 경로가 확인된 뒤 필요한 메타데이터의 최소 바이트만 읽도록 별도 단계에 명시한다. 원본의 새로운 영역이 필요하면 별도 추출 승인을 받는다.

### B540-12 결과 검토 및 부트 선택 규칙

**증거:** 사용자 전달 전체 JSON 및 기존 부트 선형 디스어셈블 텍스트 전문. 종료 코드 `0`, EUID `0`, 입력 동일성 `true`. 결과 경로 B540-12 결과 폴더, 사용자 보고 JSON SHA-256 `73abf881b0a94808e7d40744c9b44f0ddaa5860f7dc8f24f97d762e834dba682`. 로컬에 바이트 동일한 원본 파일을 첨부받지는 않았다. 정렬된 입력 범위의 literal 값과 objdump 주석 대조는 표시된 모든 해당 항목에서 `true`. Python/objdump 보조 증거이며 새 REA Evidence는 아니다.

**경계 문제:** 선형 출력은 데이터/리터럴 풀 때문에 함수 시작 `0x4010003c`, `0x40100084`, `0x401000dc`, `0x401001a0`, `0x401001fc`, `0x40100234`, `0x40100268`, 진입 `0x40100438` 중 여러 곳의 시작 경계를 놓쳤다. 범위 밖 literal 참조 6개는 그 어긋난 출력에 나타나며 실제 미해결 코드 참조로 채택하지 않는다. 이미 정확한 진입부터 얻은 B540-11 출력을 우선 사용한다. 특히 `0x40100234`는 레코드의 주소 바이트를 조립하는 호출대상이나 전문에서 정확히 디코딩되지 않아 다음 단계에서 해당 시작점으로 재디코딩한다. 부트 문자열 후보가 있다고 LX106 전체 ISA 지원 또는 모든 호출 의미를 확정하지 않는다.

#### 1. 실제 크기 경로와 저장본 선택

- 헤더 크기 nibble `2`: `0x40100507~0x4010050a` → `0x401007e9` → 참조 문자열 `8Mbit(512KB+512KB)\n` → `0x401007f2`에서 `a12=252 (0xfc)` → `0x401007f5`에서 `0x40100531`로 합류한다.
- `0x40100533~0x40100541`: 기준 `a12<<12 = 0xfc000`을 스택 `+160`에 보존하고 `+0x3000 = 0xff000`에서 4바이트를 스택 `+8`에 읽는 호출을 한다.
- `0x40100544~0x4010055a`: 읽은 첫 바이트만 사용한다. **0이면 기준+1 섹터 `0xfd000`, 0이 아니면 기준+2 섹터 `0xfe000`**를 계산하고 8바이트를 스택 `+12`에 읽는다. 제어 바이트 `01`은 따라서 `fe` 저장본 선택에 대응한다. 앱 슬롯 선택과 구분한다.
- 주소·버퍼·길이 인자 및 이미지 magic 후속 검사와 함께 보면 ROM `0x40004b1c`는 플래시 읽기 함수라는 해석이 강하게 뒷받침된다. ROM 내부 코드/독립 심볼/실제 반환값·읽기 성공 여부는 확인하지 않았다.
- 이 경로에는 제어 `+4` 이후의 두 magic·`0x45b`·`0x20`·`0xf7/f5`를 읽거나 검사하는 코드가 없다. 그 필드가 SDK의 다른 루틴에서 선택·검증에 쓰이는지는 미확인이다. 기존 작업 가설을 이 부트로더의 검증 규칙으로 채택하지 않는다.
- **fd/fe의 유일한 차이 `+0x8`은 `[+0,+8)` 밖이다.** 첫 8바이트는 같아 초기 부트 레코드 값도 같다. 차이값을 부트 선택 플래그로 추정했던 B540-10 가설은 이번 코드로 뒷받침되지 않는다.

#### 2. 선택 레코드 형식과 모드 분기

다음에서 `r0~r7`은 선택 섹터 첫 8바이트를 뜻한다. 아직 원문값은 미수신이다.

- 스택 `+12=r0`, `+13=r1`, `+14..16=r2..r4`, `+17..19=r5..r7`.
- `0x4010055d~0x4010056c`: `r1 & 0x1f == 6`이고 `r0 & 3 != 3`이면 그대로 사용한다. 그렇지 않으면 8바이트를 `0xff`로 채우는 후보 호출 뒤 `r0` 하위 2비트를 `0`, `r1` 하위 5비트를 `6`으로 만들고 갱신 함수 `0x401000dc`를 호출한다. memset 후보가 표준 의미라면 초기화 값은 `fc e6 ff ff ff ff ff ff`. 이 갱신은 펌웨어 실행 시 일어날 수 있는 경로이며 조사 호스트가 플래시에 쓴다는 뜻이 아니다.
- `0x40100669~0x40100678`: 고전 user1/user2 경로 조건은 `r1.bit7==1` 및 `(r1.bit6==1 또는 r1.bit5==0)`이다.
- 고전 경로 `0x40100683~0x4010071a`: `state=r0&3`, `backup=(r0>>2)&1`. user1 (`0x1000`)은 `(state,backup)=(0,1)` 또는 `(1,0)`, user2는 `(0,0)` 또는 `(1,1)`, state 2 등은 오류 경로다. user1 주소는 literal을 호출 인자로 쓰고, user2는 아래 산식으로 계산한다.
- 크기 `2`의 user2 계산 `0x40100750~0x4010077c`: `a13=0xfc`; 크기 `3..6` 전용 테이블 경로를 우회; `(((0xfc+4)>>1)<<12)+0x1000 = 0x81000`를 로더 래퍼 `0x40100084`의 인자로 전달한다. 이 산식은 기존 EA 두 후보와 일치한다.
- 고전 경로가 아니면 test/enhance 분기가 이어진다. `r1.bit6==0` 및 `r1.bit5==1`이면 `r2..r4` 주소 조립 함수로 test 주소를 얻는다. 나머지의 `r1.bit7==0`이면 `r0.bit2`에 따라 `r2..r4` 또는 `r5..r7`을 호출대상 `0x40100234`에 준다. 주소 조립의 정확한 비트 연산은 경계 재디코딩 후 확정한다. 다른 조합에는 주소 레지스터의 정의 경로 및 선행 test 분기의 영향이 있어 추가 검토가 필요하다.
- 별도 test-GPIO 분기: 기준 섹터 `0xfc000`의 128바이트를 스택 `+32`에 읽고 스택 `+151`, 즉 원본 `0xfc077`을 검사한다. 값 `0xa0..0xaf`는 GPIO mux 설정과 GPIO 입력 후보 호출에 따라 test 주소 부팅을 유도할 수 있다. 해당 영역은 이번 승인 추출 밖이므로 아직 읽지 않았다. 따라서 일반 레코드 선택만으로 test 경로 부재나 현재 실행 슬롯을 확정하지 않는다. 이 GPIO 로직은 부트 test 모드이지 제품 릴레이 GPIO 확인이 아니다.

#### 3. 이미지 선택 및 실패 경로

- `0x4010003c` 후보 함수는 헤더를 읽고 `0xe9`면 `0`, `0xea`와 두 번째 바이트 `4`면 헤더 `+12` 길이값, 그 외는 `-1`을 반환하는 흐름이다. 정확한 첫 명령/읽기 길이는 다음 단계에서 함수 시작으로 재디코딩한다.
- 로더 래퍼 `0x40100084`: E9면 앱 시작, EA면 앱 시작+반환 길이+`16`을 `0x4010fc08`로 간접 호출한다. 기존 EA 내부 E9 경계 `0x56080`/`0xd61a0`와 일치하는 산식이다.
- `0x401005a0~0x401005ae`에서 부트 DRAM `0x3ffe8010`의 바이트를 `0x4010fc00`으로 복사하는 후보 호출이 있어 `0x4010fc08`은 이 덤프의 DRAM 세그먼트로부터 복사되는 로더 후보이다. 로더 길이는 `0x3ffe8000`의 u32에서 읽으며 아직 미수신이다. ROM 코드라고 오인하거나 승인 밖 메모리로 임의 매핑하지 않는다.
- `0x401001fc`는 레코드 `r0.bit2`가 1이면 이를 0으로 바꾸고 `0x401000dc`로 갱신한 뒤 `first boot failed, reboot to try backup bin` 문자열과 재부팅 후보 함수 `0x401001a0`를 호출한다. 0이면 `backup boot failed.` 경로. 갱신 함수는 읽은 저장본 반대 섹터에 4 KiB를 쓰고 제어 첫 4바이트를 전환하는 흐름이지만 erase/write ROM 호출 내부는 미검증이다.

**현재 결론:** 덤프 헤더와 부트 코드에 따른 저장본 선택은 `fe`로 정적으로 좁혔다. 고전 user2 주소 `0x81000` 및 EA→내부 E9 전달 산식도 코드로 뒷받침된다. 그러나 실제 선택 레코드 값, 로더 검증·진입 분기, test GPIO 설정/입력 및 실제 부팅 관찰이 없어 활성 앱 슬롯은 아직 확정하지 않는다.

### B540-13: 선택 레코드 최소 필드와 정확한 경계 디코딩 — 기존 결과 검토 완료

**목적:** 선택 레코드 `fe` 첫 8바이트와 기존 부트 로더 입력을 확인하고, 선형 출력에서 틀어진 함수 시작을 정확한 주소로 디코딩한다. 이미 분석한 문자열/상수 집계를 반복하지 않는다.

**입력 및 출력 범위:** 기존 B540-09의 부트 E9 추출본, fd 설정 레코드 추출본, fe 설정 레코드 추출본, ff 후미 제어 추출본, B540-11 부트 IRAM 추출본과 설치된 해시 고정 objdump만 사용한다. fd/fe는 첫 8바이트 동일 여부와 **fe `[+0,+8)`만** 출력하며 다른 설정 원문은 출력하지 않는다. 기존 B540-10 전체 차이 증거를 이용해 +8 값은 읽기 출력하지 않는다. 부트 DRAM의 길이 필드 `0x3ffe8000`과 코드 복사 원본 `0x3ffe8010`을 기존 부트 파일에서 확인하되 새 raw 파일을 만들지 않는다.

**디코딩 범위:** IRAM 함수 범위 `[0x4010003c,0x4010007c)`, `[0x40100084,0x401000c6)`, `[0x401000dc,0x40100191)`, `[0x401001a0,0x401001f4)`, `[0x401001fc,0x40100232)`, `[0x40100234,0x4010024c)`, `[0x40100268,0x401002ec)`. 실제 로더 길이가 부트 DRAM 소스 범위 안에 맞으면 기존 부트 E9 추출본을 그대로 objdump binary 입력으로 사용한다. 복사 소스 파일 오프셋 `0x990`을 로더 실행 주소 `0x4010fc00`에 대응시키는 `--adjust-vma=0x4010f270`을 적용하고 로더 진입 `0x4010fc08`부터 복사 길이 끝까지만 디코딩한다. 이 매핑은 해당 복사 범위의 재배치 분석용이며 파일 전체의 실제 로드 주소라고 해석하지 않는다. 새 raw 파일 또는 비탐색 stdin 입력을 만들지 않는다. 로더 출력의 범위 내 l32r literal 값도 같은 입력 오프셋으로 대조한다.

**부작용:** 작업 폴더 아래 새 B540-13 결과 폴더에 결과 JSON·부분 디스어셈블 텍스트·stderr만 `0600`으로 생성한다. 새 raw 파일·추가 영역 추출·설치·다운로드·외부 접속·장치 실행은 없다. EUID 0이면 결과도 root 소유로 예상한다.

**필요한 결과:** 최소 필드 JSON과 SHA-256, 부분 디스어셈블/로더 전문, 종료 코드 및 오류 출력. 레코드 첫 8바이트도 전달 전에 검토한다. 실제 코드가 사용하는 최소 부트 필드이나 자격증명 마스킹의 완전성은 보장할 수 없다.

**후속 승인 경계:** 현재 승인 밖 원본 `0xfc077`의 test-GPIO 한 바이트 검사가 필요하면 정확한 범위와 출력 경로를 별도로 제시하고 승인받는다. 앱 슬롯 선택을 확인한 뒤 코드/버전/MQTT/TLS/제어 분석에 필요한 각 앱 영역의 파일화도 별도로 승인받는다. 메타데이터와 정적 분기 평가를 실제 장치 실행이나 에뮬레이터 실행으로 표현하지 않는다.

#### 2. 이미지 헤더 함수와 복사 로더

- `0x4010003c`는 입력 파일 오프셋을 `a2`로 받고 ROM `0x40004b1c`에 버퍼 `a1`, 길이 `16`을 전달한다. 이후 `E9`이면 `0`, `EA`이고 두 번째 바이트 `4`이면 `+12`의 little-endian u32, 그 외는 메시지 출력 후보와 `-1` 반환이다. 이 함수 자체에서는 해당 읽기 반환 코드가 분기 조건으로 검사되지 않는다.
- `0x40100084` 래퍼는 반환값 `-1`이면 `1`을 반환하고, `0`이면 입력 오프셋 그대로, 그 외이면 입력+반환값+`16`을 복사 로더 진입 `0x4010fc08`에 전달한다. 해시·체크섬을 검증하는 래퍼라는 의미는 아니다.
- 기존 B540-07 경계와 대조: A `0x1000+0x55070+0x10=0x56080`, B `0x81000+0x55190+0x10=0xd61a0`. 일반 user2 경로는 따라서 B 내부 E9를 로더 입력으로 삼는 산식이다.
- 복사 길이 필드는 부트 파일 `0x980`의 u32 `760 (0x2f8)`이다. 소스 `[0x990,0xc88)`는 기존 부트 DRAM 세그먼트 안에 정확히 들어간다. 복사 바이트 SHA-256 `65349a212664dae1d2b7218c015f887697987b0c1e151d415258942b29cca7ed`.
- 소스 DRAM `[0x3ffe8010,0x3ffe8308)` → 실행 매핑 `[0x4010fc00,0x4010fef8)`, 진입 `0x4010fc08`. 파일 전체의 실제 로드 주소가 아니라 이 복사 구간의 재배치 매핑이다. 새 raw 파일은 생성하지 않았다.
- 선두 두 리터럴 `0x40004b1c` 및 `0x400018b4`에 대한 출력의 8개 l32r 참조는 실제 입력 u32와 모두 일치한다. 전자는 플래시 읽기, 후자는 메모리 복사라는 의미가 호출 인자와 후속 코드로 강하게 뒷받침되지만 ROM 내부/독립 심볼/실행 성공은 미검증이다.
- `0x4010fc08~0x4010fc90`: 16바이트 읽기의 반환값과 E9 magic을 검사한다. 헤더 `+4`의 진입 주소를 보존하고 `+1`의 세그먼트 수를 사용한다. 첫 세그먼트 주소·길이는 헤더 다음 8바이트에서 조립하고 이후 16바이트 버퍼 읽기로 데이터를 이어간다.
- `0x4010fc95`에서 XOR 누적값을 `0xef`로 시작한다. byte 또는 word 단위 복사 경로와 16바이트 읽기/복사 루프가 실제 세그먼트 데이터 바이트를 XOR한다. 다음 세그먼트의 주소·길이를 버퍼 또는 분할 읽기로 조립하며 세그먼트 수를 줄여 반복한다.
- 정상 마지막 세그먼트 경로 `0x4010fddc~0x4010fde9`는 버퍼 `+15`의 저장 체크섬과 XOR를 비교한다. 불일치하면 `0x4010fdec`에서 `1`을 반환한다. 일치하면 `0x4010fea9~0x4010feab`에서 보존한 헤더 진입 주소를 `callx0` 한다. 기존 B540-07의 XOR·16바이트 패딩 검사와 부합한다. 서명·암호학적 인증·EA 외부 전체의 무결성을 보장하는 검사는 아니다.
- **예외 경로를 누락하지 않는다:** 세그먼트 수 0은 `0x4010fc90`에서 진입 호출점으로 바로 분기한다. 다음 세그먼트 헤더가 버퍼 경계를 가로지를 때 `0x4010fe69` 읽기 후 반환값이 0이 아니면 `0x4010fe6c`도 실패 반환점이 아닌 진입 호출점 `0x4010fea9`로 간다. 따라서 모든 읽기 오류·형식 오류가 fail-closed된다고 결론 내리지 않는다. 현재 두 내부 E9는 세그먼트 수 3이며 실제 오류·해당 특수 경로의 실행은 관찰하지 않았다. 이 정적 분기만으로 장치 취약점이나 악용 가능성을 확정하지 않는다.
- 출력 범위 안에서 목적지 주소 허용 목록·명시적 세그먼트 수 상한·암호학적 서명 검사를 식별하지 않았다. ROM 호출 내부와 다른 부트 코드의 검사를 포함하는 부재 증명이 아니다. 복사/호출 분석은 정적이며 펌웨어를 실행한 것이 아니다.

#### 3. 실패 복구와 부트 저장본 갱신

- `0x401001fc`는 `r0.bit2`가 1일 때 `r0 &= 0xfb`로 바꾸고 갱신 함수 `0x401000dc`를 호출한다. 현재 레코드를 대입하면 `0xfd → 0xf9`이며 state는 `1`, bit2는 `0`으로 된다. 다음 고전 선택은 **user1(파일 `0x1000`)**이다.
- `0x401000dc`는 제어 첫 4바이트를 읽고, 현재 선택 섹터의 4096바이트를 읽은 뒤 첫 8바이트만 새 레코드로 교체한다. 제어가 0이면 현재 fd를 읽어 fe로 쓰고 제어 바이트를 1로, 0이 아니면 현재 fe를 읽어 fd로 쓰고 제어 바이트를 0으로 바꾸는 흐름이다.
- 현재 값에서는 조건부 복구가 **fe 읽기 → 변경 첫 8바이트를 포함한 4 KiB를 fd에 쓰기 → 제어 섹터를 갱신해 첫 바이트 0으로 전환**하는 코드에 대응한다. 이는 펌웨어의 실행 시 쓰기 경로이며 분석 호스트가 덤프·설정 파일을 변경했다는 뜻이 아니다.
- 호출 인자는 ROM `0x40004a00`의 섹터 지우기, `0x40004a4c`의 플래시 쓰기라는 해석과 부합한다. 내부·실제 성공·전원 차단 안전성은 미검증이며 이 갱신 함수는 각 ROM 반환값을 검사하는 분기를 보이지 않는다. 제어 `+4` 이후의 magic/순번/검증값을 갱신하거나 검증하는 코드로 표현하지 않는다.
- 실패 메시지 뒤 `0x401001a0`는 MMIO `0x60000904`에 0을 쓰고 `0x60000900`을 읽어 bit 연산/쓰기를 반복한 뒤 ROM `0x40002ecc(0x4e20)` 호출을 무한 반복한다. watchdog/reset 준비 및 delay 후보로 해석하되 정확한 MMIO 의미·실제 리셋은 독립 검증하지 않았다.
- bit2가 이미 0이면 `backup boot failed.` 후보 메시지 후 반환한다. 모든 이미지 실패가 항상 이 복구 함수에 도달하거나 성공한 앱 진입 후 실패를 이 로더가 감지한다는 결론은 아니다.

**결론 갱신:** 일반 경로의 최초 대상은 user2(`0x81000`), 로더 입력은 B 내부 E9(`0xd61a0`), 조건부 실패 복구 후 대상은 user1(`0x1000`)로 좁혔다. test-GPIO 우회·실제 읽기/복사/진입 성공·현재 실행 슬롯은 미확인이다. 기존 부트만으로 가능한 코드 경계·최소 레코드·로더 검토를 완료했으며 다음은 승인 밖 최소 test 설정 바이트이다.

### B540-14: test-GPIO 설정 한 바이트 확인 — 결과 검토 완료

- **승인 관찰:** 사용자가 2026-10-23 질문에 `한 바이트 검사와 제한된 JSON 생성만 승인`을 선택했다. 승인 범위는 아래 한 바이트 확인·동일성 해시·새 제한된 JSON 생성뿐이며 다른 범위로 확대하지 않는다. 이후 사용자 결과를 수신해 아래에 검토 기록을 추가했다.
- **목적:** 일반 user2 선택보다 앞서는 test-GPIO 분기의 설정 조건이 덤프에서 성립할 수 있는지 확인한다. 제품 릴레이 핀이나 실제 GPIO 입력/활성 슬롯 검증이 아니다.
- **새로 승인받을 정확한 값 범위:** 원본 파일 오프셋 `[0xfc077,0xfc078)`의 단 한 바이트. 기존 부트가 읽는 128바이트/전체 4 KiB 섹터를 추출하거나 출력하지 않는다.
- **입력:** 분석 호스트의 덤프 사본, 기대 크기 `1048576`, 덤프 기대 SHA-256. 동일성용 전체 파일 해시만 전후 계산하며 다른 바이트는 결과로 공개·추출하지 않는다.
- **출력:** 작업 폴더 아래 새 B540-14 결과 폴더의 결과 JSON에 EUID, 시각, 원본 동일성, 값/정확한 파일 범위, `0xa0 <= 값 <= 0xaf` 조건 여부 및 한계를 기록한다. JSON SHA-256도 출력한다. raw `.bin`·다른 설정 원문은 만들지 않는다.
- **명령:** 승인 후 Python 표준 라이브러리만 사용하는 명령을 채팅에 직접 제공한다. `os.open`/`O_NOFOLLOW`로 열린 일반 파일 FD의 크기·SHA-256을 확인하고 정확히 한 바이트만 `os.pread`로 읽는다. 같은 FD 및 종료 시 현재 경로의 전후 해시·파일 상태를 대조해 변경 여부를 기록한다. 파일 잠금/원자적 스냅샷 보장은 아니다. 입력 동일성 불일치이면 디렉터리 생성 전에 중단한다. 새 JSON은 `0600`으로 배타 생성하며 해시를 출력한다. 기존 B540-13과 도구/시그니처/문자열 분석은 재실행하지 않는다.
- **부작용:** 새 디렉터리 `0700`, JSON `0600`, 소유자는 실제 EUID를 따른다. 이전 EUID 0이므로 root 실행·소유일 수 있다. 원본 읽기와 해시 계산, 최소 JSON 생성뿐이며 설치·다운로드·장치/에뮬레이터 실행·외부 접속·계정/소유권 변경은 없다. 셸 기록은 별도로 남을 수 있다.
- **필요 결과:** 기존 실행 여부를 먼저 구분한 뒤 새 단계 승인·실행이 이루어지면 결과 JSON 전체·SHA-256·종료 코드·오류. 실패 시 재실행하지 말고 오류를 먼저 전달한다.
- **판단:** 값이 `0xa0..0xaf` 밖이면 B540-12에서 검토한 test 설정 조건은 덤프 값 기준으로 성립하지 않는다고 좁힌다. 범위 안이면 실제 GPIO 입력과 해당 선행 분기를 추가 검토해야 하며 바로 user2 또는 test 부팅을 확정하지 않는다. 어느 경우든 실제 활성 슬롯·부팅 성공은 런타임 증거 없이는 미확인이다.
- 앱 파일화·버전/코드 비교·MQTT/TLS/제어 분석용 추가 추출은 이번 승인안에 포함하지 않는다. 신규 도구나 장치·외부 접속 역시 포함하지 않는다.

### B540-14 결과 검토 및 부트 조사 종료 경계

- 사용자 전달 JSON 전체, 결과 디렉터리 B540-14 결과 폴더.
- 보고 시각 `2026-10-23T17:36:01.560154+09:00`, EUID `0`, 종료 코드 `0`.
- 사용자 보고 결과 JSON SHA-256: `44ba5c64447be10de30ec44f4612e007add3b7524af9b693d329df5334557f57`. 바이트 동일한 원본 JSON 파일을 로컬에 첨부받지는 않았다. Python 보조 증거이며 새 REA Evidence가 아니다.
- 원본 크기 `1048576`, 시작/같은 FD 종료/현재 경로 종료 SHA-256이 모두 덤프 기대값과 일치하고 `source_identity_ok: true`. 원자적 잠금·덤프 획득 시점 검증은 아니다.
- 승인 범위 `[0xfc077,0xfc078)`의 값은 `0x00`. `matches_test_gpio_config_range: false`.
- **정적 판단:** B540-12에서 분석한 선행 test-GPIO 설정 값 조건 `0xa0..0xaf`는 이 덤프 값에서 성립하지 않는다. 따라서 이 설정 조건에 의한 GPIO 입력 판정·test 주소 우회는 덤프 기준 일반 선택의 방해 요인에서 제외한다. 모든 test 기능/복구 모드/런타임 GPIO 입력이 없다는 뜻은 아니다.
- **부트 조사 결론:** 제어 `01` → fe 첫 8바이트 `fd e6 ff ff ff ff ff ff` → 유효 레코드/고전 모드 → state `1`, bit2 `1` → user2 **파일 `0x81000` 최초 시도** → EA 래퍼로 B 내부 E9 `0xd61a0` 전달 → 정상 로더 경로의 체크섬 및 헤더 진입 주소 `0x40100004` 호출이라는 정적 연계를 좁혔다. B540-07은 해당 이미지 XOR 일치를 확인했으나 실제 읽기/복사/실행 성공을 측정한 것은 아니다.
- 실패 처리에 도달하고 ROM 지우기/쓰기·재부팅이 기대 의미로 작동하면 bit2를 지워 user1을 재시도하는 경로이다. 실제 활성 앱 슬롯·원래 덤프 획득 시점의 실행 슬롯·실패/복구 발생 여부는 미확인이다. user2를 ‘현재 실행 중’ 또는 ‘항상 부팅 성공’이라고 표현하지 않는다.
- B540-09~14의 부트/메타데이터/복사 로더 정적 조사를 이번 범위에서 정리했다. 실제 장치·기존 UART/네트워크 캡처는 없으므로 런타임 검증을 확대하지 않는다. B540-14를 재실행하거나 후미 섹터를 추가 출력하지 않는다.
- 이전 채팅의 B540-14 명령은 limitations 문자열에 한국어 이외 표현을 넣었다가 즉시 한국어로 덮어쓰는 불필요한 대입을 포함했다. 전달된 결과는 한국어이며 검사를 실패로 해석하지 않는다. 이후 신규 명령에서는 처음부터 한국어만 사용하고 기존 로그는 수정하지 않는다.
