# B540 덤프 분석 — 색인 및 현재 상태

- 최초 작성: 2026-10-23 (KST)
- 마지막 갱신: 2026-11-21 (KST), 제어 기능 근거 문서 [장치 MQTT 제어](mqtt-device-control.md) 추가. 2026-10-23 (KST), 새 에이전트가 실행 여부 확인 후 B540-19 기존 결과 검토 완료; B540-20 후속 제한 분석의 수동 명령 제공, 실행 여부·결과 대기
- 분석 방식: 별도 Rocky Linux에서 사용자가 액션을 수동 실행하고 결과를 전달하면 검토 후 다음 액션을 정한다. SSH 또는 Linux MCP 직접 접속은 사용하지 않는다.
- 상태: 실제 REA Evidence 1건과 Python/objdump 보조 결과를 검토했다. 정적 분석이며 완전한 역공학·원본 소스 복원·동작 검증 완료를 뜻하지 않는다.

## 현재 진행 및 재개 지점

- **재개:** 사용자 실행 완료 확인 후 B540-19의 기존 JSON·4개 텍스트·빈 stderr·종료 코드 `0`을 검토했다. 기존 B540-19 결과 폴더, 보고 JSON SHA-256 `9ee61d74e45441c3f9d208375378df8b56a7ea4f0dc86f80b8af39e34b57a4f2`. 재실행·자동 에이전트 생성·Linux 접속은 하지 않았다.
- **완료:** B540-01~19 결과 검토. 완료된 추출·설치·분석은 재실행하지 않는다. B540-19는 입력/도구 전후 동일성 true 및 objdump 4회 종료 코드 0 보고를 확인했다.
- **대기:** B540-20 외부 초기화 후속·실분기·앱 읽기 helper 제한 분석. 채팅에 수동 명령 제공, 실행 여부·결과는 미수신이다. 실행 또는 성공을 단정하지 않는다.
- **필요 결과:** B540-20 결과 디렉터리, JSON 전체·보고 SHA-256·6개 텍스트 전문·stderr·최종 종료 코드. 이미 실행했다면 재실행 대신 기존 산출물을 사용하고, 실패해도 오류/부분 결과부터 확인한다. `.bin`·설정 원문은 요청하지 않으며 민감정보는 전달 전 검토한다.
- **다음 분석 범위:** 기존 두 앱의 외부 초기화 후속 A `[0x40215d63,0x40215f90)`/B `[0x40295d63,0x40295f90)` 각 557바이트, 실제 분기 A `[0x40215f90,0x40215fc8)`/B `[0x40295f90,0x40295fc8)` 각 56바이트, IRAM 읽기 helper `[0x40101628,0x40101694)` 각 108바이트。입력·해시·매핑·출력 범위는 [앱 초기화 분석의 B540-20](b540-rea-app-init.md)를 참조한다.
- **실행 경계:** 별도 Rocky Linux 9.8, 이전 EUID `0`. 기존 분석 호스트의 작업 폴더 도구·산출물을 재사용한다. 추가 raw 영역 추출·설치·장치/에뮬레이터 실행·외부 접속은 정확한 범위와 경로를 제시해 별도 사용자 승인을 받는다. 계정·소유권을 임의 변경하지 않는다.
- **현재 한계:** 덤프·부트 코드 기준 user2 최초 시도이나 실제 활성 슬롯은 미확인이다. 외부 링크 주소 규칙과 cache 후보 호출 인자는 확인했지만 실제 cache 동작·검증값 일치·정확한 버전·MQTT/TLS는 미확인이다. 제품 제어/계량 기능의 MQTT 오퍼레이션·리소스 처리는 정적 분석으로 [장치 MQTT 제어](mqtt-device-control.md)에 정리했고, 실장비 동작과 릴레이 GPIO는 미확인이다.

## 핵심 요약

### 확인된 사실

- 해시가 고정된 1 MiB 덤프의 선두에 세그먼트 3개와 일치하는 XOR 체크섬을 가진 E9 부트 이미지가 있다. `2nd boot version : 1.6` 문자열을 확인했다.
- `0x01000`, `0x81000` EA 후보에서 길이 필드를 따라 내부 E9 이미지가 이어지며, 두 내부 E9의 세그먼트 경계와 XOR 체크섬이 일치한다.
- 두 이미지의 외부 데이터 및 세 내부 대응 세그먼트가 모두 바이트 동일하지 않다. 기능·버전 차이는 아직 확인하지 않았다.
- 두 애플리케이션 데이터 후보 범위에 SHA-256 K 상수 64개와 AES 정방향·역방향 S-Box 전체가 존재한다.
- `0x7c000`, `0x7d000` 두 4 KiB 설정 후보 섹터는 전체 바이트와 SHA-256이 동일하다. 공개 제품 표기 `B540_W`, `DAWONDNS`와 MQTT/API로 추정되는 도메인 문자열을 포함한다.
- 양쪽 애플리케이션 범위에서 MQTT, HTTP/TLS, Wi-Fi, OTA, UART, GPIO/스위칭, 계량, 스케줄 관련 키워드가 발견됐다. 문자열 조사이며 실제 구현 검증은 아니다.
- 실제 REA `inspect_firmware_regions` 검사 Evidence ID: `ev_2b66eac1dbff97022229d355225c317be63e786edc39fa5b897c524c45c925e0`.

### 가장 잘 뒷받침되는 해석

- **ESP8266 기반 B540_W 관련 플래시 펌웨어 덤프**로 판단한다. ESP8266 표기, 헤더, 로드 주소, 체크섬과 제품 문자열이 함께 뒷받침한다. 실제 장치 모델과 덤프 획득 경위의 독립 확인은 아니다.
- **두 애플리케이션 슬롯을 갖는 OTA형 레이아웃**과 **중복 설정 저장** 가능성이 높다. B540-12~13에서 부트용 fd/fe 저장본 선택·반대 저장본 갱신·실패 후 bit2 전환을 코드로 좁혔다. 제품 설정 0x7c000/0x7d000의 선택 규칙은 별개이며 미확인이다.
- 제어 첫 바이트 `01`은 **fe 부트 레코드 선택**이다. B540-14에서 `0xfc077=0x00`으로 해당 test-GPIO 설정 조건을 덤프 값 기준으로 배제했다. 레코드 `fd e6 ff ff ff ff ff ff`는 **덤프·부트 코드 기준 user2(파일 0x81000) 최초 시도**, 실패 처리 도달 시 user1 재시도와 부합한다. 실제 활성 앱 슬롯·부팅 성공·동적 전환은 미확인이다.
- MQTT·네트워크·제어·계량 관련 기능 후보가 있지만 표준 SDK 문자열을 포함할 수 있다. 해당 제품의 실제 기능 구현은 코드 참조·프로토콜·하드웨어 증거가 있어야 확정할 수 있다.
- B540-17~18에서 공개 문자열 대조와 출력 helper의 실제 `-0x40200000` 연산으로 **외부 링크 주소=0x40200000+원본 파일 오프셋** 규칙을 좁혔다. header size `2`의 앱 초기화는 1 MiB 값을 선택한다. cache 후보 helper는 byte[0x3ffe8004] 값에 따라 ROM `0x40004678`에 `(0,0,1)` 또는 `(1,0,1)`을 전달하며 그 외 값이면 호출을 생략한다. 실제 ROM 의미·cache 실행 매핑은 미확인이고 앱 B를 인자 1과 동일시하지 않는다.
- 정상 magic 후 길이 `32`를 인자로 계산 함수에 전달해 저장 검증값과 비교하는 정적 흐름을 확인했다. 알고리즘·비교 성공은 미확인이다. 파일 `0x3ffe8000` 초기값 `0`은 다른 주소인 런타임 전역 `0x3fffc714`의 값이 아니다.

### 아직 결론 내릴 수 없는 항목

- 활성 슬롯, OTA 상태, 두 이미지의 정확한 버전 및 동작 차이.
- EA 전체 포맷의 별도 인증·체크섬과 실제 Xtensa/cache 실행 매핑.
- MQTT 포트·TLS·토픽·인증 방식, API 엔드포인트의 실제 호출. 명령 및 응답 JSON은 정적 분석으로 [장치 MQTT 제어](mqtt-device-control.md)에 정리했고 실장비 확인은 미확인이다.
- AES/SHA 실제 호출과 TLS 또는 저장 암호화 사용 여부, OpenPGP 서명 존재.
- 릴레이 핀, UART 패킷 형식, 계량 칩과 보정값. 타이머·스케줄의 MQTT 설정 형식은 [장치 MQTT 제어](mqtt-device-control.md)에 정적 분석으로 정리했고 동작 검증은 미확인이다.
- Windows 로컬 원본과 Linux 사본의 해시 동일성, 원본 장치의 플래시 전체성.

## 1. 증거 및 해석 규칙

- **관찰**: 사용자가 전달한 명령 출력 또는 검사 결과에 직접 나타난 사실.
- **추정**: 관찰을 특정 파일 형식이나 장치 동작과 연결한 해석. 추가 검증이 필요하다.
- **미확인**: 현재 도구, 검사 범위 또는 전달된 증거만으로 판단할 수 없는 항목.
- `B540-01` 등의 ID는 이 조사에서 사용하는 액션 ID이며 REA Evidence ID가 아니다.
- 지금까지의 원시 출력은 채팅으로 전달되었다. 별도 원본 로그 파일은 아직 보관하지 못했으며, 상세 문서는 해당 출력의 주요 사실을 정리한 것이다.
- 실제 REA 결과의 Evidence ID, 도구 버전, 대상 해시, 검사 범위와 제한 사항을 함께 기록한다. 첫 결과는 B540-06R에서 확인했다.
- 파일 오프셋과 CPU 메모리 주소를 구분한다. 정적 검사 결과를 실제 실행 관찰로 표현하지 않는다.
- 민감한 설정값은 문서에서 마스킹하고, 생략된 증거 범위를 명시한다.

## 2. 분석 대상과 동일성

### 관찰

- 파일 크기: `1,048,576`바이트, `1 MiB`
- SHA-256: 분석 기준으로 고정한 기대 해시(값은 저장소에 적지 않음)
- B540-02 검사 전후 해시 일치.
- B540-03의 기대 해시, 검사 시작 해시, 검사 종료 해시 일치.

### 한계

- 검사 시작·종료 시점의 해시 일치는 확인했지만, 두 시점 사이에 파일을 잠근 원자적 스냅샷 검사는 아니다.
- Windows 로컬 원본의 해시는 아직 확인하지 않았다. Linux 사본과 로컬 원본의 동일성은 미검증이다.
- 파일명이 B540이라는 사실만으로 실제 장치 모델, 덤프 획득 방법 또는 플래시 전체성을 확정하지 않는다.

## 문서 유지 및 다음 인계 원칙

- 결과를 받을 때는 **이 색인의 현재 상태**, **해당 주제 문서의 상세 액션·결과**, **이력 문서의 짧은 갱신 항목**만 수정한다. 상세 결과를 색인에 중복 추가하지 않는다.
- 새로운 액션의 목적·명령·부작용·필요 결과는 계속 채팅에 직접 제공한다. 상세 기록은 해당 주제 문서에 둔다.
- 새 에이전트는 먼저 이 색인을 읽고 현재 주제 문서를 읽는다. 이전 주제의 해시·승인·근거가 필요할 때만 해당 문서를 참조한다. 과거 인계 기록을 현재 실행 지시로 사용하지 않는다.
- 향후 MQTT/TLS 또는 제어·계량 분석이 실제로 시작되면 해당 주제의 상세 문서를 별도로 분리하고 여기에 링크를 추가한다. 아직 조사하지 않은 기능의 빈 문서는 미리 만들지 않는다.
