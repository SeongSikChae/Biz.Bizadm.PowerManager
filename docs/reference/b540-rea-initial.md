## 3. B540-01: Linux 환경 확인

### 실행 및 결과

- OS: Rocky Linux `9.8` (Blue Onyx)
- 커널: `5.14.0-687.10.1.el9_8.0.1.x86_64`
- 호스트 아키텍처: `x86_64`. 이는 분석 호스트의 아키텍처이며 펌웨어 CPU를 뜻하지 않는다.
- Python: `3.9.25`, `/bin/python3`
- file: `5.39`, `/bin/file`
- 사용 가능한 기본 명령: `sha256sum`, `stat`, `od`, `strings`, `readelf`, `timeout`, `prlimit`
- 당시 PATH에서 찾지 못한 명령: `rea`, `node`, `npm`, `binwalk`, `unblob`, `java`, `analyzeHeadless`
- `GHIDRA_HOME`, `GHIDRA_INSTALL_DIR`, `REA_BINWALK_COMMAND`, `REA_UNBLOB_COMMAND`: 미설정
- 대상 파일: 읽기 가능한 일반 파일로 확인.

### 해석과 범위

- 기존 Python과 기본 명령으로 원본을 변경하지 않는 보조 검사를 수행할 수 있다.
- PATH 검색 실패는 알려진 명령 경로가 없다는 뜻이며, 호스트 전체에 해당 소프트웨어가 없음을 증명하지 않는다.
- Linux REA와 펌웨어 검사 엔진은 아직 사용 가능한 상태로 확인되지 않았다.

## 4. B540-02: 파일 식별

### 관찰

- `file -b` 결과: `DOS executable (COM)`
- 선두 16바이트: `e9 03 00 20 38 04 10 40 00 00 10 40 68 09 00 00`
- 마지막 256바이트 `[0xfff00, 0x100000)`: 모두 `0xff`
- `stat`, `sha256sum`, `file`, 선두·후미 `od` 검사 종료 코드: 모두 `0`

### 해석

- DOS COM 판정은 채택하지 않는다. 통상적인 COM 로드 이미지의 크기 범위를 크게 넘으며, 선두 데이터와 이후 검증 결과는 ESP8266 이미지 형식에 더 잘 부합한다.
- `0xff` 후미는 지워진 플래시 또는 패딩과 부합하지만, 후미 256바이트만 확인했으므로 전체 빈 영역의 시작 위치를 확정할 수 없다.

## 5. B540-03: ESP 이미지 구조 검증

### 검사 방법과 범위

- 기존 Python 표준 라이브러리로 little-endian 이미지 헤더와 세그먼트를 해석했다.
- 파일의 4 KiB 경계에서만 `0xe9` 또는 `0xea` 이미지 후보를 찾았다.
- 선택된 ASCII 부팅·SDK·제품 키워드 문자열을 검색했다. 출력 제한은 40개이고, 실제 일치 결과는 18개였다.
- `0xe9` 이미지의 세그먼트 데이터에 ESP 형식의 XOR 체크섬을 계산했다.
- 추출, 외부 주소 접속, 펌웨어 실행은 수행하지 않았다.
- 전체 이미지 후보 검색, 모든 인코딩 문자열 검사, 모든 파티션 검증은 아니다.

### 5.1 파일 오프셋 0x00000: 유효한 E9 부트 이미지

관찰:

- 매직: `0xe9`
- 세그먼트 수: `3`
- 플래시 모드 원시 값: `0x00`
- 플래시 크기·주파수 원시 값: `0x20`
- 헤더 진입 주소: `0x40100438`

세그먼트:

1. 세그먼트 0
   - 헤더 파일 오프셋: `0x00008`
   - 데이터 파일 범위: `[0x00010, 0x00978)`
   - 로드 주소: `0x40100000`
   - 길이: `2,408`바이트
2. 세그먼트 1
   - 헤더 파일 오프셋: `0x00978`
   - 데이터 파일 범위: `[0x00980, 0x00c88)`
   - 로드 주소: `0x3ffe8000`
   - 길이: `776`바이트
3. 세그먼트 2
   - 헤더 파일 오프셋: `0x00c88`
   - 데이터 파일 범위: `[0x00c90, 0x00f08)`
   - 로드 주소: `0x3ffe8310`
   - 길이: `632`바이트

체크섬:

- 데이터 뒤 패딩: `7`바이트, 모두 `0x00`
- 체크섬 파일 오프셋: `0x00f0f`
- 계산값: `0xd8`
- 저장값: `0xd8`
- 일치: `true`
- 해석된 이미지 끝: `0x00f10` (exclusive)

해석:

- 구조와 체크섬이 일치하는 ESP8266 E9 부트 이미지로 강하게 뒷받침된다.
- 헤더 선언을 ESP8266 형식으로 해석하면 QIO, 1 MiB, 40 MHz이다. 이는 헤더의 설정값이며 실제 장치의 플래시 크기나 동작 주파수를 측정한 결과가 아니다.
- 체크섬 일치는 형식적 일관성의 증거이며, 암호학적 진위나 안전성 검증이 아니다.
- `2nd boot version : 1.6` 문자열과 위치는 2차 부트로더라는 해석을 뒷받침한다.

### 5.2 파일 오프셋 0x01000 / 0x81000: 추가 이미지 후보

관찰:

- `0x01000` 선두 16바이트: `ea 04 00 01 04 00 10 40 00 00 00 00 70 50 05 00`
- `0x81000` 선두 16바이트: `ea 04 00 02 04 00 10 40 00 00 00 00 90 51 05 00`
- 두 위치 모두 `0xea`로 시작하며, 검사기는 extended ESP image 후보로 기록하고 내부 해석은 수행하지 않았다.
- 두 후보 시작 위치의 차이: `0x80000` (512 KiB)

추정:

- ESP8266의 두 애플리케이션 슬롯 또는 OTA 관련 레이아웃일 가능성이 있다.

미확인:

- EA 확장 형식의 정확한 해석, 각 세그먼트 경계, 전체 길이, 체크섬.
- 두 애플리케이션의 버전·기능·내용 차이.
- 현재 선택된 부트 슬롯과 OTA 상태.
- 후보 사이의 모든 영역이 해당 슬롯에 속하는지 여부.

### 5.3 주요 문자열 관찰

부트로더 영역:

- `0x00d01`: `2nd boot version : 1.6`
- `0x00eb0`: `enhance boot mode, `

첫 애플리케이션 후보 주변:

- `0x4e5d0`: `Firmware ONLY supports ESP8266!!!`
- `0x4e9c1`: `SDK ver: %s compiled @ Jul 19 2016 17:58:40`
- `0x4ed80`: `don't supported flash map.`
- `0x4f094`: `SDK version:%s`

두 번째 애플리케이션 후보 주변:

- `0xce6b0`: `Firmware ONLY supports ESP8266!!!`
- `0xceaa1`: `SDK ver: %s compiled @ Jul 19 2016 17:58:40`
- `0xcee60`: `don't supported flash map.`
- `0xcf174`: `SDK version:%s`

제품·설정 관련:

- `0x7c083`, `0x7d083`: `dwmqtt.dawonai.com`
- `0x7c0fb`, `0x7d0fb`: `DAWONDNS`
- `0x7c10a`, `0x7d10a`: `B540_W`
- `0x7c2cd`, `0x7d2cd`: `dwapi.dawonai.com`

해석과 한계:

- ESP8266 표기와 유효한 헤더는 대상 플랫폼 판단을 강하게 뒷받침한다. CPU 코드 참조나 실제 실행은 아직 분석하지 않았다.
- SDK 관련 문자열에 2016-07-19 컴파일 시각이 있지만, 이것을 전체 제품 펌웨어의 빌드 시각이나 정확한 SDK 버전으로 단정하지 않는다.
- `0x7c000`, `0x7d000` 부근에 동일한 제품·서버 문자열이 4 KiB 간격으로 반복된다. 중복 설정 레코드 후보이나 파티션 종류, 레코드 형식, 활성본은 미확인이다.
- 도메인 이름은 문자열 관찰이다. MQTT/API 통신 구현, 프로토콜·포트·TLS, 서버 현재 운영 상태는 미확인이며 해당 주소에 접속하지 않았다.
- `B540_W`는 제품 식별 단서이지만 덤프 원본 장치 모델의 독립적인 확인은 아니다.

## 6. B540-04: Linux 분석 도구 설치 준비

### 승인된 범위

- 사용자 전용 경로: 분석 호스트의 작업 폴더
- Node.js, REA `6.5.0`, Binwalk `3.1.x` 설치 허용.
- sudo, 시스템 패키지, Java/Ghidra, 추가 빌드 도구가 필요하면 별도 확인.

### 제시한 액션

- Node.js `22.22.0` Linux x64 공식 배포 아카이브를 내려받고 공식 `SHASUMS256.txt`와 SHA-256을 비교한다.
- 이 비교는 배포 체크섬 일치 확인이며 별도의 서명 검증은 아니다.
- Node.js 설치 경로: 작업 폴더 아래 Node.js 22.22.0 폴더
- REA 설치 경로: 작업 폴더 아래 REA 6.5.0 폴더
- npm 설치 대상: `rea-agents@6.5.0`
- npm의 `--ignore-scripts`, `--engine-strict`, `--no-audit`, `--no-fund` 옵션을 사용하도록 제시했다.
- npm 캐시와 다운로드·임시 파일도 승인된 경로 아래로 제한한다.
- PATH 변경은 해당 Bash 실행 안에서만 적용하고 셸 설정 파일은 수정하지 않는다.
- 설치 후 REA 패키지 버전과 `rea --help`를 확인한다.
- Binwalk 빌드 판단을 위해 cargo/rustc, C/C++ 빌드 도구, pkg-config, liblzma/fontconfig 가용성만 조회한다.
- 대상 파일 SHA-256을 다시 확인한다.

### 실행 결과 및 현재 상태

- 사용자는 B540-04를 두 번 실행했으며, 첫 실행의 출력은 확보하지 못했다고 알렸다.
- 두 번째 실행에서 `STOP: installation path already exists; not overwriting.` 및 종료 코드 `1`이 반환되었다.
- 이 중단은 Node.js 설치 경로 또는 REA 설치 경로 중 적어도 하나가 존재한다는 뜻이다. 두 경로가 모두 존재하거나 설치가 완료되었다는 증거는 아니다.
- 첫 실행의 다운로드·체크섬·npm 설치 성공 여부 및 마지막 도달 단계는 미확인이다.
- 기존 설치를 삭제하거나 재설치하지 않는다. B540-04R에서 절대 경로를 사용해 Node.js 버전, REA 패키지 버전, CLI 도움말과 Binwalk 빌드 전제 조건을 확인한다.
- B540-04R은 설치·다운로드·의도적인 파일 생성 없이 기존 도구와 패키지를 조회한다. 도구 실행 자체의 내부 부작용까지 보장하는 검사는 아니다.
- 당시에는 Binwalk 설치 명령과 실행 결과가 없었다. 이후 B540-05에서 설치 성공을 확인했으며 아래에 기록한다.
- 이 확인 단계 당시 실제 REA 펌웨어 검사는 미수행이었다. 이후 B540-06에서 명령 완료와 JSON 생성이 보고됐으며 아래에 기록한다.

### B540-04R: 기존 설치 상태 확인 결과

관찰:

- 예상 Node.js/npm 파일, REA `package.json`, `scripts/rea.mjs`, `dist/cli-runtime/cli.js`가 모두 존재한다.
- 패키지 선언: `rea-agents`, 버전 `6.5.0`.
- Node.js 허용 버전 선언: `^22.19.0 || ^24.11.0 || >=26.0.0`.
- Node.js 실행 버전: `v22.22.0`, 종료 코드 `0`.
- npm 실행 버전: `10.9.4`, 종료 코드 `0`.
- 절대 Node.js 경로로 실행한 REA `--help`: `rea@6.5.0`, 종료 코드 `0`.
- 실제 도움말에 `inspect-firmware-regions` 명령이 있으며, 하위 명령 인수는 아직 조회하지 않았다.
- 전체 출력 형식 옵션은 `--format`이고 `json`이 지원된다. 명령 인수는 해당 하위 명령 도움말로 확인한다.
- 빌드 도구: gcc/g++ `11.5.0`, GNU Make `4.3`, pkg-config `1.7.3`. 조회 종료 코드는 모두 `0`.
- pkg-config가 보고한 liblzma `5.2.5`, fontconfig `2.14.0`. 조회 종료 코드 `0`이나 실제 컴파일·링크 성공은 아직 검증하지 않았다.
- PATH에서 cargo/rustc/git를 찾지 못했다.
- 대상 SHA-256은 기존 기대값과 일치한다.

해석과 다음 조치:

- Node.js와 REA의 기존 CLI 설치는 실행 가능한 것으로 확인되어 재설치하지 않는다. CLI 도움말 성공이 모든 분석 엔진의 작동을 보장하지는 않는다.
- 첫 실행의 다운로드 검증 출력은 소실됐으므로 이를 사후에 관찰한 것으로 취급하지 않는다.
- Binwalk `3.1.0`의 소스 빌드에는 Rust/Cargo가 필요하다. 이는 앞서 별도 확인하기로 한 추가 빌드 도구이므로 사용자 전용 설치 범위를 확인한 후 진행한다.
- crates.io 패키지 기반 설치는 git 저장소 복제가 필수는 아니다. git 설치를 기본 요구에 추가하지 않는다.
- 설치를 진행한다면 CARGO_HOME/RUSTUP_HOME, 캐시·임시·빌드·설치 파일을 기존 승인 경로 아래로 제한하고 셸 설정 및 시스템 패키지를 변경하지 않는다.

### B540-05: 사용자 전용 Rust/Cargo 및 Binwalk 설치

- 사용자가 Binwalk 빌드용 추가 Rust/Cargo 설치를 승인했다.
- 승인 범위는 기존 분석 호스트의 작업 폴더 아래이며 sudo, 시스템 패키지, 셸 설정, Java/Ghidra는 변경하지 않는다.
- 공식 Rust 배포 서버와 crates.io 다운로드, 의존성 빌드 스크립트 실행이 포함됨을 안내했다.
- 재현 가능한 툴체인 선택: Rust `1.90.0`, minimal profile. Binwalk 대상 버전: `3.1.0`, Cargo `--locked` 사용.
- Rustup 설치 파일은 공식 배포 서버의 SHA-256 목록과 비교한다. 별도 서명 검증은 아니다.
- Cargo/Rustup 홈, 빌드·임시·설치 파일 및 로그를 승인된 경로 아래로 제한한다.
- `binwalk --version` 및 실제 REA의 `inspect-firmware-regions --help` 출력을 수집한다. 아직 펌웨어 검사는 수행하지 않는다.
- 설치 출력 소실을 방지하기 위해 새 로그 경로에 출력과 오류를 함께 기록한다.

실행 결과:

- 설치 로그: B540-05 결과 폴더의 설치 로그. 내용은 채팅으로 전달됐으며 로컬 원본 로그 첨부는 아직 없다.
- Rustup 설치 파일 SHA-256: `5be191e8c70a5007074254cb74d78dbfdd25cd5a61c27de7b8e5410122ec24f4`.

권한 관련 추가 관찰:

- 전달된 터미널 프롬프트는 root 프롬프트였다. root 셸에서 실행 중일 가능성이 높으나 EUID는 아직 직접 조회하지 않았다.
- 설치 위치가 사용자 홈 아래여도 파일 소유권이 일반 사용자라는 보장은 없다. 이후 분석 명령은 root 셸에서도 지원하되 설치·설정 변경을 추가하지 않는다.
- 실행 계정을 임의로 바꾸거나 소유권을 변경하지 않는다.

### B540-08: 빈 영역·설정 후보·기능 단서 조사

- 원본을 읽어 4 KiB 단위 전부 `0xff`인 영역을 요약하고 trailing FF 시작을 확인한다. 이를 확정 파티션 맵으로 표시하지 않는다.
- `[0x7c000, 0x7d000)`, `[0x7d000, 0x7e000)` 두 후보 섹터의 해시·일치 여부·차이 위치만 비교한다. 비밀번호·SSID·장치 ID 등 설정 원문은 출력하지 않는다.
- 파싱된 애플리케이션 데이터 범위에서 네트워크·OTA·UART·GPIO·계량·스케줄·스위칭 관련 ASCII 키워드 문장의 개수와 위치를 조사한다.
- 민감한 줄은 가리고, 다른 문자열도 직접 인용 대신 제한된 기능 키워드·오프셋 위주로 출력한다. 필터는 민감정보 완전 탐지를 보장하지 않는다.
- 설정 후보 범위에서 이미 확인된 공개 제품명·서버 주소의 위치만 재확인한다.
- 디컴파일을 수행하지 않으며 문자열 후보를 구현·실행 확인으로 취급하지 않는다.
- 새 JSON·오류 로그만 생성하고 원본을 변경하거나 외부 주소에 접속하지 않는다.

실행 결과:

- 디렉터리: B540-08 결과 폴더.
- 종료 코드 `0`; stderr 표시에서 오류 내용은 관찰되지 않았다. 파일 크기는 별도로 전달받지 않았다.
- EUID: `0`으로 root 실행 확인. 도구가 사용자 홈 아래 있다고 실행 권한이 일반 사용자로 제한된 것은 아니며, 이후 기본 분석을 위해 추가 권한 작업은 하지 않았다.
- 검사 시작·종료 대상 SHA-256은 기존 기대값과 일치.
- JSON 전체 내용은 채팅으로 전달됐다. Python 보조 검사이며 새 REA Evidence는 아니다.

전체 바이트가 FF인 4 KiB 섹터의 연속 범위:

- `[0x61000, 0x7c000)`, `110592`바이트 (`108 KiB`).
- `[0x7f000, 0x81000)`, `8192`바이트 (`8 KiB`).
- `[0xe1000, 0xfb000)`, `106496`바이트 (`104 KiB`).
- 파일의 최종 연속 FF 범위: `[0xff020, 0x100000)`, `4064`바이트.
- 정렬된 FF 범위 검사와 trailing 검사 범위가 다르다. 비어 있지 않은 섹터 안의 FF 부분이나 앞선 이미지 끝부터 다음 4 KiB 경계까지는 전부 조사한 것으로 표시하지 않는다.
- `0xfb000` 이후에 전부 FF가 아닌 섹터가 있으나 내용을 파싱하지 않았다. ESP SDK 시스템 설정·RF 데이터 후보일 수 있지만 위치만으로 용도를 확정하지 않는다.

설정 후보 섹터 비교:

- A `[0x7c000, 0x7d000)`, B `[0x7d000, 0x7e000)`: 두 4 KiB 블록 전체 바이트 동일.
- 차이 바이트 수 `0`.
- 두 섹터 SHA-256 같음(개인 설정 영역이라 값은 적지 않음).
- 공개 문자열의 대응 상대 위치도 일치: MQTT 후보 도메인 `+0x83`, `DAWONDNS` `+0xfb`, `B540_W` `+0x10a`, API 후보 도메인 `+0x2cd`.
- 동일한 제품·서버 설정 레코드를 중복 저장한 것으로 추정한다. 두 섹터가 동일하다는 사실은 검증했으나 설정 스키마·활성본 선택·복구 규칙은 미확인이다.
- SSID·비밀번호·장치 ID 등의 설정 원문은 수집 출력과 문서에 표시하지 않았다.

기능 키워드별 일치 문자열 개수 (A/B 순서):

- MQTT: `57 / 57`, 각 영역에서 민감 키워드 포함 줄 `2`개는 샘플 위치 표시에서 제외.
- HTTP/TLS 합산 범주: `16 / 16`, 민감 키워드 포함 줄 각 `4`개 제외.
- Wi-Fi/네트워크: `50 / 51`.
- OTA/업데이트: `18 / 18`.
- UART/시리얼: `4 / 4`.
- GPIO/스위칭: `8 / 8`.
- 계량 관련 일반 키워드: `10 / 10`.
- 스케줄/타이머: `11 / 11`.
- 위 집계는 `image_A_data=[0x1010, 0x60b30)`, `image_B_data=[0x81010, 0xe0c88)`에서 수행했다. 범위에 일부 헤더와 데이터도 포함된다.
- 범주간 같은 문자열이 중복 집계될 수 있다. 숫자는 함수·기능·고유 문자열 수가 아니다. 단순 단어가 SDK 메시지나 무관한 문자열에 포함될 수 있다.
- HTTP와 TLS를 합산한 범주이므로 16개 일치를 TLS 사용 증거로 취급하지 않는다. 계량 칩 이름 또는 제품의 계량 구현이 검증된 것은 아니다.
- 두 영역의 집계가 유사하다는 사실은 공통 SDK·기능군 가능성과 부합하지만 기능 동등성을 입증하지 않는다. Wi-Fi 문자열 1개 차이의 내용·원인도 미검토이다.

후속 조사 시작점으로 보존한 대표 오프셋 (각 범주의 첫 비민감 샘플 A/B):

- MQTT: `0x4f6a0 / 0xcf768`.
- HTTP/TLS: `0x51250 / 0xd1340`.
- Wi-Fi/네트워크: `0x4efe0 / 0xcf0c0`.
- OTA/업데이트: `0x4e5d0 / 0xce6b0`. 이는 알려진 ESP8266 전용 안내 문구에도 일치하므로 OTA 구현 확인점으로 단정하지 않는다.
- UART/시리얼: `0x556c4 / 0xd57b4`.
- GPIO/스위칭: `0x50790 / 0xd0880`.
- 계량: `0x4ef10 / 0xceff0`.
- 스케줄: `0x4ead0 / 0xcebb0`.
- 전체 샘플 위치는 분석 호스트의 결과 JSON 및 이 대화의 전체 전달 결과에 남아 있다. 문자열 원문·연결된 코드·실행 흐름은 아직 수집하지 않았다.

## 7. REA 환경 제한

- 앞선 로컬 REA 상태 조회에서는 REA `6.5.0`, Windows Ghidra `12.1` 엔진 가용성을 확인했다.
- 해당 Windows REA의 Ghidra 경로는 네이티브 x86/x64 PE와 명시적 raw 6502 이미지로 제한된다. 이 ESP8266 덤프를 임의의 x86/6502 프로필로 열지 않는다.
- 펌웨어 검사 `inspect_firmware_regions`는 Linux와 caller-supplied Binwalk `3.1.x` 및 util-linux prlimit 환경을 필요로 한다.
- Linux Binwalk 검사는 구조·시그니처 관찰을 제공하며, Xtensa 코드 디컴파일 지원을 자동으로 보장하지 않는다.
- 심층 코드 분석은 대상 아키텍처와 이미지 매핑을 검증하고 실제 엔진의 지원 범위를 확인한 뒤 별도로 결정한다.

## 8. 이번 범위의 완료 상태와 남은 조사

### 완료한 작업

1. Linux 환경과 도구 가용성 확인, 승인된 사용자 지정 경로에 도구 설치, 실제 버전·실행 상태 검증.
2. 대상 파일 크기·SHA-256·헤더 식별 및 후속 액션별 해시 재확인.
3. REA/Binwalk 시그니처 검사와 Evidence ID·보고 한계 기록.
4. E9 부트 이미지 및 두 EA 후보 뒤 내부 E9의 경계·체크섬, 대응 데이터 차이 조사.
5. SHA-256 전체 K 상수 및 AES 정방향·역방향 S-Box 검증.
6. 두 설정 후보 섹터 전체 비교, FF 영역 조사, 제한된 기능 키워드와 후속 조사 오프셋 보존.
7. 관찰·추정·미확인을 분리한 한국어 기본 분석 결과 문서화.

### 부분 확인 또는 미수행

- 기능 후보 조사는 문자열 수준까지 수행했다. 코드 참조·함수 디컴파일은 Xtensa 매핑·도구 지원 검증 및 추가 환경 준비가 필요하므로 이번 범위에서 수행하지 않았다. 이 보고서의 완료 상태가 해당 기능 검증 완료를 뜻하지 않는다.
- 원본 구조는 기본 정적 조사 수준에서 확인했다. 파티션 전체 의미, EA 전체 검증·매핑, 슬롯·버전·부팅 선택 규칙은 미확인이다.
- Windows 원본 해시와 Linux 사본 동일성, 설치 당시 첫 다운로드 검증 로그, 로컬에 바이트 동일한 원본 증거 파일 보관은 미확인이다.
- root 권한으로 실행했으므로 향후 런타임·신규 설치가 필요할 경우 권한 범위를 별도로 정해야 한다. 파일 소유권은 변경하지 않았다.

### 후속 심층 분석의 우선 대상

- MQTT 연결·인증·토픽·메시지/응답 구조와 API 호출 추적: 공개 문자열을 출발점으로 실제 호출 참조와 함수 흐름 필요.
- 슬롯별 EA/IROM 매핑과 부트 선택 메타데이터: 형식에 맞는 파서·주소 매핑 검증 필요.
- 제어·계량 기능: UART 메시지, GPIO·릴레이 처리, 계량 칩·보정 루틴의 코드 또는 장치 증거 필요.
- 보안·암호 동작: TLS 호출·인증서 검증·AES/SHA 호출 흐름이 필요하며 상수 포함만으로 결론 내리지 않는다.

예비 조사 완료 시점에는 심층 분석 도구 설치, 내용 추출 또는 장치 실행을 승인·수행하지 않았다. 이후 B540-09에서 부트 이미지와 후미 세 섹터의 제한 추출만 승인되어 manifest를 전달받았다. 이 승인·실행의 구체적인 범위는 9절에 기록하며, 다른 영역 추출·신규 도구 설치·장치 실행까지 확대하지 않는다.
