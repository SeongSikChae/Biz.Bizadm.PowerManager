# B540 앱 진입 및 초기화 분석

- 범위: B540-15~20, 두 앱 파일화, IRAM 진입·초기화, 정적 외부 링크 매핑, cache 후보와 SDK 검증 흐름.
- 상태: B540-19 기존 결과 검토 완료; B540-20 외부 초기화 후속·실분기·앱 읽기 helper 제한 분석의 수동 명령 제공, 실행 여부·결과 대기.
- [분석 색인 및 현재 상태](b540-rea-analysis.md) · [초기 조사](b540-rea-initial.md) · [부트 분석](b540-rea-boot.md) · [기록 이력·과거 인계](b540-rea-history.md)

> 정적 링크 주소와 실제 실행 매핑을 구분한다. 실제 활성 슬롯·cache 동작·정확한 버전·제품 기능은 미확인이다. 과거 단계의 미확인 표현은 이후 결과와 함께 읽으며, 완료된 명령을 재실행하지 않는다.

## 단계별 기록

### B540-15: 두 앱 검증 범위 파일화 및 제한 진입점 디코딩 — 결과 검토 완료

- **승인 관찰:** 사용자가 2026-10-23 `두 검증 이미지 파일화·제한 진입점 분석만 승인`을 선택했다. 아래 두 이미지·정적 진입점·제한 산출물 범위만 승인됐으며 신규 설치·다른 영역 추출·장치 실행·외부 접속은 포함하지 않는다. 이후 사용자가 실행 결과를 전달해 아래 결과 검토에 반영했다.
- **목적:** 덤프 기준 최초 시도 앱 B와 대체 앱 A를 기존 코드 분석 도구의 입력으로 보존하고, 내부 E9가 선언한 실제 IRAM 매핑·진입점을 출발점으로 cache/IROM 설정과 버전/코드 차이를 조사한다. 전체 문자열·Binwalk·부트 조사를 반복하지 않는다.
- **새 승인 요청 범위:** 원본의 A `[0x01000,0x60b40)` `392000`바이트와 B `[0x81000,0xe0c90)` `392336`바이트, 총 `784336`바이트만 새 액션 디렉터리의 앱 A 이미지 추출본, 앱 B 이미지 추출본으로 파일화한다. B540-07에서 내부 E9 끝까지 검증한 범위이며 전체 512 KiB 슬롯이나 제품 설정 섹터를 추출하지 않는다. 다른 raw 하위 파일은 만들지 않는다.
- **입력·동일성:** 분석 호스트의 덤프 사본, 기대 크기/해시는 B540-14와 동일. 승인된 두 이미지의 외부 데이터/내부 세그먼트 기대 해시는 B540-07 값을 재사용해 산출물 동일성을 검증한다. 기존 objdump 작업 폴더 아래 xtensa-binutils 2.43.1의 objdump, 크기 `8615816`, SHA-256 `42e3012463be044cadfc14733c45e645c5b038f36ee60574972527b8f645ac30`를 재사용한다. 버전·설치 가용성 검사나 재빌드는 하지 않는다.
- **추가 디코딩 범위:** 두 앱의 내부 E9 IRAM 진입 `[0x40100004,0x40100104)` 각 256바이트만 기존 objdump로 디코딩한다. raw binary 입력은 위 두 이미지 파일 그대로 사용한다. A IRAM 데이터 파일 `0x56090` → 이미지 상대 `0x55090` → 선언 로드 `0x40100000`, `--adjust-vma=0x400aaf70`. B IRAM 데이터 파일 `0xd61b0` → 이미지 상대 `0x551b0` → 동일 선언 로드, `--adjust-vma=0x400aae50`. 이 재배치 매핑은 IRAM 구간에만 유효하며 전체 EA 파일의 CPU 주소라고 해석하지 않는다.
- **매핑 한계:** 외부 EA/IROM 데이터의 실행 주소·cache bank/슬롯 전환 방식은 아직 미확인이다. `0x402...` 주소를 슬롯 시작에 임의 가산하거나 두 외부 데이터를 동일 주소로 가정하지 않는다. 진입점의 실제 호출·상수·cache 설정을 받은 뒤 후속 범위를 정한다. 선언된 DRAM 로드 주소는 B540-07을 재사용한다.
- **출력:** 작업 폴더 아래 새 B540-15 결과 폴더에 위 두 `.bin`, 앱 A 진입점 디스어셈블 텍스트, 앱 B 진입점 디스어셈블 텍스트, stderr 로그, manifest JSON만 생성한다. manifest에는 EUID/시각/원본 전후 해시/추출 파일 해시·범위/기존 세그먼트 매핑·해시 대조/실제 objdump 명령·종료 코드/산출물 해시 및 진입점에 표시된 범위 내 IRAM l32r literal의 u32 대조를 기록한다. 설정 원문·전체 앱 문자열·계정정보를 별도 출력하지 않는다.
- **부작용:** 새 디렉터리 `0700`, 파일 `0600`; EUID 0이면 root 소유이며 샌드박스를 뜻하지 않는다. 원본 읽기 및 약 784 KiB raw+작은 텍스트/JSON 생성, 기존 objdump 두 번의 제한된 정적 실행뿐이다. 설치·다운로드·장치/에뮬레이터 실행·외부 접속·계정/소유권 변경은 없다. 앱 코드 안에도 고정 자격증명·식별자가 있을 수 있어 raw 파일은 채팅/외부에 전달하지 않고 텍스트·JSON도 사용자가 전달 전 검토한다.
- **명령:** 승인 후 Python 표준 라이브러리와 기존 objdump를 사용하는 명령을 채팅에 직접 제공한다. 원본을 O_NOFOLLOW로 읽어 기대 크기·해시를 확인하고 기존 B540-07 외부 데이터/세그먼트 해시·경계를 산출물에 대조한다. 기존 objdump 크기·해시를 검증하고 버전/설치 검사 없이 두 진입점만 디코딩한다. 새 파일은 배타 생성, chmod/umask 0600이며 오류 시 실패 manifest와 stderr를 남기고 자동 삭제·재실행하지 않는다. 성공 여부는 manifest 및 종료 코드·원본/산출물 동일성으로 구분한다. `HOME`/`TMPDIR`를 기존 사용자 지정 분석 경로로 한정하되 샌드박스나 네트워크 차단을 보장하는 것은 아니다. 실제 에이전트 실행은 하지 않으며 사용자 결과 대기이다.
- **필요 결과:** manifest JSON·보고 SHA-256·두 진입점 텍스트 전문·종료 코드·오류. raw `.bin` 파일은 요청하지 않는다. 진입 코드가 현재 ISA로 일관되게 디코딩되지 않으면 그 구간을 미확인으로 남기고 신규 도구를 임의 설치하지 않는다.
- **다음 판단:** cache/IROM 실제 매핑을 좁힌 뒤 선택 앱 B를 우선 분석하고 A를 비교 대상으로 사용한다. 정확한 버전/빌드/동작 차이·MQTT/TLS·제품 GPIO/UART/계량은 이 파일화·진입점만으로 확정하지 않는다. 후속 제한 코드 분석은 단계별로 범위를 설명하며 추가 raw 영역·설치·실행·외부 접속이 필요하면 별도 승인받는다.

### B540-15 결과 검토

#### 증거와 산출물

- 사용자 전달 manifest JSON 전체와 두 진입점 텍스트 전문, stderr, 종료 코드 `0`. 재추출·재실행하지 않았다.
- 결과 디렉터리 B540-15 결과 폴더, 시각 `2026-10-23T17:42:31.407075+09:00`, EUID `0`, `success: true`.
- 사용자 보고 manifest JSON SHA-256: `7ea868d1460fc427d22a6aacedcfb562739757b89f8245ad238dc1e237c1db11`. 원본 JSON/텍스트/raw 파일의 바이트 동일 사본은 로컬에 첨부받지 않았다. Python/objdump 보조 증거이며 새 REA Evidence가 아니다.
- 원본 시작·종료 SHA-256은 기대값과 일치, `source_identity_ok: true`, `tool_identity_after_ok: true`. 설치·버전·Binwalk·전체 문자열 검사를 반복하지 않았다.
- A 앱 A 이미지 추출본: 파일 `[0x1000,0x60b40)`, `392000`바이트, SHA-256 `29e386c4eaf308b8425a57d0c87b98771365dfb263d338137dce8fd662c336dd`.
- B 앱 B 이미지 추출본: 파일 `[0x81000,0xe0c90)`, `392336`바이트, SHA-256 `b4ca0b76d24bdc06ff1e0890d06fbb3213e3d8276e3e4b65a1497dea07ea9d09`.
- 두 이미지의 외부 데이터 및 3개 내부 세그먼트 보고 해시는 모두 B540-07과 일치한다. IRAM 크기는 모두 `31728 (0x7bf0)`바이트, 선언 매핑 `[0x40100000,0x40107bf0)`.
- 앱 A 진입점 디스어셈블 텍스트: `3082`바이트, SHA-256 `22c136253ee419f57e2554f4b19e3163ad7dc9b9f4af541a72e555e385dea8c7`.
- 앱 B 진입점 디스어셈블 텍스트: `3080`바이트, SHA-256 `d05a5bfb1f587c49a6fed08f154ed00d84ccd36bc09b806d74fab676022f627c`.
- stderr 로그: `28`바이트, SHA-256 `3a6ef3381c2b07d24d02a2a30a7d57dfc7147984fdbfe7b66d0c32eed5490041`. 내용은 명령이 삽입한 `=== 앱 A ===` 및 `=== 앱 B ===` 두 줄뿐이다. 비어 있지 않지만 objdump 오류·경고는 전달 내용에서 관찰되지 않았다. 두 objdump 종료 코드 `0`, 보고 산출물 mode 모두 `0o600`. 디렉터리 mode/실제 파일 UID는 manifest에 없어 직접 검증하지 않았다.

#### 진입점과 경계 문제

- 두 앱 `0x40100004`는 검증된 IRAM literal `0x40100000`을 `a2`로 읽고 `0x40100007`에서 `wsr.vecbase a2`, `0x4010000a`에서 `call0 0x40100268`을 실행하는 정적 코드이다. **현재 앱의 0x40100268은 이전 부트 이미지의 같은 주소와 바이트가 다른 대상이다.** 부트 SPI helper 의미를 이 앱 주소에 전용하지 않는다.
- 호출 후 `0x4010000d`에 `ill`, `0x40100010`에 `waiti 2` 및 반복 분기가 표시된다. 초기화 함수가 반환하지 않는 구조와 부합하지만 호출대상·실제 실행 없이 확정하지 않는다.
- 진입 이후 선형 범위에는 예외 벡터/패딩/리터럴 풀이 섞인 것으로 보이며 `excw`·불완전 명령 표시가 많다. 기본 binutils의 LX106 전체 ISA 지원 실패라고 단정하지도, 이들 전부를 실제 실행 opcode라고 채택하지도 않는다. 실제 call/branch target부터 다시 디코딩할 범위를 정한다.
- `0x40100051`의 `l32r` 및 주석 주소 `0x400e14a0`은 선언 IRAM 밖이고 경계가 틀어진 선형 출력에 나타난다. objdump binary 입력은 재배치 후에도 전체 EA 파일이므로 주석의 `0x52520d42`/`0x00f00df0`는 잘못된 메모리 매핑으로 다른 파일 바이트를 읽은 표시일 수 있다. 실제 ROM literal/유효 참조/앱 기능 차이로 채택하지 않는다.
- IRAM 안의 literal 대조는 4개씩 모두 `true`: vector base `0x40100000`, 포인터 `0x3ffe8000`, 예외 경로 후보 스택 `0x3ffeaf30`(A)/`0x3ffeaf60`(B), 호출대상 `0x40100210`.
- `0x4010009f` 이후 표시되는 레지스터 저장·`epc1`/`exccause`/`excvaddr`/`excsave1` 읽기·PS/SAR 변경 및 `0x40100210` 간접 호출은 예외 처리 경로와 부합한다. 정확한 해당 경로 시작은 아직 별도 확인하지 않았으며 일반 부팅 초기화나 MQTT 호출로 해석하지 않는다.
- A/B의 stack literal 차이는 `0x30`이다. A DRAM 2 선언 끝 `0x3ffe8db0+0x20f4=0x3ffeaea4`, B 끝 `0x3ffe8db0+0x212c=0x3ffeaedc`. stack literal은 이 선언 데이터 끝보다 각각 `0x8c`/`0x84` 위에 있다. 링크/메모리 배치 차이 단서일 뿐 버전·기능·제품 스택 전체를 확정하지 않는다.
- 출력 마지막 `0x40100102`는 3바이트 명령이 stop-address `0x40100104`에 걸쳐 끝난 표시이다. 실제 opcode 부재 또는 지원 실패로 채택하지 않는다.

**결론:** 앱 진입의 공통 vector base 및 앱 초기화 호출대상 `0x40100268`을 확보했다. 외부 IROM 매핑·cache 설정·정확한 버전·기능 동등성은 아직 미확인이다. B540-15의 파일화는 완료됐으므로 같은 raw 범위를 다시 추출하지 않는다.

### B540-16: 기존 앱 초기화 호출대상 제한 디코딩 — 결과 검토 완료

- **목적:** 두 앱의 실제 진입이 직접 호출하는 `0x40100268`부터 초기화 흐름·cache/IROM 관련 호출/주소 후보를 얻는다. 부트 이미지의 동주소 함수와 혼동하지 않는다.
- **입력:** 기존 B540-15 디렉터리의 앱 A 이미지 추출본/앱 B 이미지 추출본과 기존 objdump만 읽는다. 크기/기대 해시는 위 B540-15 결과를 사용한다. 원본 전체·설정·새 영역을 읽거나 추출하지 않는다.
- **디코딩 범위:** 각 앱의 선언 IRAM `[0x40100268,0x40100468)` 512바이트. A `--adjust-vma=0x400aaf70`, B `--adjust-vma=0x400aae50`를 재사용하고 전체 EA의 실제 CPU 매핑으로 해석하지 않는다. 범위 내 l32r은 같은 IRAM 데이터에서 u32를 대조한다. 호출/분기 타깃은 목록으로만 기록하고 외부 IROM/DRAM 값·문자열은 조회하지 않는다. 출력에 리터럴 풀이 섞이면 다음 실제 타깃으로 경계를 좁히며 자동 재귀 디스어셈블하지 않는다.
- **명령:** 채팅에 Python 및 기존 objdump 명령을 직접 제공한다. 새 raw 파일·추출·설치·다운로드·펌웨어 실행·외부 접속이 없는 기존 파일의 후속 정적 분석이다. 입력 크기/해시·IRAM 재배치·전후 동일성을 확인하고 기존 산출물은 덮어쓰지 않는다. binutils 버전/빌드 검사는 반복하지 않는다.
- **출력·부작용:** 작업 폴더 아래 새 B540-16 결과 폴더에 앱 A 초기화 디스어셈블 텍스트, 앱 B 초기화 디스어셈블 텍스트, stderr 로그, 결과 JSON만 생성한다. 디렉터리 `0700`, 파일 `0600`; 실제 EUID 0이면 root 소유일 수 있다. 기존 objdump 두 번·최대 30초씩 timeout, 입력 읽기/해시와 작은 텍스트/JSON 생성뿐이며 샌드박스·네트워크 격리를 보장하는 표현은 하지 않는다.
- **필요 결과:** 결과 JSON·SHA-256·두 초기화 텍스트 전문·종료 코드·오류. raw 파일을 보내지 않고 텍스트/JSON도 전달 전 민감정보 여부를 검토한다. 실패하면 기존 오류/산출물을 먼저 전달하고 재실행하지 않는다.

- 선택 레코드 첫 u32의 비트 `8..12`를 보존하고 제어 `+12+4*s`, `+20+4*s` u32를 스택에 보존한 뒤 `0x401004f4(선택 레코드 버퍼)`를 호출한다. 필드의 checksum/순번 의미나 검증 결과는 아직 미확인이다. 기존 control s=1 값으로는 +16=0x20, +24=0xf5에 대응하지만 실제 의미 확정은 아니다.
- `0x401006ac`은 IRAM `0x401001b0`, 이어 외부 링크 주소 A `0x40215fe8`/B `0x40295fe8`로 호출한다. 전자는 cache 관련 후보로 다음 코드 확인 필요, 후자는 아직 디코딩·함수 의미 미확인이다.
- **부트와 다른 검증:** `0x401006c4`의 스택 `+0x4ac`은 제어 `+4`이며 `0x55aa55aa`와 비교한다. 이어 스택 `+0x4c4`은 제어 `+28`이며 `0xaa55aa55` 또는 `0xffffffff`이면 `0x401007b0`로 분기한다. 그렇지 않은 magic 조합에서 A `0x40215fc8`/B `0x40295fc8`에 인자 `q-3`으로 호출하는 경로가 있다. 미검토 함수에 erase/reset/checksum 이름을 임의 부여하지 않는다. B540-12의 부트 선택 경로에서 이 magic을 검사하지 않는다는 결론과 모순되지 않는다.
- 기존 B540-10 제어의 두 magic은 위 비교값과 일치하므로 읽기/size/unit 전제가 맞으면 `0x401007b0` 경로에 대응한다. 목적지의 순번/길이/검증값 처리 및 성공/복구 흐름은 다음 단계에서 확인한다.

- `0x40100728`은 실제 분기 타깃인데 선형 출력은 `0x40100726`부터 엇갈려 `0x40100729` 범위 밖 l32r로 표시했다. 이 가짜 주석/분기 의미를 채택하지 않고 타깃 `0x40100728`부터 재디코딩한다.

### B540-18: 초기화 후속·cache 관련 호출대상 제한 분석 — 결과 검토 완료

- **목적:** header size 2의 분기 `0x40100796`, 정상 magic 후속 `0x401007b0`, 초기화 끝과 실제 cache 관련 호출 `0x401001b0`를 연결하고 기존 DRAM의 플래시 구조 pointer 최소 필드를 확인한다.
- **입력:** 기존 B540-15 앱 두 파일과 기존 objdump만 읽는다. 원본 전체·부트/설정 raw·신규 도구는 사용하지 않는다. 이미 완료된 문자열·부트·시그니처 분석은 반복하지 않는다.
- **정확한 디코딩 창(각 앱):** `[0x40100728,0x4010073a)` 18바이트 — 잘못된 선형 경계의 실제 target; `[0x40100765,0x40100965)` 512바이트 — 이전 잘린 명령 뒤부터 초기화 후속과 크기 분기·magic 후속; `[0x401001b0,0x4010020c)` 92바이트 — 실제 초기화 call target. 새 literal/분기 경계가 보이면 자동 재귀 분석하지 않고 다음 타깃을 정한다. 입력 전체의 IRAM adjust-vma는 기존 A/B 값 재사용.
- **최소 pointer 필드:** 선언 DRAM1의 `0x3ffe8000` u32만 읽어 `0x3fffc714` 값이 동일한지 대조한다. pointer가 기존 앱의 선언 DRAM 데이터 안에 있으면 해당 pointer `+4`, `+12`의 u32만 읽는다. 다른 DRAM·설정 원문·자격증명·식별자는 출력하지 않는다. 이것은 파일의 초기화 데이터이며 ROM 값/실제 실행 값이 아니므로 size 이후 갱신·RAM 변경을 별도로 고려한다.
- **출력·부작용:** 작업 폴더 아래 새 B540-18 결과 폴더 아래 두 앱의 세 코드 텍스트(총 6개), stderr 로그, 결과 JSON만 생성. 디렉터리 `0700`, 파일 `0600`, EUID 0이면 root 소유일 수 있다. 기존 입력 해시 대조·objdump 6회 각 30초 timeout·IRAM literal/최소 pointer 대조뿐이다. 새 raw·추출·설치·장치/에뮬레이터 실행·외부 접속·계정/소유권 변경 없음.
- **필요 결과:** JSON 전체·SHA-256·6개 텍스트 전문·stderr·종료 코드. 전송량이 크면 기존 텍스트만 첨부/분할하며 raw `.bin`·설정값은 보내지 않는다. 오류 시 재실행하지 말고 실패 산출물/오류를 전달한다.
- **판단과 한계:** 주소 산식·control magic/검증값 참조·cache helper 의미는 실제 call 인자/리터럴/분기와 연결해 검토한다. 정적 코드가 실제 실행·활성 슬롯·외부 링크 전 영역의 실행 매핑을 증명하지 않는다. 신규 raw 범위·설치·장치 실행·외부 접속이 필요하면 별도 승인받는다.
- **명령:** 위 범위만 수행하는 Python 및 기존 objdump 명령을 채팅에 직접 제공했다. 이후 전체 결과를 수신했으며 아래에 검토를 기록한다.

#### cache 관련 helper와 실제 크기 분기

- 정확한 helper `[0x401001b0,0x401001e2)`는 `byte[0x3ffe8004]`를 읽는다. `0`이면 ROM `0x40004678(0,0,1)`, `1`이면 같은 ROM에 `(1,0,1)`을 전달하며 그 외 값이면 이 ROM 호출 없이 반환한다. 리터럴 주소·u32 대조 모두 일치한다.
- 이 호출 패턴은 ESP8266 Cache_Read_Enable 후보와 부합한다. 다만 이번 출력에 독립 ROM 심볼/ROM 코드/런타임 증거는 없으므로 함수명, 인자의 bank/주소변환 의미, 실제 cache 적용 성공은 미확인으로 유지한다. **앱 B이므로 첫 인자가 반드시 1이라는 결론은 아니다.** 두 앱의 해당 helper 명령은 같다.
- B540-17의 크기 nibble `2 → 0x40100796`은 literal `0x100000`을 크기 인자에 설정하고 `0x40100610`으로 돌아간다. 기본 512 KiB 경로가 아닌 **1 MiB 값**을 선택하는 정적 경로이다. 해당 경로는 앞서 확인한 byte[0x3ffe8004]=0 설정과 연결된다. 다른 초기화·호출이 플래그를 바꾸는지와 실제 읽힌 헤더/ROM 구조체는 미확인이다.
- helper 뒤에는 리터럴 풀과 다른 함수가 이어진다. `0x401001e5/0x401001ed` 등의 선형 명령을 helper 일부로 채택하지 않는다. 후속 MMIO/전역 쓰기는 별도 함수 후보이며 제품 GPIO/릴레이 제어로 확정하지 않는다.

#### magic 후 길이·검증값 비교 및 외부 초기화 호출

- `0x401007b0`는 스택 `+0x4cc` 값을 `32`와 비교한다. B540-17의 저장 관계상 제어 `+12+4*s`에서 온 값이다. 현재 s=1이면 기존 제어 `+16=0x20`과 부합한다. 순번으로 확정하지 않고 **선택 저장본의 검증 길이 필드** 후보로 좁힌다.
- 길이가 32이면 `a2=선택 레코드의 스택 버퍼`, `a3=그 길이`를 전달해 A `0x402177ac`/B `0x402977ac`를 호출한다. 반환 a2를 스택 `+0x4c8`의 저장값(제어 `+20+4*s`)과 비교한다. 현재 s=1의 기존 제어 `+24=0xf5`와 연결되지만 계산 알고리즘 및 실제 일치는 아직 확인하지 않았다. 0x494바이트 전체 또는 서명/암호학적 인증을 검증한다고 표현하지 않는다.
- 길이가 32가 아니거나 계산값이 다르면 A `0x40215fc8`/B `0x40295fc8`에 `a2=q-3`을 전달한 뒤 `0x401006f1`로 합류한다. 일치 경로도 같은 지점으로 합류한다. 미디코딩 호출에 erase/reset/복구 성공 이름을 부여하지 않으며 불일치가 반드시 부팅 중단이라는 결론은 아니다.
- 실제 분기 `0x40100728`은 `call0 0x40101694` 후 반환값이 정확히 1인지 정규화해 `0x4010075a`로 갈지 결정한다. 그 반환 의미는 미확인이다. 앞서 잘못된 경계의 주석은 대체한다.
- 초기화 후반 `0x40100768`에서 literal A `0x40215b64`/B `0x40295b64`를 읽고 `0x4010076b`에서 `callx0` 한다. 이후 스택과 레지스터 복원·`ret.n`이 있다. 따라서 이 함수는 IRAM startup에서 실제 호출하는 **외부 초기화 함수 후보**이다. SDK 메인/user_init/MQTT 진입이라고 이름을 확정하지 않는다.
- 호출대상 차이 `0x80000`은 슬롯간 링크 주소 차이와 같다. 후속 진단 문자열은 A `0x4024ea40...`/B `0x402ceb20...`, timer 관련 전역은 A `0x3ffeb0c0`/B `0x3ffeb0f0` 등 배치 차이가 있지만 버전·동작 동등성/차이를 증명하지 않는다.

#### 최소 DRAM 검사의 한계와 선형 디코딩 제외

- 파일 초기 DRAM `0x3ffe8000` u32는 A 이미지 상대 `0x5cc88`, B `0x5cda8`에서 모두 `0`. `matches_literal_3fffc714: false`, 산술상 pointer+4/+12는 `0x4/0xc`라 선언 DRAM 밖이고 조회하지 않았다.
- **이 검사로 runtime 구조체 포인터를 판정할 수 없다.** startup의 literal `0x3fffc714`는 `0x3ffe8000`과 다른 전역 주소이다. 이전 최소 검사안의 두 값을 연결하는 가정은 성립하지 않는다. 0x3ffe8000 초기값 0을 ROM 전역의 값 또는 NULL 구조체·손상 증거로 해석하지 않는다. ROM 영역/실제 RAM 조회로 자동 확대하지 않는다.
- continuation의 실제 startup 뒤 리터럴 풀에서 경계가 틀어졌다. 특히 A `0x40100801/0x40100804`와 A/B `0x401008e9/0x401008ea` 등의 범위 밖 l32r 주석, B의 `0x401008f8 → 0x4016271c` 표시는 실제 함수/호출/기능 차이로 채택하지 않는다. 실제 target `0x40100800` 등부터 디코딩하면 경계가 복구될 수 있지만 이번 후속 목적에 필요 없어 추가 실행하지 않는다.
- 출력 끝 `0x40100963`의 잘린 명령도 실제 ISA 지원 실패로 판단하지 않는다. 관찰된 timer/리스트 유사 후속 흐름을 제품 스케줄·계량 기능으로 확정하지 않는다.

### B540-19: 외부 초기화·검증값 계산 실호출대상 제한 디코딩 — 기존 결과 검토 완료

- **목적:** IRAM startup에서 확인된 외부 call target을 정적 링크 주소 모델로 디코딩해 다음 SDK/사용자 초기화 호출을 얻고, 길이 32의 검증값 계산 함수가 어떤 연산을 하는지 확인한다. MQTT/TLS/제어 기능을 문자열만으로 확정하지 않는다.

#### 검증값 계산: 초기값 0xef의 8비트 XOR

- 실제 call target A `[0x402177ac,0x402177da)`/B `[0x402977ac,0x402977da)`의 명령 바이트는 전달 텍스트상 같다. 반환은 A `0x402177d8`/B `0x402977d8`의 `ret.n`이다. 반환 이후의 데이터·다른 함수는 계산 루틴에 포함하지 않는다.
- 입력 `a2`는 버퍼, `a3`는 길이이다. 길이 0이면 `0xef`를 반환한다. 길이가 0이 아니면 누산값 `a0=239 (0xef)`, 인덱스 `a6=0`으로 시작해 `l8ui buffer[index]` → XOR → `extui ... 0,8`로 8비트 누산값을 유지하고, 인덱스는 `extui ... 0,16`으로 16비트에 한정해 길이와 비교한다.
- B540-18의 길이 `32` 호출에는 **`0xef XOR buffer[0] XOR ... XOR buffer[31]`**을 반환하는 연산이다. SHA/AES/CRC/암호학적 인증 계산이 아니다. 이 함수의 32바이트 계산을 SDK 설정 전체 `0x494`바이트의 무결성 검증 또는 서명 검증이라고 확대하지 않는다. 일반 길이 전 범위에서 안전하게 종료하는 함수라고 보장하지도 않는다(인덱스 16비트 제한).
- 호출자는 반환값을 저장 제어 u32와 비교한다. 기존 s=1의 저장값 `0xf5`가 이 결과와 일치하려면 해당 32바이트의 순수 XOR이 `0x1a`여야 한다는 산술적 필요조건만 얻었다. 이번 입력에는 설정 레코드 원문이 없으므로 실제 계산·비교 일치·런타임 성공은 미확인이다. 설정을 새로 추출하거나 원문을 요청하지 않았다.
- 실제 함수 안에는 l32r이 없다. JSON의 계산 창 literal 대조 각 4개는 반환 뒤 다른 함수 후보의 참조이다. 주석/u32 일치가 반환 뒤의 선형 출력 전체를 실제 코드로 만드는 것은 아니다.
- 반환 뒤 A/B `...77da`부터 리터럴 데이터가 명령처럼 표시된다. A `0x402177e9 → 0x402578ec`의 `call4`, B의 `lsxu f0`·`excw` 및 틀어진 프롤로그는 실제 이 계산 함수의 호출/ISA/기능 차이로 채택하지 않는다. 후속 별개 함수가 필요할 때는 실제 시작/호출 근거를 확보하며 이번 다음 범위에는 포함하지 않는다.

- 초기화 창 끝 A `0x40215d63`/B `0x40295d63`의 2바이트 `movi.n a4,1`은 stop-address를 가로질러 바이트가 출력되지 않았다. 손상/ISA 미지원으로 판단하지 않는다. 함수 반환·user_init 연결은 아직 범위 밖이다. 다음 창은 이 실제 명령 시작부터 이어가며 이미 완전 디코딩한 초기화 창 전체는 반복하지 않는다.

### B540-20: 외부 초기화 후속·실분기·앱 읽기 helper 제한 디코딩 — 수동 명령 제공, 결과 대기

- **목적:** B540-19 창 끝의 잘린 명령부터 외부 초기화 후속/새 call target을 얻고, 실제 분기 `...15f90/...95f90` 경로와 IRAM `0x40101628`의 플래시 읽기 후보 의미를 확인한다. 아직 user_init·SDK 버전·제품 기능을 확정하지 않는다.
- **기존 입력·도구:** B540-15 결과 폴더의 두 앱 및 기존 xtensa-elf-objdump만 재사용한다. 크기·SHA-256은 위 B540-19 및 아래 인계 값을 따른다. 원본 덤프·제품/SDK 설정 파일·다른 raw 입력은 열지 않으며 새 raw 추출·설치·장치/에뮬레이터 실행·외부 접속은 없다.
- **각 앱 코드 범위:** 외부 초기화 후속 A `[0x40215d63,0x40215f90)`/B `[0x40295d63,0x40295f90)` 각 557바이트; 실제 분기 A `[0x40215f90,0x40215fc8)`/B `[0x40295f90,0x40295fc8)` 각 56바이트; IRAM 읽기 helper `[0x40101628,0x40101694)` 각 108바이트. 각 앱 총 721바이트, 두 앱 합계 1442바이트다. 임의 재귀 디코딩·전체 문자열/포인터 검색·범위 밖 코드 확장은 하지 않는다.
- **매핑:** 외부 adjust A `0x40201000`/B `0x40281000` 및 유효 데이터 경계는 B540-19 그대로 사용한다. 내부 IRAM은 A 이미지 상대 `0x55090`·adjust `0x400aaf70`, B 상대 `0x551b0`·adjust `0x400aae50`, 선언 `[0x40100000,0x40107bf0)`만 유효하다. 둘을 파일 전체의 실제 CPU/cache 매핑으로 혼동하지 않는다.
- **최소 데이터 대조:** 각각 코드 창 내 l32r의 literal 주소가 해당 매핑 구간 안에 4바이트 정렬돼 있으면 그 u32와 objdump 주석만 대조한다. 가리키는 문자열/버퍼/설정/MMIO/ROM은 미조회로 남긴다. 기존 이미지의 외부 길이와 IRAM segment header/경계만 확인하며 별도 raw 파일은 만들지 않는다.
- **명령:** 채팅에 `/bin/python3`와 기존 objdump 6회(각 30초 timeout)만 사용하는 복사 가능한 수동 명령을 직접 제공한다. 입력/도구를 O_NOFOLLOW·일반 파일 FD로 읽어 기대 크기/해시를 확인하고 FD 기반 실행/입력 전달 후 전후 FD·현재 경로의 동일성을 확인한다. 기존 설치·버전·가용성 검사는 반복하지 않는다. 네트워크 차단·샌드박스·원자적 잠금은 보장하지 않는다.
- **출력·부작용:** 작업 폴더 아래 새 B540-20 결과 폴더 아래 앱 A 후속 디스어셈블 텍스트, 앱 B 후속 디스어셈블 텍스트, 앱 A 분기 디스어셈블 텍스트, 앱 B 분기 디스어셈블 텍스트, 앱 A 읽기 helper 디스어셈블 텍스트, 앱 B 읽기 helper 디스어셈블 텍스트, stderr 로그, 결과 JSON만 생성한다. 디렉터리 `0700`, 파일 `0600`, EUID 0이면 root 소유다. 기존 입력/도구 읽기·해시·작은 텍스트/JSON 생성 이외에 계정/소유권 변경·다운로드·앱 실행은 없다. 오류 시 실패/부분 산출물을 보존하고 자동 재시도·삭제하지 않는다.
- **필요 결과:** 기존 결과 디렉터리 경로, JSON 전체·보고 SHA-256·6개 텍스트 전문·stderr·최종 종료 코드. 전달 전 민감정보 검토, `.bin`·설정 원문 전송 금지. 이미 실행했거나 실패했다면 재실행하지 말고 기존 결과/오류부터 전달한다.

## B540-19 새 에이전트 인계 — 2026-10-23 (과거 시점; 이후 위 결과 검토 완료)

> 아래는 인계 당시 기록이며 현재 실행 지시가 아니다. 새 에이전트는 실행 여부 확인 후 B540-19 기존 결과를 수신·검토했으며 재실행하지 않았다. 현재 재개점은 위 B540-20이다.

- 사용자가 B540-19부터 별도 새 에이전트에서 이어가겠다고 요청했다. 현재 채팅의 추가 분석·실행 안내는 중단한다. 새 에이전트를 자동 생성하거나 Linux에 접속하지 않았다.
- B540-18까지 결과 검토 완료. B540-19는 Python/objdump 명령을 이전 채팅에 직접 제공했으나 실행 여부·결과는 아직 미수신이다. **새 에이전트의 첫 행동은 실행 여부 확인**이다. 이미 실행했다면 기존 결과 디렉터리·JSON·보고 SHA-256·4개 텍스트·stderr·종료 코드를 받는다. 오류가 있었다면 부분 산출물부터 받고 자동 재실행하지 않는다. 미실행으로 확인되면 위 B540-19 범위의 수동 명령만 제공한다. 명령 전문은 이 문서에 저장되지 않았으므로 이전 채팅을 참조하거나 같은 범위·검증·부작용을 유지해 다시 작성한다.
- 기존 입력 디렉터리: B540-15 결과 폴더. A 앱 A 이미지 추출본 크기 `392000`, SHA-256 `29e386c4eaf308b8425a57d0c87b98771365dfb263d338137dce8fd662c336dd`; B 앱 B 이미지 추출본 크기 `392336`, SHA-256 `b4ca0b76d24bdc06ff1e0890d06fbb3213e3d8276e3e4b65a1497dea07ea9d09`.
- 기존 도구: 작업 폴더 아래 xtensa-binutils 2.43.1의 objdump, 크기 `8615816`, SHA-256 `42e3012463be044cadfc14733c45e645c5b038f36ee60574972527b8f645ac30`. 새 설치·빌드·가용성 탐색·Binwalk·전체 문자열·완료된 추출을 반복하지 않는다.
- 마지막 확인 결과: B540-18 결과 폴더, 보고 JSON SHA-256 `a568f7f087aa85bcf275e7545749f9eb70c5451d5c5090dfac818c4492517e71`, 종료 코드 `0`. 사용자 전달 텍스트/JSON 보조 증거이며 바이트 동일한 원본 로그는 Windows에 첨부받지 않았다.
- 별도 Rocky Linux 9.8, 이전 EUID `0`. 모든 명령은 사용자 수동 실행이며 SSH/Linux MCP 직접 접속 금지. 액션 ID·목적·복사 가능한 명령·부작용·필요 결과를 한국어 채팅에 직접 제공한다. 새 raw 추출·설치·장치/에뮬레이터 실행·외부 접속은 별도 승인 대상이다.
- 정적 외부 링크 규칙과 실제 cache 실행 매핑을 구분한다. 앱 B를 cache 인자 1과 동일시하지 않고 `0x3ffe8000` 초기값을 `0x3fffc714`의 런타임 값으로 취급하지 않는다. 실제 활성 슬롯·계산 알고리즘/검증 성공·버전·MQTT/TLS·제어/계량은 미확인이다.
- 결과를 받으면 [색인](b540-rea-analysis.md)의 현재 상태, 이 문서의 B540-19 결과, [이력](b540-rea-history.md)의 짧은 항목을 갱신한다. 과거 B540-13 인계 문구를 현재 지시로 사용하지 않는다.
