# D01_28 분석을 끝까지(인자 추적) 하고, 주소 모델을 경험적으로 바로잡는다

## 상황

plan 검토 1회차 지적. plan의 슬롯 B 주소 매핑이 틀렸다(검토 의견: 검증된 적재 규칙과 0x80000 어긋남). 메인이 원격 `.dis`로 확인하니 핵심은 맞으나 원인이 달랐다 — FOTA 형식 문자열(`GET %s%s` 등)은 irom이 아니라 DRAM(`0x3ffe9a17`)이고, 기존 `appB-irom.dis`는 그 문자열을 `l32r`로 싣는 코드를 포함하지 않는다(요청 생성이 SDK `upgrade_lib`이거나 앱이 완성 url을 넘기는 방식). 매핑과 분석 깊이를 정해야 했다.

- 정한 단계: plan
- 관련: 옛 작업 스펙의 plan.md 요약·결정·인터페이스·데이터·검증 전략(`docs/specs/b540-fota-path/`(지움. `15dc357`에 있음)), 짝 태스크 `T01_02`

## 결정

- A. 깊게: plan 주소 모델을 이미지 세그먼트 헤더에서 도출한 값으로 바로잡고, 필요한 범위를 다시 디스어셈블해 `GET %s%s`의 두 조각을 끝까지 추적한다.
- 옛 기록의 결정 칸: A(사용자 선택, 2026-11-20)

## 이유

- spec C1~C6을 실제로 충족하려면 정확한 요청 경로가 필요하고, 사용자가 404 원인을 끝까지 보기를 원했다. B는 빠르지만 "왜 404인가"의 정확한 답(경로 구성)을 못 준다. - 경험적으로 확정한 매핑(이미지 세그먼트 헤더, 바깥 EA 0x81000 + 안쪽 E9 0xd61a0): - irom0: 파일 0x81010~0xd61a0. 기존 `appB-irom.dis`는 0x40201000에 감쌈(`.dis` 주소 = 파일 + 0x40180000). 펌웨어 참 링크 주소 = 파일 + 0x40200000(= `.dis` 주소 + 0x80000), `b540-mqtt-topic.md`의 0x402cxxxx 표기와 같은 기준. - IRAM: vaddr 0x40100000, 파일 0xd61b0, 길이 0x7bf0(`appB-iram.dis`). - DRAM: seg2 vaddr 0x3ffe8000(파일 0xddda8), seg3 vaddr 0x3ffe8db0(파일 0xdeb5c). FOTA 문자열은 seg3.
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.

## 버린 안

| 안 | 버린 이유 |
| --- | --- |
| B. 구조만: 깊은 인자 추적은 접고, 이미 확인한 구조적 사실(FOTA 흐름·설정 키·URL 분할·문자열 DRAM 위치·404는 서버에 테스트 장치용 이미지가 없을 가능성)만 `b540-fota.md`에 반영하고 정확한 `%s`는 미확인으로 둔다. | 위 「이유」에 함께 적힘 |
