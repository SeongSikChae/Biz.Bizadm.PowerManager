# D01_21 FOTA 헤더 순서는 만든 요청 메시지의 단위 테스트로 보고, 가짜 서버로는 헤더가 있는지와 값만 본다

## 상황

plan 검토 1회차 지적 1. plan은 FOTA 고정 헤더를 장치와 같은 순서로 보낸다고 정하고 가짜 서버로 순서를 확인한다고 했다. 그런데 가짜 HTTP 서버(Kestrel)는 잘 알려진 헤더를 정해진 칸에 담아 원래 순서를 보존하지 않는다. 기존 가짜 서버는 받은 헤더를 사전에 담아 순서가 아예 없다. 그래서 그 검증은 늘 실패하거나 순서를 보지 않고 통과한다. spec C16은 `Connection`·`User-Agent`가 있는지만 요구하고, 순서는 plan이 더한 것이다.

- 정한 단계: plan
- 관련: 옛 작업 스펙의 plan.md 결정(FOTA 헤더), 바꿀 파일·구조(테스트 파일), 검증 전략 C14(`docs/specs/dawon-fake-device/`(지움. `15dc357`에 있음)), 짝 태스크 `T01_01`

## 결정

- A. 순서는 단위 테스트: 가짜 서버로는 고정 헤더가 모두 있고 값이 맞는지만 본다. 순서는 `FotaDownloader`가 만드는 `HttpRequestMessage`의 헤더 순서를 단위 테스트(`FotaDownloaderTests.cs`)로 본다. 회선 위 순서는 확인하지 않는다고 적는다.

## 이유

- 장치 순서대로 넣는 의도는 단위 테스트로 지키고 가짜 서버를 늘리지 않는다. B는 spec에 없는 요구를 위해 테스트 코드가 늘어난다. C는 다원이 헤더 순서로 거를 가능성에 대한 대비를 버린다.
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.
