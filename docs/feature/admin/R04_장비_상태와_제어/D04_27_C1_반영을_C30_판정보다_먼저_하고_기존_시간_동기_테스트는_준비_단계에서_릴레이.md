# D04_27 C1 반영을 C30 판정보다 먼저 하고, 기존 시간 동기 테스트는 준비 단계에서 릴레이 상태를 먼저 보고한다

## 상황

plan 검토 1회차 지적 1. C30을 구현하면 릴레이 상태를 모르는 장비가 `tisyn`을 보낼 때 서버가 `r` `/100/0/30`도 서버 → 장치 토픽에 보낸다. 기존 `TimeSyncResponseTests`의 세 테스트는 그 토픽에 응답이 하나뿐이라고(`Single()`) 단정하고, `MqttPacketFragmentationTests`는 `tisyn` 뒤 TLS 레코드가 하나라고 단정하며, `MqttSubscribeLogTests.NonDownlinkTopics_HaveNoDeliveryLogs`는 전달 로그가 하나라고 단정한다. 그런데 plan은 기존 테스트 파일을 고치지 않는다고 적었고, 한 메시지 안에서 C1 반영과 C30 판정의 순서도 정하지 않았다. 그대로면 기존 테스트가 실패해 C28을 채우지 못한다.

- 정한 단계: plan
- 관련: 옛 작업 스펙의 plan.md 바꿀 파일·구조(서버 테스트), 결정(장비 메시지 처리 순서), 검증 전략 C28(`docs/specs/device-control/`(지움. `15dc357`에 있음)), 짝 태스크 `T04_02`

## 결정

- A. 순서를 정하고 테스트 준비를 바꿈: C1 반영을 C30 판정보다 먼저 한다. `TimeSyncResponseTests`·`MqttPacketFragmentationTests`는 장치가 `tisyn` 전에 `/100/0/31` 상태 보고를 먼저 보내게 준비 단계만 바꾸고 단정은 그대로 둔다. `MqttSubscribeLogTests`는 이미 `/100/0/31` `true`를 보내므로 고치지 않는다.

## 이유

- 사용자가 말하지 않음
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.
