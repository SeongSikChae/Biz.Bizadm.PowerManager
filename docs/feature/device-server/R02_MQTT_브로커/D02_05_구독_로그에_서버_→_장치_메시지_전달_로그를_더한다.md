# D02_05 구독 로그에 서버 → 장치 메시지 전달 로그를 더한다

## 상황

이 작업의 범위. 목표는 서버가 보낸 서버 → 장치 메시지(`tisyn` 응답 `w` `/99/0/1`)가 장비까지 가는지 서버 로그로 가리는 것이다. 이슈 #23 처음 범위는 클라이언트의 구독·구독 해제 기록뿐이었다. 그런데 구독 기록만으로는 "구독이 있다"까지만 알 수 있고, 브로커가 그 메시지를 장비 클라이언트에게 실제로 넘겼는지는 알 수 없다. MQTTnet 5.2에는 메시지를 어느 구독 클라이언트의 큐에 넣었는지·버렸는지 알려 주는 이벤트(`ApplicationMessageEnqueuedOrDroppedAsync`)와 구독자가 없어 아무에게도 가지 않았음을 알려 주는 이벤트(`ApplicationMessageNotConsumedAsync`)가 있다.

- 정한 단계: spec
- 관련: 옛 작업 스펙의 spec.md 무엇을·왜, C3·C4(`docs/specs/mqtt-subscribe-log/`(지움. `15dc357`에 있음)), 짝 태스크 `T02_06`

## 결정

- A. 구독 + 전달 로그: 구독·구독 해제 로그에 더해, 서버 → 장치 토픽 메시지가 어느 클라이언트에게 넣어졌는지/버려졌는지, 구독자가 없어 아무에게도 가지 않았는지를 로그로 남긴다. 장치 → 서버 메시지는 서버 핸들러만 받으므로 전달 로그를 남기지 않는다. 이슈 #23 제목·본문을 범위에 맞게 고친다.

## 이유

- A는 구독이 있는데도 장비가 반응하지 않을 때 "브로커가 장비 ClientId에게 넘겼다"까지 서버 로그로 확인되어, 남은 원인을 장비 쪽(수신 처리)으로 좁힐 수 있다. 장치 → 서버 메시지를 빼므로 로그가 크게 늘지 않는다. B는 구독이 확인된 뒤에도 전달 여부를 UART 같은 다른 방법으로 다시 확인해야 해 목표를 한 번에 채우지 못한다.
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.
