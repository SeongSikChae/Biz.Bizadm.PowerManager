# D02_06 전달 로그에서 버림을 빼고 큐에 넣은 것만 남긴다

## 상황

spec 검토 1회차 지적 1. 검토 의견: C3이 서버 → 장치 메시지를 "버렸으면 Warning"으로 남기라고 했지만, MQTTnet 5.2는 넘침 정책이 `DropOldestQueuedMessage`이면 큐에 넣기가 늘 성공하고, 밀려 버려지는 이전 메시지는 별도 이벤트 `QueuedApplicationMessageOverwrittenAsync`로만 알려진다(`MQTTnet.Server.xml`의 `MqttSessionStatus.TryEnqueueApplicationMessage` 설명). 서버는 넘침 정책·큐 크기를 정하지 않아 MQTTnet 기본값을 쓰므로 C3의 Warning 경로는 일어나지 않고, 자동 테스트로 확인하려면 브로커 옵션을 바꿔야 해 "동작을 바꾸지 않는다"(C5)와 부딪힌다. 확인할 수 없는 완료 조건이 남는 것이 문제다.

- 정한 단계: spec
- 관련: 옛 작업 스펙의 spec.md 무엇을·왜, C3. D001의 "넣었는지·버렸는지"는 이 결정으로 "넣었는지"가 된다.(`docs/specs/mqtt-subscribe-log/`(지움. `15dc357`에 있음)), 짝 태스크 `T02_06`

## 결정

- A. 버림을 빼고 넣음만: C3을 "큐에 넣을 때마다 받는 클라이언트마다 Information 로그(보낸 ClientId, 받는 ClientId, 토픽)"로 줄이고 버림 여부·Warning을 뺀다.

## 이유

- A를 고른 이유는 버림이 한 클라이언트 큐에 메시지가 기본 한도만큼 쌓여야 생기는 드문 상황이고, 이번 목표(서버 → 장치 메시지가 장비까지 가는지)는 넣음 로그와 구독자 없음 로그(C4)로 채워지기 때문이다. B는 드문 상황을 위해 요구와 테스트용 설정 주입 경로를 늘리고 C5 문구까지 한정해야 해 고르지 않았다.
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.

## 버린 안

| 안 | 버린 이유 |
| --- | --- |
| B. 덮어쓰기까지 Warning: 버림을 "큐에 넣지 못함 또는 큐에 있던 메시지가 새 메시지에 밀려 버려짐"으로 정의해 둘 다 Warning으로 남기고, 버림 경로는 테스트에서만 큐 크기를 작게 준 브로커로 확인하며, C5의 "동작을 바꾸지 않음"은 운영 설정 기준으로 한정한다. | 위 「이유」에 함께 적힘 |
