# D02_02 기준 spec R5는 `tisyn` 응답만 적고, 명령 발행(`w`·`chg`·`reb`)은 구현하지 않은 채 둔다

## 상황

spec 검토 2회차 지적 2. 「기준 spec에 미치는 변경」은 R5에 "서버 → 장치 발행은 `w`만 동작"이라고 적게 되어 있었는데, 완료 조건 C1~C4는 `tisyn` 응답만 정한다. `tisyn`과 상관없는 일반 `w` 발행의 `sid`(현재 `IDeviceCommandPublisher.WriteAsync`에는 `sid` 인자가 없음), retain 여부, 토픽은 어떤 조건에도 없어서, 기준 spec이 "`w` 발행이 동작한다"고 적으면서 그 동작은 정해지지도 확인되지도 않은 채 남는다.

- 정한 단계: spec
- 관련: 옛 작업 스펙의 spec.md 「기준 spec mqtt-broker에 미치는 변경」, 「하지 않는 것」(`docs/specs/tisyn-response/`(지움. `15dc357`에 있음)), 짝 태스크 `T02_05`

## 결정

- A. R5를 `tisyn` 응답으로 한정: R5에는 "기본 핸들러가 `tisyn`에 응답한다"만 적고, 명령 발행(`MqttDeviceCommandPublisher`의 `w`·`chg`·`reb`)은 지금처럼 `NotImplementedException`으로 둔다. `tisyn` 응답은 명령 발행과 별개인 시간 동기 응답으로 정한다.

## 이유

- 범위가 가장 작고, 근거 없는 일반 `w` 명령의 동작(어떤 `sid`·QoS로 보낼지)을 이번 작업에서 정하지 않아도 된다. B는 인터페이스 변경과 테스트가 늘고, 일반 명령 발행의 동작을 실장비 근거 없이 정하게 된다.
- 옛 결정 기록을 옮긴 것이다. 옛 기록은 사용자가 직접 말한 이유와 에이전트의 추천 이유를 나눠 적지 않았다.

## 버린 안

| 안 | 버린 이유 |
| --- | --- |
| B. 일반 `w` 발행도 정의: `WriteAsync`의 토픽, retain 없음, `sid`(인자로 받도록 인터페이스를 바꿈)를 완료 조건에 더하고 테스트하며, `tisyn` 응답도 이것을 써서 보낸다. | 위 「이유」에 함께 적힘 |
